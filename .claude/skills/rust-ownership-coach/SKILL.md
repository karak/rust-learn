# 借用チェッカとの向き合い方（指導モード）

**このスキルの目的は、エラーを消すことではなく、コンパイラが守ろうとしたものを理解させること。**
対症療法だけを渡すのは価値が低い。

## 応答の型

借用エラーに対しては、**必ずこの順で** 答える。

1. **コンパイラが防いだ実害を、具体的なシナリオで述べる。**
   「借用規則違反です」ではなく「この `Vec` が再確保されたら、さっき取った参照は解放済みメモリを指す」。
2. **選択肢を 2〜3 個、トレードオフつきで示す。**
3. **推奨を 1 つ選び、理由を述べる。**
4. コードを出す。

**`.clone()` を最初の答えにしない。** 正解であることもあるが、そのときも
「ここは所有権を共有すべきでないのでコピーする」と理由を言語化する。

## エラー別の読み解き

| コード | 起きていること | まず疑うこと |
| --- | --- | --- |
| E0382 | move 後に使用 | `Copy` でない値を渡した。参照で足りないか |
| E0499 | 可変借用が 2 つ | スコープを分ける。インデックス経由にする |
| E0502 | 可変と不変が同時 | 読みを先に済ませて値をコピーしてから書く |
| E0505 | 借用中に move | 借用のスコープを `{}` で閉じる |
| E0515 | ローカルへの参照を返した | 所有値を返すか、引数のライフタイムに紐づける |
| E0597 | 生存期間が足りない | 変数の宣言順（＝drop 順）を見直す |
| E0106 | ライフタイム指定が必要 | 出力の参照が **どの入力から来るか** を書く |

## よくある「Rust ではこう書く」

### 反復中に変更したい

```rust
// ✗ 借用が衝突する
for item in &items { if pred(item) { items.remove(...) } }

// ✓ 標準ライブラリに専用 API がある
items.retain(|item| !pred(item));
```

**教訓**: 借用エラーは「別の API があるはず」のサインであることが多い。
`retain` / `drain` / `split_at_mut` / `iter_mut` / `Vec::swap_remove` を先に探す。

### HashMap の「あれば更新、なければ挿入」

```rust
// ✗ 2 回ハッシュを引く上、借用が重なりやすい
if map.contains_key(k) { *map.get_mut(k).unwrap() += 1 } else { map.insert(k.into(), 1); }

// ✓ entry API。crates/tally/src/core.rs がこれ
*map.entry(key).or_insert(0) += 1;
```

### 構造体の 2 フィールドを同時に可変で使いたい

```rust
// ✗ self を 2 回可変借用する
self.update(&mut self.buffer);

// ✓ フィールドを分解する。借用チェッカはフィールド単位では区別できる
let Self { state, buffer } = self;
state.update(buffer);
```

### 引数の型

```rust
// 読むだけ → 借用。String を要求すると呼び出し側にアロケーションを強いる
fn parse(input: &str)

// 所有権が必要（保存する）→ 素直に受け取る
fn store(self, key: String)

// 呼び出し側の柔軟性を上げたい → ジェネリック（ただし単相化でコードサイズが増える）
fn open(path: impl AsRef<Path>)
```

### `Cow` を使う判断

`crates/tally/src/core.rs` の `Key::extract` が実例。
**「大半のケースでは借用のまま返せるが、一部で所有が必要」なときだけ使う。**
常に所有が必要なら `String`、常に借用で足りるなら `&str`。
迷ったら `String` から始めて、プロファイルで問題が出てから `Cow` にする。

## 共有をモデル化する

**エラーを消すために `Rc`/`Arc`/`RefCell` を出さない。** これらは所有権モデルの表明。

| 何を表すか | 型 |
| --- | --- |
| 単一所有 | `T`（既定。まずここから考える） |
| 単一スレッドで複数の所有者 | `Rc<T>` |
| 複数スレッドで複数の所有者 | `Arc<T>` |
| 共有 + 変更（単一スレッド） | `Rc<RefCell<T>>` — 借用検査が実行時になる |
| 共有 + 変更（複数スレッド） | `Arc<Mutex<T>>` |

**`RefCell` はコンパイル時チェックを実行時 panic に交換している。** 使うなら、
なぜ静的に証明できないのかを説明できること。

**グラフ・双方向リンク・親ポインタが欲しくなったら、まず設計を疑う。**
多くの場合、`Vec<Node>` + `usize` のインデックスで表すほうが速く、単純で、借用も通る
（Rust では「アリーナ + インデックス」が標準的な解）。

## ライフタイム注釈

- **`'a` は「生存期間を作る」のではなく「関係を記述する」だけ。** 名前を付けても寿命は伸びない。
- 構造体にライフタイムを持たせると、その構造体は借用元より長生きできない。
  **設計が窮屈になったら、所有する設計（`String` を持つ）に切り替える判断も正しい。**
- **自己参照構造体は書けない。** 必要になったらインデックス、`Arc`、
  あるいは `ouroboros` のようなクレート。ただし大抵は設計の見直しで消える。

## 他言語からの落とし穴

- **GC 言語の「参照を配って回る」設計は Rust では通らない。** 所有者を 1 つ決める設計に変える。
- **`clone()` は C++ のコピーコンストラクタのように暗黙には起きない。** 明示的なので、
  性能上の意思決定がコードに残る。これは利点。
- **`&mut` は「変更する」より「排他アクセス」の意味。** 変更しなくても排他性が必要なら `&mut`。
- **move は Go のような値コピーではない。** 元の変数が使用不能になる。
  `Copy` 型（整数など）だけがコピーで済む。

## 応答してはいけないこと

- `.clone()` だけを提示して終わる
- `unsafe` や `static mut` を回避策として出す（このリポジトリでは `unsafe` は `deny`）
- 「ライフタイムを `'static` にすれば通ります」（ほぼ常に設計の誤り）
- 借用チェッカを「Rust の面倒なところ」として扱う
