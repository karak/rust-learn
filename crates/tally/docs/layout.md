# tally のコード配置

**このクレートのどこに何を置くか、なぜそこなのか** の正本。
コードを足す・動かす前にここを読む。

学習の進み方はリポジトリ直下の `docs/curriculum.md`、
いまどこまで進んだかは `docs/handoff.md` を見ること。ここには状態を書かない。

---

## ファイルの配置

| パス | 役割 | 置いてよいもの | 置いてはいけないもの |
| --- | --- | --- | --- |
| `src/core.rs` | 集計ロジック | 純粋関数、データ構造、その単体検査 | **I/O 全般**（ファイル、標準入出力、時刻、環境変数） |
| `src/error.rs` | ライブラリ境界のエラー型 | `thiserror` の enum とその補助 | `anyhow`、表示の都合だけの型 |
| `src/cli.rs` | 引数定義 | `clap` の型、引数から内部型への変換 | 集計ロジック、I/O |
| `src/main.rs` | 実行の外枠 | 引数解釈の呼び出し、I/O、終了コード、ログ初期化 | **ロジック全般。** 純粋関数にできるものは `core` へ |
| `src/lib.rs` | 公開面の宣言 | `pub mod`、再エクスポート | 実装 |
| `tests/cli.rs` | 統合テスト | 終了コード、stdout と stderr の分離、引数の実配線 | 純粋関数の入出力検査 |
| `docs/` | このクレートの構造の説明 | 配置・設計判断・その理由 | 進捗、日付つきの記録 |

**判断に迷ったら**: それは「プロセスを起動しないと確かめられないこと」か。
そうでなければ `core` に置き、ユニットテストで検査する。

## テストが 2 箇所に分かれるのは、選択ではなく制約

| 種別 | 置き場所 | 見えるもの |
| --- | --- | --- |
| ユニット | `src/**` の `#[cfg(test)] mod tests` | **非公開項目を含む全て** |
| 統合 | `tests/*.rs` | **公開 API のみ** |

`tests/` 配下の各ファイルは **独立したクレートとしてコンパイルされ**、
このライブラリを外部依存として読み込む。したがって非公開項目は見えない。

再現できる。`tests/` に次を置いてビルドすると失敗する。

```rust
#[test]
fn 非公開項目に触れるか() {
    let _ = tally::core::snippet("x");
    let _ = tally::core::SNIPPET_CHARS;
}
```

```text
error[E0603]: function `snippet` is private
error[E0603]: constant `SNIPPET_CHARS` is private
```

ユニットテストが検証している対象はほぼ全て非公開である
（`Key::extract` / `needs_lowering` / `fold_case` / `snippet` / `SNIPPET_CHARS`）。
「借用が維持されているか」「文字境界で切れているか」といった検査は
**`tests/` からは原理的に書けない。**

**テストのために `pub` を付けない。** 公開 API は semver の対象であり、
検査の都合で広げると段階 5 の `tally-core` 分離時に負債になる。
検査したい対象が非公開なら、テストを同じモジュールに置く。

### C++ / JUnit との違い

`src/` と並行する `test/` ツリーにテストを置く慣習とは逆で、
Rust は **テスト対象と同じファイル・同じモジュール内**にユニットテストを置く。
子モジュールが親の非公開項目を見られる、という可視性規則をそのまま使っている。

```rust
#[cfg(test)]
mod tests {
    use super::*;   // 親の非公開項目が全て見える
```

`#[cfg(test)]` により通常のビルドではコンパイルされず、リリースバイナリに混入しない。
`friend` 宣言や `#define private public` に相当する回避策は要らない。

### 統合テストを書いてよい条件

**プロセスを起動しないと観測できないものだけ。** プロセス起動は遅く、
同じことをユニットで書けるなら常にそちらが正しい。

- 終了コード
- stdout と stderr が混ざっていないこと
- 引数が実際に配線されていること

なお `clippy.toml` の `allow-expect-in-tests` は `#[cfg(test)]` にしか効かない。
`tests/` 配下は通常のクレートなので、ファイル先頭で明示的に `allow` する。

## 読む順序

**ロジックから読み、I/O を最後に読む。** この順で読めることが、この配置の目的でもある。

1. `src/core.rs` — 集計ロジック。I/O を持たない。テストの主戦場
2. `src/error.rs` — ライブラリ境界のエラー型
3. `src/cli.rs` — 引数定義
4. `src/main.rs` — I/O と終了コードのみ
5. `tests/cli.rs` — 統合テスト

---

## 押さえておくべき設計判断

壊さないために、変更前に理由を把握しておくもの。

| 判断 | 理由 |
| --- | --- |
| `core` は I/O を持たない | テストの大半をプロセス起動なしで回すため。ユニットが多数派になるよう保つ |
| `Key` と `Selector` を分けている | 「どこから取るか」と「どう正規化し欠損をどう扱うか」は別の関心事 |
| **`Selector` に入れてよいのは「参加する行がどうキーを産むか」だけ** | 「どの行が参加するか」（`--filter`）はパイプライン側。`Regex` は `PartialEq` を実装せず derive も壊れる |
| `select` の `match` が `_` を使わず全バリアントを列挙 | `Key` に変種が増えたとき、`strict` が黙って無視されずコンパイルエラーになる |
| エラーの文字列が `String` でなく `Box<str>` | `Result` の大きさは最大バリアントで決まり、1 行ごとに 3 段返る。**失敗しない行も払う** |
| `--strict` が clap の `requires = "field"` を持つ | `--field` 無しでは意味を持たない。実行時に黙って無視するより引数解釈で拒否する |
| `fold_case` が `Cow` を返す | 変換不要なら借用のまま返す。無条件に `to_lowercase()` を呼ぶとテストが落ちる |
| 集計結果に全順序を与えている | `HashMap` の反復順に依存すると出力が実行ごとに変わる |
| ライブラリは `thiserror`、バイナリは `anyhow` | 公開 API に `anyhow::Error` を出すと呼び出し側が種類で分岐できない |
| `main` が `ExitCode` を返す | `Result` を返すとエラーが `Debug` 表示になり読めない |
| stdout はデータ専用 | 統合テストが stdout の完全一致を検査しており、この契約を守らせている |

---

## 新しいコードをどこに置くか

上から順に問う。**最初に「はい」になったところが置き場所。**

1. **プロセスを起動しないと観測できないか** → `tests/cli.rs`
2. **引数の形の話か** → `src/cli.rs`
3. **失敗の種類を表す型か** → `src/error.rs`
4. **I/O・終了コード・ログの初期化か** → `src/main.rs`
5. それ以外 → **`src/core.rs`**（既定。純粋関数として書く）

5 に落ちなかった場合、**純粋な部分を切り出せないか**を先に検討する。
`main.rs` にロジックが溜まると、検証手段がプロセス起動しか無くなる。
