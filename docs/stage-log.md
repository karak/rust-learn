# 段階の実績記録

**各段階で実際に何を作り、何を測り、予定と何が違ったか** の記録。
`docs/curriculum.md` が「何をどう学ぶか」（予）を持ち、**この文書が「実」を持つ。**

**新しい記述を足す前に、下の除外リストを読むこと。**
この文書は `docs/curriculum.md` から分離して作られたが、
**分離の原因は「予」と「実」が同じ文書に混ざって、片方が腐っても気づけなかったこと**である。
同じことをここで繰り返さないために、境界を先に書く。

---

## 書くもの

| 種類 | 例 |
| --- | --- |
| **完了した日付** | 「段階 2 は 2026-08-16 に完了した」 |
| **実際に作ったもの**（成果物の所在） | 「`--filter` を足した。述語は `tally_reader` が受ける」 |
| **日付つきの実測値** | 「2026-08-16 に測った: 208 命令 対 333 命令」 |
| **予定と違ったこと** | 「課題は trait への切り替えだったが、結論は enum のままだった」 |
| **あとで覆った判断** | 「段階 2 で『効いた』と書いた設計が、段階 5 で再評価された」 |
| 他の文書へのポインタ | 「詳細は `learning-log.md` 節 10-1」 |

**この文書の中心は「予定と違ったこと」である。** 予定どおりだったことは
`curriculum.md` を読めば分かるので、ここに書く価値が薄い。

## 書かないもの

| 書かないもの | 正しい場所 | 理由 |
| --- | --- | --- |
| 段階の定義・課題・完了条件・読む順序 | `docs/curriculum.md` | それが「予」である |
| **いまどこにいるか・次に何をするか** | `docs/handoff.md` | **状態は 1 箇所。** かつて `progress.md` と `handoff.md` に二重に書いて破綻した |
| 進行中のチェックリストの状態 | `docs/handoff.md` | 同上。完了したものだけがここに来る |
| **技術的な学びの本体** | `docs/learning-log.md` | ここには節番号だけ書く。本文を写すと二重管理になる |
| 設計判断の過程・代替案 | `docs/adr/` | 同上。ADR 番号だけ書く |
| 進め方の反省（KPT） | `docs/journal/` | 同上。日付だけ書く |
| **テスト名・テスト件数** | `cargo t` / `cargo nextest list` | **分離前にここで実際に腐った**（下の「この文書ができた経緯」） |
| コミット SHA・ブランチ名 | `git log` | 同じ理由 |
| リポジトリの規約 | `CLAUDE.md` | — |

**「現在の状態を写したもの」は書かない。「いつ何を観測したか」は書いてよい。**
`CLAUDE.md`「『記録』と『転記』は別物」がこの区別の正本。

## この文書ができた経緯（2026-08-19）

**`docs/curriculum.md` が予実管理メモになっていた。** 混ざっていたのは 4 種類。

1. 見出しの（済）
2. 完了条件のチェック状態（`- [x]`）
3. 「実装の記録」節（段階 1〜5）
4. 「証跡」の表（**テスト名の一覧**。段階 1・2）

**4 は実際に腐っていた。** 段階 5 でクレートを分割したとき、
表に載っていたテスト名のうち 2 件が存在しなくなり
（`strict_なしなら従来どおりスキップされる`、`strict_指定が_selector_に反映される`）、
モジュール接頭辞は全件が誤りになった（`core::tests::` → `select::tests::` ほか）。
**`CLAUDE.md` の「テストが通るか・件数 → `cargo t` を実行する。文書に書かない」に
違反していた箇所であり、違反したとおりに腐った。**

**3 も腐りかけていた。** 段階 2 の「実装の記録」は
「段階 1 で `Selector` に畳んだ設計が実際に効いた」と書いていたが、
段階 5 の [ADR-0005](adr/0005-selector-public-api.md) 論点 1 は同じ判断を
**「当時の実装の都合だった」と再評価して `strict` を `Counter` へ移した。**
curriculum 側の成功譚は更新されず、**教材の中に古い結論が残った。**

**カリキュラムに実績を書くと、実績が教義として読まれる。** これが分離の理由である。

## 段階 4: イテレータとクロージャ

**完了: 2026-08-16。**

- `--filter <REGEX>` を足した。集計をイテレータアダプタの合成で書いた
- `tally_reader` は `Regex` ではなく `Fn(&str) -> bool` を受ける

**着手前に決めた仕様**（利用者への契約は
`crates/tally/docs/output-format.md` が正本。ここには理由だけ）

1. **照合対象は生の行全体。** 抽出後のキーではない。
   `tally --filter X` が `grep X | tally` と一致することを優先した。
   `--field lvl --filter error` が他のフィールドの `error` も拾うのは
   この帰結であって、不具合ではない
2. **落ちた行は `total` にも `skipped` にも数えない。**
   フィルタは集計の上流にある。この決定により
   **「`--filter` 版と `grep` 版の出力がバイト単位で一致する」ことがテストできる**
3. **行番号は落ちた行も数える。** エラーメッセージの「何行目」は
   入力ファイルの行番号でなければ、利用者が原因の行を開けない。
   **`enumerate` を `filter` より前に置く**ことでこれを保証する

**実測（2026-08-16、release ビルド、当該関数の機械語）**

| | `for` ループ版 | アダプタ合成版 |
| --- | --- | --- |
| 命令数 | 208 | 333 |
| スタックフレーム | 240 バイト | 704 バイト |

**「ゼロコスト抽象」はこの形では字義どおりには成立しなかった。**
ただし測ったのはコードサイズであって実行時間ではない。

**予定と違ったこと**

- **最初の計測は「完全一致」という逆の結果を出した。**
  シンボル抽出の欠陥で同じ関数を 2 回比べていた。
  **陽性対照（行番号を 1 ずらしただけの版を検出できるか）で発覚した**
- **`enumerate` を `filter` の後ろに置く不具合を、テストで先に観測してから直した。**
  骨格の段階でエラーが `line_no: 2`（本来 3）を返した

**学びの所在**: `docs/learning-log.md` 節 10-1〜10-4。

## 段階 5: モジュール・クレート設計

**設計: 2026-08-17。実装: 2026-08-19。**

- `crates/tally-core` を切り出した。`clap` にも `anyhow` にも依存しない
- [ADR-0004](adr/0004-error-type-shape.md) と
  [ADR-0005](adr/0005-selector-public-api.md) を `accepted` にした
- 公開 API 全てに doc コメントと動くサンプルを付けた
- **`anyhow` を `tally` からも落とした**（`CLAUDE.md` の方針 3 を書き換えた）
- ワークスペースの lint に `missing_docs` を足した
- CI に rustdoc の警告検査を足した

**実測**

- **エラー型の大きさは [ADR-0004](adr/0004-error-type-shape.md) 論点 7 が正本。**
  要点だけ: `TallyError` は 48 バイトのまま変わらず、
  **最内段の戻り値だけ 48 → 32 に縮んだ**
- **2026-08-19 に測った変化**（現在の件数ではなく、この日の差分として記録する）

  | 項目 | 変更前 | 変更後 |
  | --- | --- | --- |
  | ワークスペースのメンバ | 1 | 2 |
  | `tally` の直接依存 | 8 | 7（`anyhow` と `serde` が抜け、`tally-core` が入った） |
  | 統合テスト | 17 件 | 15 件 |
  | ユニットテスト | 42 件 | 85 件 |
  | doc テスト | 0 件 | 13 件 |

  **統合テストを 2 件減らし、ユニットテストを 43 件増やした。**
  減らしたのは「純粋なロジックをプロセス起動で確かめていたもの」で、
  ADR-0004 論点 5 の「統合テストは配線の確認だけに減らす」を実行した結果。

**予定と違ったこと**

- **着手前に全論点を決めておいたので、実装中に設計へ戻った回数は 0 だった。**
  一方で **ADR が形を指定していなかった項目で判断が 5 件発生した。**
  うち 3 件は ADR 自身が「実装時に決める」と予告していたが、
  **2 件は予告が無かった**（モジュールを公開するか / `tally_reader` の引数の形）。
  **「決定済み」は「実装が一意に決まる」ではない**
- **段階 3 で未消化だった 3 概念の回収は、概ね失敗した。**

  | 概念 | 結果 |
  | --- | --- |
  | 孤児ルール | **説明としてのみ。** ADR-0005 論点 4 の決め手に使ったが、コードでは使っていない |
  | `From` / `Into` | **使った。** 同じ `?` が 2 つの異なる `From` を経由して 1 つの型に合流する |
  | `AsRef` / `Deref` | **使わなかった。** `Box<str>` の `Deref` に暗黙に乗っているだけ |
  | 関連型 vs 型パラメータ | **使わなかった。** trait を定義していないため出番が無い |

  **`AsRef` と関連型は trait を自分で定義するまで出番が来ない。**
  段階 6 でも来ない見込みなので、**必要になる課題を用意しないと消化されない**
- **`cargo lint` が通っても rustdoc が落ちた。** 公開項目の doc から
  非公開項目への intra-doc link があり、外部の読み手が辿れない状態だった。
  検査自体が無かったので CI に足した
- **CI の設定が 48 コミットのあいだ実態と食い違っていた。**
  `pull_request` トリガが一度も発火しておらず、
  トピックブランチに push しても CI が回らなかった。
  ブランチ運用を [ADR-0006](adr/0006-branching-strategy.md) として決めた
- **feature flag は使わなかった。** 段階 5 の「扱う概念」に入っていたが、
  `serde_json` は入力の解釈に必須で `tally-core` の硬い依存であり、
  **gate する対象が無かった。** 投機で足さない（ADR-0002 の方針に従う）

**学びの所在**: `docs/learning-log.md` 節 6-7〜6-9・節 11（モジュールとクレートの分割）。
進め方の反省は `docs/journal/2026-08-19.md`。
