## Problem

### 引用の出典を確かめずに引き写した

**既存の文書は検証済みではない。** まして自分が書いたものは。

`ADR-0002` の記述を信頼して `ADR-0004` に持ち込み、**「違反」という強い語で
2 度使った。** 鉤括弧で括った時点で「原文どおり」を主張しているのに、
原文を見ていない。

**機構**: **鉤括弧で他の文書を引用したら、その場で出典を `grep` する。**
`git ls-files '*.md' | xargs grep -n "引用文"` で 1 コマンド。
節を移動したときに参照を直す手順（`CLAUDE.md`）と同じ道具が使える。

### 却下案を不利に書いた — これは 2 回目

段階 3 の振り返りに、こう書いてある。

> **自分が推す案の利点は疑ったが、退ける案の欠点を疑わなかった。**
> 中立を意図して書き直したときですら、**攻撃の方向だけが検証を免れていた**

今回は「攻撃」ではなく **「却下案のスケッチを不完全に書く」** 形で出た。
バリアントを 2 つ落としただけで、比較表の 1 行目が成立しなくなっていた。

**同じ学びを 2 回書いた。** 段階 2 の振り返りの Try 7 に従えば、
**3 回目を待たずに機構へ変換する**べき対象。

**機構**: **比較表を書いたら、却下案の側の記述を採用案と同じ精度で書き直してみる。**
具体的には「却下案のコード片に、採用案にあるものが全部あるか」を数える。
今回は `OpenInput` と `Read` の 2 つが欠けていた。

### 決定を書き足す編集は、文書の構造を壊す

「未決定を並べる」形式で書いた文書に決定を足していくと、
**導入 → 決定 → 選択肢** の順序が崩れる。ADR-0002 で
「履歴依存を排してフラットに」と学んだのに、**別の形で同じことが起きた。**

**機構**: **決定を書き足したら、その節を頭から読み直す。** 差分だけ見ない。
`Edit` は差分しか見せないので、意図的に `Read` で節全体を読む。

  あわせて `cargo.allTargets` を `true` にしてある（テストとベンチも解析対象になる）

  プロジェクトの `.claude/settings.json` の `enabledPlugins` に明示した
- **`main` への push が、2 つのワークツリーの間で 2 回衝突した**

### 報告のまま載せるもの（本ワークツリーでは追試していない）

- **プラグインの反映にはセッションの再起動が要る。**
  同一セッション内では `LSP` ツールで `.rs` を検証できないことを、
  作業したセッション側が確認したとのこと。**こちらでは追試していない**

### push の衝突は双方向に起きた

これが今回いちばん記録に値する。

1. 別ワークツリー側が push しようとして **non-fast-forward で reject された。**
   本ワークツリー側が並行して `main` を進めていたため
2. 別ワークツリー側が `git fetch` → `rebase` → push で解消した
3. **その直後、今度は本ワークツリー側の push が同じ理由で reject された。**
   相手の push が着地したため
4. 本ワークツリー側も fetch → rebase → push で解消した

**同じ失敗が数分のうちに向きを変えて 2 回起きている。**
複数のワークツリーが同じ `main` を並行して進める運用では、
**「fast-forward できるはず」というローカルの前提が数分で崩れる。**

### Keep

**reject されたとき、force push も reset もせず、先に触ったファイルを突き合わせた。**

```
comm -12 <(git show --name-only --format= <相手のコミット> | sort -u) \
         <(git show --name-only --format= <自分のコミット> | sort -u)
```

重複ゼロ（相手は設定ファイル、こちらは `docs/`）と分かってから rebase した。
**「衝突していない」を確かめてから統合する**のと、
「たぶん大丈夫」で統合するのは別の行為である。

2. **同一セッション内で反映を確認できない変更は「反映確認できていない」と明記する。**

### Problem

#### 基準は、立てられた文脈とセットでないと切り札になる

「いま必要か」を問う限り答えは常に「不要」で、**それは判断していない。**

**機構**: **DoD には「何を満たせば完了か」だけを書く。**

**分割の構造そのものが検証可能な主張である**のに、構造だから正しいと思っていた。

  新バリアントとして来るはず」
- **調べた結果**: `serde_json::Value::pointer` は**先頭の `/` を要求する**
  （実装が `if !pointer.starts_with('/') { return None; }`）。
  したがって `JsonField("lvl")` と `JsonPointer("/lvl")` は意味が違い、互換に畳めない
- **推測は当たっていた。しかし根拠は推測ではなかった。** 決め手を差し替えた

#### 3. 文書内の相互参照を、確かめずに書いた

- **書いたこと**: `learning-log.md` に「節 7-3 の `Regex` と同型」
- **実際**: 節 7-3 は `regex` クレートの**線形時間保証**の話で、`PartialEq` に触れていない。
  正しい出典は `crates/tally/docs/layout.md:87`
- **本日の Problem 1（引用の出典を確かめずに引き写した）と同型**

#### 4. 「未確認」と明記した推測が、その場の判断材料に使われた

- **論点 3 に書いたこと**: 「JSONPath を採ると `Key` の `PartialEq, Eq` derive が
  壊れる可能性が高い。解析済み型の derive は**未確認**。論点 4 で確かめる」
- **論点 4 で確かめた結果**:

  | 型 | `PartialEq` | `Eq` |
  | --- | --- | --- |
  | `regex::Regex` | ✗ | ✗ |
  | `jsonpath_rust::parser::model::JpQuery` | **✓** | ✗ |
  | `serde_json_path::JsonPath` | **✓** | **✓** |

  **`PartialEq` は壊れない。** 壊れうるのは `Eq` だけ、しかも 2 クレートのうち片方だけ
- **結論は変わらなかった**（JSONPath を別 ADR に送る理由は、
  戻り値が 0..n になって集計モデルが変わることで独立に立つ）。
  **しかし変わらなかったのは、もう 1 つの理由が強かったからにすぎない**

#### 5. 推す案の根拠を、対立案に答えない形で書きかけた

- **書きかけたこと**: 4a の決め手を「Rust API ガイドライン C-COMMON-TRAITS に沿うから」
- **問題**: 対立案 4b は「**必要になるまで surface を広げない**」に立っている。
  これは `core.rs:121` の doc に明記され、論点 2 でゲッタを置かない根拠にも使った、
  **このリポジトリが自分で持っている方針**である。ガイドラインを引くだけでは答えていない
- **書き直した後**: その方針が効くのは**下流が自分で埋められる場合**だけ。
  関数ならラッパを書けるが、**トレイト実装は孤児ルールにより下流が絶対に書けない**。
  **2 つの方針は衝突しておらず、適用条件が違うだけだった**

#### 6. 出典が無いことを、確かめて明記した

- Cargo Book の semver の章の**全節を列挙**し、
  **トレイト実装の追加・削除を扱う節が無い**ことを確認した
- ADR に「MAJOR として扱うが、**根拠は Cargo Book ではない**」と書いた

#### 7. 指示が両読みできたので、書く前に聞いた

- **ユーザーの指示**（原文）: 「Eqはたすが上策で良い」
- 「いま外して、要求が出たら足すのが上策（4b）」とも
  「保つ = すでに足してある（4a）」とも読めた。**採る案でコードの中身が変わる差**
- 聞いた。答えは 4a

### Problem

#### 案を書くとき、決まっていない要素を束ねた

選択肢は**独立に賛否を言える粒度**で出さないと、比較そのものが成立しない。
D2 に serde 対応を束ねたことで、「newtype にするか」と「serde に対応するか」を
**1 つの賛否として**提示していた。

**論点を直交する 2 軸に分ける作業を 3 回やった直後に、案の側で同じ混同をした。**
軸の分割は覚えていたが、**同じ検査を案に掛ける発想が無かった。**

**機構**: **案を書いたら、その案が含む決定の数を数える。2 つ以上なら分ける。**
論点に掛けている検査を、案の粒度でも掛ける。

#### 文書内の相互参照も「出典未確認の引用」である

本日の Try 1 は「**鉤括弧で他の文書を引用したら `grep` する**」だった。
**節番号での参照（「節 7-3 と同型」）はその形をしていないので素通りした。**

**機構**: **Try 1 を「他の文書」から「自分の文書の他の節」へ広げる。**
節番号を書いたら、その節を開いて主張が本当にそこにあるか見る。

#### 「未確認」は伝播を止めるが、使用は止めない

「未確認」と明記していたので、**取り違えは起きなかった。** ラベルは効いた。
しかし論点 3 は、その未確認の推測を **JSONPath を範囲外にする 2 つの理由の 1 つ**として
実際に使っていた。結論が変わらなかったのは、**もう 1 つの理由が独立に立っていたから**であって、
ラベルが働いたからではない。

**機構**: **「未確認」と書いた事実は、その場の判断材料に使わない。**
使うなら先に確かめる。確かめないなら、判断の根拠から外す。
**理由を並べるときは「これを消しても結論が立つか」を見る。**

#### ガイドラインは決め手にならない

「C-COMMON-TRAITS に沿うから」は、**対立案が立っている方針に何も答えていない。**
権威を引くのは、相手の根拠を検討しないで済ませる手口になる。

**機構**: **決め手は、対立案の根拠が「なぜ今回は当てはまらないか」で書く。**
今回の形にすると「その方針が効くのは下流が自分で埋められる場合だけである」になり、
**2 つの方針が衝突していなかったことまで見えた。**

### Keep

#### 対称性の検査が、案をまたぐ前提の不整合を捕まえた

これまでの対称性の検査は**案の内部**（却下案のコード片に要素が足りているか）を見ていた。
今回は**案をまたいだ**不整合が出た。

- D2b を却下する根拠: 「`Key` は `Deserialize` を持たないので死んだコード」
- 3c を却下する根拠: 「`Deserialize` を手書きすることになる」

**同じ前提（`Key` に `Deserialize` が無い）を、片方では「まだ無いから利益が無い」、
もう片方では「いずれ来るからコストになる」と逆向きに使っていた。**
3c の当該 Bad を取り消した（却下自体は別の根拠で変わらない）。

#### 決め手を、意味論の読みから調査結果へ置き換えた

「新バリアントで来るはず」という読みは当たっていたが、
**当たっていたことと、根拠として使えることは別である。**
`pointer` の先頭 `/` 要求という**確かめられる事実**に差し替えた。

#### 指示が両読みできたとき、推測で進めなかった

「Eqはたすが上策で良い」は、**私が直前に立てた枠組み**
（「いま決めるべきは外す候補だけ／足す候補は後回しでよい」）を使うと 4b に読め、
素直に読むと 4a に読めた。**自分の枠組みが解釈を引っぱる形**だったので、聞いた。

#### 出典が無いことを、確かめてから「無い」と書いた

Cargo Book に節が無いことを、全節の列挙で確認した。
**「たぶん無い」ではなく「列挙して無かった」と書ける状態にした。**
