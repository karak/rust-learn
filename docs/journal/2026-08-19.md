### 3. Confirmation の項目を、自分で読み違えていた

ADR-0005 の Confirmation にこう書いてあった。

> `select` から防御的な `match` が消え、`let ... else` 1 行になっている

実装後、`select` は確かに `let ... else` 1 行になった。**しかし `match` は
消えていない。`Counter::on_missing` へ移っただけ**である。`strict` が
`Counter` へ動いたのだから、それを見る `match` も一緒に動くのが当然だった。

チェックを「✅」で終えかけたが、**何をどう確かめたかを表に書こうとして
気づいた。** 「消えた」ではなく「移った」と書くべきだと分かった時点で、
Confirmation の文言のほうが不正確だったと判明した。

同じ項目にもう 1 つ読み違いがあった。

> `extract` の `match` に `_ =>` が無いままコンパイルが通る

`extract` の中には `_ =>` が **ある**。ただし `Key` に対する `match` ではなく、
`serde_json::Value` に対する `match`（`Array` / `Object` を畳んでいる）のほう。
grep で `_ =>` を数えると誤判定する。

### 4. 「通らないこと」を確かめるのに一時ファイルを使った

ADR-0005 の Confirmation に
「**`Selector { .. }` を書くとコンパイルが通らない**」があった。
`tests/` に一時ファイルを置いて `cargo check`、エラーコードを控えて削除、を 6 回。

**どのコードが何を守っているかは `learning-log.md` 節 11-6 が正本**
（E0451 / E0616 / E0004 / E0624）。ここには進め方だけを書く。

**逆向き（通るべきもの）も同じ方法で確かめた** — `TallyError` の網羅 `match` と、
`LineError.line_no` を `match` なしで取ること。こちらは
**エラーが出ないことが答え**なので、出力を見るだけでは判定できない。
「落ちなかった」を明示的に成功と読む必要があった。

**1 回目は失敗した。** 6 つを 1 ファイルにまとめたら、コンパイラが最初の
エラーで止まって 1 件しか報告されなかった。分けて回す必要があった。

#### 11. squash merge を却下する理由が、一般論ではなく repo 固有だった

**squash merge は業界の既定値**なので、却下するには理由が要る。
最初に書いた理由は「履歴の粒度が失われる」だったが、**これは弱い。**
粒度が失われることは squash の定義であって、欠点の説明になっていない。

**遡って「squash は何のためにあるのか」を書いてみた。**
トピックブランチのコミットが汚いから — `wip`、`fix typo`、
`address review comments` を `main` に入れたくないから、である。

**そこで前提が成立しないことが分かった。** このリポジトリの 48 件の
コミットメッセージはすべて意味の単位で書かれており
（「ADR-0005 の論点 4 を決定し、全論点の決定を完了する」）、**隠すべき汚れが無い。**
squash の利点は「汚れを隠せる」ことなので、汚れていなければ利点も無い。

**「既定値を採らない」判断は、既定値が何のためにあるかを言えないとできない。**

#### 12. 却下した案が劣っていなかった

マージコミット（`--no-ff`）には実質的な優位があった —
**単位の境界が履歴に残る。** `git log --first-parent` が
`docs/curriculum.md` の段階と対応する一覧になる。`--ff-only` にはこれが無い。

**それでも採らなかったのは、境界の記録が既に 2 箇所にあるから**である
（`curriculum.md` の（済）、`docs/journal/` の日付）。
`CLAUDE.md` の「同じ事実を 2 箇所に書かない」に照らして、3 箇所目を作らない。

**`--no-ff` が劣っているのではなく、この repo には要らない。**
ADR にもそう書いた。「却下 = 劣っている」と書くと、
**前提が変わったとき（たとえば貢献者が増えたとき）に再検討できなくなる。**

#### 13. `--ff-only` を選んだら、2 日前の Try が仕組みになった

`git merge --ff-only` は、`main` が進んでいると **失敗する。**
つまり `rebase` を強制する。

2026-08-17 の Try 1 は「push の前に必ず `git fetch` する」だった。
**`--ff-only` を採ると、これを守り忘れることができなくなる。**
規約を 1 つ減らして仕組みに置き換えたことになる。

**これは狙って選んだのではなく、`--ff-only` の副作用として気づいた。**

## 追記 4: 秘密情報スキャンが 4 日間 no-op だった

### 起きたこと（加工前）

#### 20. フックは居たが、パターンが 0 件だった

コミットしようとして `git: 'secrets' is not a git command` で止まった。
`.git/hooks/` に 3 本のフック（`pre-commit` / `commit-msg` /
`prepare-commit-msg`）が **2026-08-15 から**居たが、
**`git-secrets` 本体が devcontainer に入っていなかった。**

入れてから設定を見たら、**`secrets.patterns` が 0 件**だった。
つまり本体が入っていたとしても、`git secrets --scan` は
**何も検査せずに全て通していた。**

**「フックがある」は「検査されている」ではない。**

#### 21. 登録したパターンが誤検知し、原因はツールの仕様だった

高信頼のつもりで足した `BEGIN [A-Z ]*PRIVATE KEY` が、
`docs/adr/0005` の `C-STRUCT-PRIVATE:` に当たった。

素の `grep` で同じ行に同じパターンを当てても**当たらない。**
`bash -x` で git-secrets を追って分かった。

```
combined_patterns=...|xox[abprs]-[0-9A-Za-z-]{10,}|BEGIN|[A-Z|]*PRIVATE|KEY
```

**git-secrets はパターンを `|` で連結するとき、空白で単語分割する。**
`BEGIN [A-Z ]*PRIVATE KEY` が 3 つの選択肢に割れ、
**裸の `PRIVATE` が別パターンとして登録されたのと同じ状態**になっていた。

`[[:space:]]` で書き直して解決した。

**ここで学んだのは正規表現の書き方ではない。**
**「動かしてみたら通った」で終えていたら、この誤検知に気づいたとき
`--no-verify` で回避していた**だろうということ。
誤検知は規約を殺す。落ちるのが日常になれば、人は迂回を覚える。

### Keep

- **原因を推測で止めなかった。** 「grep のオプション解釈だろう」と 2 回外して、
  `bash -x` で実際の呼び出しを見るまで詰めた
- **陽性と陰性の両方を自己検査に入れた。** セットアップスクリプトが
  「偽の秘密鍵を検出できる」と「作業ツリーで誤検知しない」を毎回確かめる。
  **項目 20 の再発はこれで構造的に閉じる**

### Problem

- **セキュリティ制御が 4 日間 no-op だったことに、誰も気づかなかった**（項目 20）。
  他の 3 件（rustdoc / CI トリガ / 文書規約）と違い、
  **これは気づかないまま公開リポジトリに秘密を載せうる。**
  同じ「担保の経路が切れている」でも、**代償の大きさが違う**
- **フックを入れた 2026-08-15 の時点で、動作確認をしていない。**
  入れた記録も文書に無かった（`git-secrets` の語が repo 全体で 0 件だった）

### Try

15. **セキュリティ制御は、入れた日に「破れることを確かめる」。**
    偽の秘密を置いて止まることを見る。**止まらなければ入っていないのと同じ。**
    他の検査と違い、**空振りに気づく機会が事故のときしか来ない**
16. **ツールを入れたら、それを追跡される場所に書く。**
    今回フックは `.git/` にしか無く、**リポジトリのどこにも記述が無かった。**
    `scripts/setup-git-secrets.sh` を追跡される正本にした
17. **検査に例外を入れたら、例外が広すぎないことを確かめる。**
    許可を足したあと、**別の場所では今も検出されること**を見る。
    片方向（通ること）だけ見ると、静かに全部を許してしまう
18. **文書に秘密の「形」を再現しない。** 検出された行を引用したくなるが、

    `--scan` と `--scan-history` は出力形式が違い、同じ許可が片方にしか効かなかった。
    Try 17 の「広すぎないか」だけでなく **「狭すぎないか」** も見る

#### 22. 仕組みが最初の獲物として自分を捕まえた

セットアップスクリプトをコミットしようとしたら、**フックに止められた。**
止まったのは `scripts/setup-git-secrets.sh` の 72 行目、
**自己検査のために偽の秘密鍵ヘッダを書いている行**である。
スキャナから見れば正しい検出で、
**入れた仕組みがその日のうちに動いた証拠**でもあった。

`.gitallowed`（リポジトリ直下、**追跡される**）にファイル名で絞った許可を書いて解決。
`git config secrets.allowed` にも書けるが、**それでは追跡されない** —
項目 20 と同じ穴をもう 1 つ開けることになる。

**ここでも空白の件が出た。** `.gitallowed` の読み込みも
`for pattern in $patterns` で単語分割している。許可の正規表現にも空白を書けない。

**許可を入れたあと、広すぎないかを確かめた** — 別ファイルに同じ偽の秘密鍵を置いて、
**それは今も検出されること**を見た。許可は「この行だけ」に効いている。

#### 23. この振り返りを書いたら、また止められた

上の項目 22 に、止まった行を**そのまま引用した。** すると今度は
**journal 自身が検出された。**

`.gitallowed` に journal のぶんを足すこともできたが、**そうしなかった。**
**文書が検出を説明するのに例外が要るのはおかしい。**
引用をやめて「72 行目の、偽の秘密鍵ヘッダを書いている行」と説明に置き換えた。

**許可を増やすより、文を変えるほうを既定にする。**
許可は積み上がると誰も読まなくなり、そのうち本物を通す。

#### 24. 許可が片方のスキャンにしか効いていなかった

`git secrets --scan`（作業ツリー）は通るのに、
**`--scan-history`（履歴全体）は落ちた。**

`--scan-history` は出力に **コミット SHA を前置する。**

```
<sha>:scripts/setup-git-secrets.sh:75:...
```

許可を `^scripts/...` でアンカーしていたので、**history 側には効いていなかった。**
`^([0-9a-f]{40}:)?scripts/...` に直した。

**片方だけ確かめて「許可が効いた」と判断していた。**
項目 22 で「別ファイルでは検出されること」は確かめたのに、
**「別のスキャン方法でも意図どおりか」は確かめていない。**
検査に例外を入れたら、**例外が効く範囲を経路ごとに見る**必要がある。

### CI に入れなかった理由

`--no-verify` はフックを飛ばすので、**ローカルだけでは穴が残る。**
それでも CI には入れなかった — pin（コミット SHA と sha256）が
**Dockerfile と CI の 2 箇所**になるためである。
`CLAUDE.md` が「ツールチェーンの版が 2 箇所にある」を落とし穴として挙げているのに、
**同じ形をもう 1 つ作ることになる。**

**穴が残っていることを書いて残すほうを選んだ**（`CLAUDE.md` の「実行環境」）。
塞ぐなら pin を 1 箇所に寄せる方法とセットで考える。
