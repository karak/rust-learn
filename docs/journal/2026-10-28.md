# 2026-10-28 振り返り（KPT）

対象: `v0.1.0` の公開（[ADR-0011](../adr/0011-v0-1-0-promise.md)）と
段階 10（[ADR-0012](../adr/0012-stage-10-associated-types.md)）。
**カリキュラムの終了基準を決め、満たした日**である。

**生の記録を先に置く。** 一般化したものだけを残すと、
後から別の型が見えたときに材料が無い。

**この文書は進め方だけを持つ。** 言語の学びは `docs/learning-log.md` にある。
今回そちらへ置いたのは 4-13（関連型は定義する側に回って初めて分かる）と
4-14（unsized な型に trait を実装すると `?Sized` が要る）の 2 件。

---

## 起きたこと（加工前）

### 1. 約束の範囲を決めたら、契約文書の欠落が 3 つ出た

- **前提**: `v0.1.0` を出す前に「何を約束するか」を決めることにした。
  Confirmation に「**2 つの契約文書を読み直す**」を入れた
- **実際**: 読み直して 3 件見つかった。
  **`--strict` がどこにも書かれていなかった**（テストがあり、
  `hint` が利用者に勧めてさえいた）。標準入力を読む条件が無かった。
  stderr の扱いが未定義だった
- **効いたのは規約ではなく手順**。「契約文書に漏れを書かない」という規約は
  以前からあったが、**漏れていることに誰も気づいていなかった**

### 2. 論点の欠点が、予想と違う向きで出た

- ADR-0011 論点 1 の欠点に書いたのは
  「2 文書の記述が曖昧な箇所は、約束も曖昧になる」だった
- **実際に効いたのは曖昧さではなく欠落**。
  **「書いていないものは変えてよい」という規則は、
  書き忘れたものを自動的に約束の外へ出す**
- 読み直しを入れていなければ、`--strict` は
  **約束の外にあることを誰も意識しないまま版に入っていた**

### 3. 穴を塞ぐ作業が、新しい矛盾を 1 つ作った

- 標準入力の節に「エラーの中での呼び名は `標準入力`」と書いた
- **その 3 節あとで**「`error:` の本文は契約ではない」と書いた
- **同じコミットの中で正反対のことを約束していた**。
  指摘されて呼び名の行を落とした
- **足した行どうしの整合は、足した本人には見えにくい**

### 4. release が落ちたが、コードは無関係だった

- `aarch64-apple-darwin` のジョブが **15 分 02 秒待って cancelled**。
  `GitHub Release` は skipped
- **ステップが 1 つも走っていない**。runner が割り当たらなかった
- プレリリースのときは同じジョブが 95 秒で終わっていた
- 失敗ジョブの再実行で通った

### 5. 試作が ADR の記述の誤りを見つけた

- 段階 10 の実装前に、5 案を捨てる前提で書いて動かした
- **論点 4 の「型パラメータは呼ぶ側の型引数が増える」が誤りだった**。
  実装が 1 つのあいだは推論が通り、turbofish も要らない
- 本当の欠点は、**2 つ目の実装を足した瞬間に既存の全呼び出しが `E0283` で落ちる**こと
- **`status` が `proposed` だったので、その場で直せた**

### 6. 実装を委譲したら、ブリーフの見落としが見つかった

- 呼び出し側は `main.rs` だけだと書いて渡した
- **`benches/aggregate.rs` も古い関数を使っていた**。
  委譲先が `cargo c`（`--all-targets`）で踏んで直した
- **コメントの削除は委譲先に判断させず、報告させた**。
  2 件が報告され、私が承認を取ってから直した

### 7. Confirmation の 1 項目が、書いた時点で間違っていた

- ADR-0012 に「公開 API が変わっていない」と書いた
- **公開関数を 2 つ消す作業なので、`tally` の lib API は必ず壊れる**。
  測ると major が要る結果だった
- **約束は破っていない**（ADR-0011 が契約を 2 文書に限った）。
  間違っていたのは「何を確かめるか」のほう

### 8. 4 日前の取りこぼしが、ログから見つかった

- 別件の調査で古い transcript を読み、
  **ユーザーの依頼に `No response requested.` と返していた**のを見つけた
- 依頼は 3 週間以上、持ち越しとして引き継がれていた

---

## Keep

- **Confirmation に「読み直す」を入れること。** 1 の 3 件はこれで出た。
  **検査にできないものは、手順として書くと拾える**
- **ADR を `proposed` で出し、実装してから `accepted` にすること。**
  5 の訂正はこの順序だから成立した
- **委譲でもコメントの削除は承認制のまま運ぶこと。**
  委譲先はユーザーに尋ねられないので、報告させて親が尋ねる
- **試作を捨てる前提で書くこと。** 5 案を比べて 1 日で済んだ

## Problem

- **足した行どうしの整合を見ていない**（3）。
  文書を増やす作業に、増やした箇所の突き合わせが入っていない
- **Confirmation の項目そのものを検算していない**（7）。
  「何を確かめるか」を間違えると、Confirmation は通っても意味が無い
- **ジョブの失敗を、中身を見ずに「落ちた」と受け取りかけた**（4）
- **ユーザーの依頼を落とした**（8）。しかも気づいたのが 3 週間後

## Try

- **契約文書に行を足したら、同じ文書の他の節と突き合わせる。**
  とくに「何を約束しないか」を書いた節とは必ず照合する
- **Confirmation を書いたら、各行に「これは本当に確かめたい対象か」を 1 回問う。**
  7 は、書いた直後に問えば気づけた
- **CI の失敗は、ジョブの開始時刻と終了時刻を先に見る。**
  ステップが走っていなければ、それは待たされただけである
