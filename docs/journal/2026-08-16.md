## Problem — 最も大きかった指摘

### TDD の「red」を取り違えていた

段階 2 の着手時、テストを書いてから `cargo test` を走らせ、
**コンパイルエラーが出た状態を「red 確認」と報告した。** これは誤り。

**red と呼べるのは、テストが実行されアサーションが失敗した状態だけ。**
コンパイルが通らない状態では、そのテストが目的の挙動を本当に検出できるかが
未検証のまま残る。red を見る目的は「まだ実装していないことの確認」ではなく
**「テストが機能していることの証明」** であり、コンパイルエラーはその証明にならない。

**静的型付け言語での正しい手順:**

1. テストを書く
2. **型・API の骨格だけを足してコンパイルを通す。** 振る舞いは未実装のまま。
   スタブが偶然テストを通してしまわないよう注意する
3. 実行し、**アサーションが落ちることを確認する**
4. 落ち方が期待どおりか読む（typo ではなく機能の不在が理由か）
5. 最小限の実装で green にする

**振る舞いが複数あるならサイクルを分ける。** 段階 2 は
「エラーを返す」→「抜粋を 40 文字に切る」→「制御文字をエスケープする」の 3 サイクルに
分割した。1 サイクルで全部通そうとすると、先頭のアサーションで落ちて
後続のアサーションの red を観測できない。

## Keep — この手順が実際に効いた

### red がテストの誤りを教えた

制御文字のテストで、入力を `{"a":"\u{1b}[31m"}` としていた。
実行すると `InvalidJson` で落ち、期待した `MissingField` に到達していなかった。

**生の ESC を含む行は JSON として不正**（JSON 文字列は U+0000..=U+001F の
エスケープを要求する）ため、この経路には到達しない。つまり **テストが誤っていた。**

コンパイルエラーで満足していれば気づかなかった。
実際に走らせて失敗メッセージを読んだから分かった。
**これが「red を見る」ことの価値そのもの。**

修正後は CR（JSON の空白として妥当な制御文字）を使い、
端末でカーソルが行頭へ戻る実害に即した検査にした。

### ただし、その訂正は過剰訂正だった（コードレビューで発覚）

上の発見から私は **「脅威モデルの説明が過大だった」と結論し、記録に残した。
これが誤り。** レビューで指摘され、実測して確認した。

JSON がエスケープを要求するのは **C0 制御文字（U+0000..=U+001F）だけ**。
それ以外は生で書ける。実際に U+202E（RTL override、表示順を反転させる）と
U+007F（DEL）は合法な JSON 文字列を素通りして抜粋に到達する。

```
$ printf '{"a":"\u{202e}RTL\u{7f}"}\n' | tally --field lvl --strict
error: ... "{\"a\":\"\u{202e}RTL\u{7f}\"}"     ← {:?} が救っている
```

**エスケープは必要だった。** 私の記録は「不要な防御を入れてしまった」と
読める形になっており、**そのまま残せば読者に防御を外させる**ところだった。

構造として何を間違えたか: **否定の主張を検証しなかった。**
「ESC は通らない」は実測した。しかし
**「したがって危険な文字は通らない」は検証しないまま結論した。**
前者から後者は導けない。1 つの反例（U+202E）を試せば 5 行で崩せた。

### 段階 1 の設計判断が回収できた

`--ignore-case` のときフラグを `Key` ではなく `Selector` に畳んだ判断が、
段階 2 で **`select` の呼び出し側を 1 箇所も変えずに済む**形で効いた。
「後で増えるから今分けておく」が空手形にならなかった数少ない例。

### 「約束を書いたコメント」は検証できる — そして偽だった

`Selector` の doc に「後続のフラグ（`--filter`）を足すときに各所のシグネチャを
壊さずに済む」と書いていた。整理レビューで **これは falsifiable で、しかも偽**
だと指摘された。

- `Selector` は `PartialEq, Eq` を derive しているが、`Regex` は `PartialEq` を
  実装しない。`filter: Option<Regex>` を足すと derive が壊れる
- そもそも `--filter` は「**どの行が参加するか**」であり、
  `Selector` が答える「**参加する行がどうキーを産むか**」とは別の問い

**教訓**: コメントに「将来こうしても壊れない」と書いたら、それは検証可能な主張。
書いた時点で、壊れる条件を 1 つ探す。境界を言語化して doc に書き直した。

### 自分で書いた不便が、次の変更で自分に返ってきた

テストヘルパ `sel` / `sel_ci` / `sel_strict` が `Selector` の全フィールドを
それぞれ列挙していたため、`--strict` を足すときに **3 つ全部を編集する羽目になった。**
構造体更新構文（`..sel(key)`）にすれば `sel` だけで済む。

**教訓**: 同じ編集を 3 箇所でしたら、それは設計が要求している作業ではなく
**構造の欠陥が請求してきたコスト**。その場で直す。

### ワイルドカードの `_` は、将来の自分への沈黙

`match (self.strict, self.key.field_name())` の `_ => Ok(None)` は、
`Key` に変種が増えたとき **黙って `strict` を無視する。**
全バリアントを列挙する形に直したので、今後は変種追加でコンパイルが止まる。

**教訓**: `_` は「今は他にない」ではなく「**今後何が増えても無視する**」と書いている。
網羅性検査を捨ててよいか毎回問う。

### 設計判断の論証で 4 つの型の誤りをした（ADR の敵対的レビューで発覚）

段階 3 の設計判断を ADR に書いたところ、**中心論証が事実に反していた。**
個別の誤りより、**誤り方に型があった**ことが重要。

1. **要件と実装制約を混同し、それを支柱に据えた。**
   「ヘルプと補完を出したい」という自分の要件を、
   「ライブラリがこう要求する」という外部制約だと思い込んだ。
   **支柱にする主張ほど検証を要する。** 支柱が折れれば論証はまるごと崩れる
2. **自分が推す案の利点は疑ったが、退ける案の欠点を疑わなかった。**
   反対案への攻撃 3 点のうち 2 点が事実に反していた。
   中立を意図して書き直したときですら、**攻撃の方向だけが検証を免れていた**
3. **推進力に重みを付けなかった。** 7 つを同列に並べたため、
   実際は 1 本で結論を出しているのに多角的に見えた。
   **重みの無い評価軸の列挙は、結論をどうとでも導ける**
4. **判別力の無い基準を判定条件に据えた。**
   自分で「実行時コストはほぼゼロ」と書きながら、
   それを実測して採否を決めるとしていた。**測っても差が出ない基準は基準ではない**

**対策として置いたもの:** 推進力の表に重みの列を必須にした。
支柱になる主張は ADR に書く前に実機で確かめる。
確認方法を書いたら「この基準で案が分かれるか」を自問する。

### ADR は初見の判断者のために書く

改訂の経緯を本文に混ぜたところ、**「かつて何が誤っていたか」が
初見の読み手にとっては雑音**だと指摘された。

判断に必要なのは **いま何が事実か** だけ。
過程は書き手にとって価値があるが、それは別の文書の担当。

- **本文はフラットに。** 履歴に依存しない比較を書く
- **経緯は改訂履歴の表だけ。** 何版で何を変えたかの 1 行で足りる
- **進め方の反省は `docs/journal/`、技術的事実は `docs/learning-log.md`。**
  ADR からは参照する

2. **機能を足したら、既存の契約文書のどの記述が偽になるかを洗う。**
   今回は `output-format.md` の `total` と `--stats` の文言が偽になった。
   偶然開いて気づいたのであって、手順ではなかった
3. **一般論を規模の確認なしに適用しない。**
   「trait は操作追加に強い」は正しかったが、
   **操作の本体が 1 行という規模では、定型のコストが利点を上回った。**
   一般論は「どの規模で効くか」とセットでないと使えない
