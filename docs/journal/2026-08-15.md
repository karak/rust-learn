## Keep — 効いたので続ける

### テストを先に書いて red を確認してから実装する

段階 1 では `--ignore-case` のテストを先に書き、コンパイルが通らないこと（red）を
確認してから実装した。特に効いたのは **課題の主眼そのものをテストにしたこと**。

```rust
assert!(matches!(extracted, Cow::Borrowed(_)), "不要なアロケーションが発生している");
```

「動く実装」なら `to_lowercase()` を無条件に呼べば書けてしまう。
このテストがあるおかげで、**手を抜いた実装が構造的に通らない**。
学習課題では「正しく動くこと」より「意図した性質を持つこと」を守るほうが価値が高い。

### 前提そのものをテストで固定する

`'ǅ'` が `is_uppercase()` で `false` になる、という事実に依存した実装を書いた。
コメントに書くだけでなく `assert!(!'ǅ'.is_uppercase())` をテストに入れた。

コメントは前提が崩れても黙っている。テストなら落ちる。
**「なぜこの実装なのか」の根拠が外部仕様にある場合、その根拠自体を検査対象にする。**

### 設計の選択肢とトレードオフを先に出す

`--ignore-case` のフラグをどこに置くか（`Key` に足す / 引数を増やす / `Selector` に畳む）を
先に並べ、後続段階でフラグが増えることを理由に選んだ。
実装後に「なぜこうしたか」を思い出すより、判断が明確に残る。

### clippy pedantic を通し切る

「動いた」で止めず `-D warnings` を通すところまでやる運用は機能している。
`tests/` 配下で `allow-expect-in-tests` が効かないことなど、
通す過程でしか気づかない事実がいくつもあった。

### 環境をコンテナで固定する

devcontainer をホストと同一バージョンで作ったことで、
「手元でだけ通る」の可能性を最初から排除できている。

## Problem — うまくいかなかった

### 1. 推測を検証前に書いた（3 回発生）

| 主張 | 実際 |
| --- | --- |
| イメージ削減の主因は `chmod -R` の範囲 | 280MB。主因は `lldb` の 550MB |
| `RUSTUP_HOME` は読み取り専用で環境が固定される | 書き込み可能。公式イメージが既に開放していた |
| `Box::new` の一時オブジェクトは最適化で常に消える | インライン化されなければ `memcpy` が残る |

いずれも**もっともらしい説明**で、実際に測るまで誤りに気づかなかった。
2 番目に至っては、誤った説明を Dockerfile のコメントとして書き込んでいた。

根本原因は「説明が筋として通っているとき、検証の必要を感じにくい」こと。
筋が通っているかどうかは、正しさの証拠にならない。

### 2. 「存在確認」で満足した

`git filter-repo` の実行後、`.serena` ディレクトリが存在することだけを見て
「ローカルには健在」と報告した。実際には追跡ファイルだった `project.yml` が
作業ツリーからも削除されていた。

**ディレクトリの存在は、中のファイルの存在を意味しない。**
これは `docs/../.claude/skills/rust-testing/` に書いた
「存在確認で終わらせず内容を検証する」というテストの原則と同じ誤りを、
自分の作業確認でやったことになる。原則を書いた側が守れていなかった。

### 3. 説明の前に前提を確認していなかった

C++ template との対比（「制約を強制せずマクロ的に自由」）を強調して説明したが、
制約付きジェネリクスを持つ言語を知っていれば自明な差で、情報量がなかった。
**対比軸を選ぶ前に、何と比べれば有益かを聞くべきだった。**

### 4. 完了条件を決めずに進んでいる

カリキュラムは段階 9 まであるが、「何をもって役目を終えたとするか」が未定義のまま。
状態を棚卸しするまで、この欠落に気づいていなかった。

## Try — 次の段階で変える

### 1. サイズ・性能・権限の主張は、書く前に測る

Problem 1 の対策。特に **コメントやドキュメントに残す前**に測る。
コードのコメントは長く残り、誤りが後続の判断を歪める。

測るコストが高い場合は、**測っていないことを明示する**（「未検証」と書く）。
断定しないという選択肢を常に持つ。

### 2. 確認は 1 段階深く見る

Problem 2 の対策。ディレクトリではなくファイル、ファイルではなく内容。
「消えていないか」ではなく「あるべきものが、あるべき形であるか」を見る。

テストに課している基準を、自分の作業確認にも適用する。

### 3. 説明の対比軸は、使う前に前提を確認する

Problem 3 の対策。すでに `CLAUDE.md` に前提と軸の使い分けを明記したので、
次からは同じ取り違えは起きにくい。新しい領域（並行性、async など）に入るときは
改めて確認する。

### 4. 段階ごとに完了条件を先に決める

Problem 4 の対策。段階 2 に着手する前に、
「何ができたら段階 2 が終わりか」を `docs/curriculum.md` に書いてから始める。

段階 1 では結果的に証跡表を残せたが、これは事後に整理したもの。先に決めるほうがよい。

### 5. 段階 2 は `error.rs` の精読から始める

現在の精読範囲は `core.rs` のみ。段階 2 の課題（`--strict`）は
エラー型の設計そのものを触るため、読まずに書き始めると
既存の設計判断（`#[source]` の使い方、行番号を持たせている理由）を壊しかねない。
