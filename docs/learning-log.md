## 1. 段階 1 の設計判断（対象: `core.rs`）

課題は `--ignore-case` を **`Cow` の借用を維持したまま** 実装すること。

### 1-1. 「大文字か」ではなく「小文字化で変化するか」

最初に書きたくなるのは `s.chars().any(char::is_uppercase)` だが、**これは誤り**。

`'ǅ'`（U+01C5）は Unicode 上 **Titlecase**（一般カテゴリ Lt）であり Uppercase プロパティを持たない。
つまり `is_uppercase()` は `false` を返すが、`to_lowercase()` では `'ǆ'` に変わる。
この実装だと `ǅ` と `ǆ` が別キーとして集計される。

正しくは「小文字化したときに変化するか」を直接見る。

```rust
value.chars().any(|c| {
    let mut lowered = c.to_lowercase();
    match (lowered.next(), lowered.next()) {
        (Some(first), None) => first != c,
        _ => true,   // 複数文字に展開される = 変換が必要
    }
})
```

**この前提自体をテストで固定した**（`assert!(!'ǅ'.is_uppercase())`）。
コメントに書いただけでは、前提が崩れたときに気づけないため。

### 1-2. `to_lowercase()` は 1 文字とは限らない

`'İ'`（U+0130）の小文字化は `'i'` + 合成用ドットの **2 文字に伸びる**。
したがって `str` の in-place 変換は一般には不可能。

ただし **ASCII に限れば長さは不変**なので、所有値であれば `make_ascii_lowercase()` で
その場変換でき、`to_lowercase()` による 2 度目のアロケーションを避けられる。
結果として 3 分岐になった。

1. 変化しない → **借用のまま返す**（大半の行がここを通る）
2. ASCII のみ → 所有値ならその場で書き換え
3. それ以外 → `to_lowercase()`

### 1-3. フラグの置き場所

`Key`（どこから取るか）に `ignore_case` を足すと、抽出と正規化という別の関心事が混ざる。
`Selector { key, ignore_case }` に畳んだ。段階 2 の `--strict`、段階 4 の `--filter` で
フラグが増えることが確定しているため、シグネチャを壊さない構造を選んだ。

### 1-4. テストで学習目標そのものを守る

`小文字化で変化しない値は借用のまま返る` は `Cow::Borrowed` であることを直接 assert する。
**`to_lowercase()` を無条件に呼ぶ実装にすると落ちる**ので、課題の主眼がテストで守られている。

「動くこと」ではなく「意図した性質を持つこと」をテストする例。

## 2. 借用と参照（ファイル非依存）

C++ の参照・ポインタとの対比で整理した。

### 2-1. `&T` は `const T&` ではない

C++ の `const` は **自分のアクセス権限** の話にすぎない。
`const std::vector<int>&` を受け取っても、別のエイリアスやコールバックから
書き換えられる可能性は残る。

Rust の `&T` は **プログラム全体に対する保証**。その参照が生きている間、
誰も（元の所有者すら）書き込めない。だから `&T` を持っているだけで
「この値は変わらない」と仮定してコードを書ける。

例外は `UnsafeCell`（`Cell` / `RefCell` / `Mutex` の中身）のみで、
これが C++ の `mutable` に相当する唯一の脱出口。**例外の所在が型に現れる**のが要点。

### 2-2. `&mut T` は `T&` ではなく `T& __restrict`

`&mut` の本質は「可変」ではなく **排他**。
C++ の `__restrict` は無検査の約束（破れば UB）だが、Rust は借用チェッカが検証済みなので、
rustc は `noalias` を付けて LLVM に渡せる。

**借用規則は安全性の制約であると同時に、最適化のための情報**でもある。
C++ コンパイラが「同じ場所を指すかもしれない」と保守的に諦める場面で、Rust は諦めなくてよい。

### 2-3. イテレータ無効化がコンパイルエラーになる

```rust
let first = &v[0];
v.push_back(4);      // error[E0502]
```

C++ で最も有名な UB の入口が、型で塞がれている。
借用チェッカは「厳しい制約」ではなく、**C++ でレビュー時に見ていた観点をコンパイラに移管したもの**。

### 2-4. 参照のサイズ（実測、aarch64 / rustc 1.97.1）

```
usize = 8     &u8 = 8      Option<&u8> = 8
&str = 16     &[u8] = 16   &dyn T = 16
String = 24   Cow<str> = 24
```

- **借用にランタイムコストはない。** 借用チェックはコンパイル時に完結し、実行時に痕跡が残らない
- `&str` / `&[T]` / `&dyn T` は fat pointer（16 バイト）。「参照は 8 バイト」と思い込むとサイズ見積もりを外す
- **`Option<&u8>` が 8 バイト。** 参照は非 null が型で保証されるため null で `None` を表現できる
- **`Cow<str>` が `String` と同じ 24 バイト。** 借用/所有を切り替える enum なのに追加領域がない

### 2-5. vtable の位置が C++ と違う

C++ は多相オブジェクト自身が vptr を持つ。Rust は **参照側**が持つ（`&dyn Trait` が fat pointer）。

- トレイトを実装しても**型のサイズは変わらない**
- 静的ディスパッチだけで使う限り**コストが完全にゼロ**
- 1 つの具象型に対し独立した trait object を何個でも作れる（多重継承の複雑さがない）
- 逆に `dyn Trait` は値として持てず、`Box<dyn Trait>` が要る

### 2-6. ライフタイム注釈の正体

`std::string_view` を返す関数の「戻り値は引数を指す」という契約を、機械検査可能にしたもの。

```cpp
std::string_view trim(const std::string& s);   // 契約はコメントか命名規約でしか表せない
```
```rust
fn trim<'a>(s: &'a str) -> &'a str             // 同じ契約。コンパイラが守る
```

`'a` は寿命を作るのではなく、**既にあった契約を書き下しているだけ**。

## 3. move と in-place 構築（ファイル非依存）

### 3-1. C++ の move とは別物

| | C++ | Rust |
| --- | --- | --- |
| moved-from | 有効だが未規定の状態。使える | **存在しない**。コンパイル時に使用不能 |
| デストラクタ | moved-from にも走る | 走らない |
| move コンストラクタ | ユーザー定義可能 | **存在しない**。常にビットのコピー |
| relocatable | 型による | **常に trivially relocatable** |

`Vec` の再確保は `memcpy` で済む（C++ の `std::vector` は要素ごとに move ctor を呼ぶ）。

### 3-2. move ctor が無いことのデメリット（実測で確認）

「余分なコピーが発生しないか」を検証した。64 KiB の構造体を
`Box::new(Big::new())` でヒープに置くコードの release ビルド生成結果。

**A. ファクトリがインライン化されない場合**
```asm
sub  x9, sp, #16, lsl #12    ; 64 KiB のスタックフレームを確保
bl   new_noinline            ; スタック上に構築
bl   __rust_alloc
bl   _memcpy                 ; 64 KiB をスタック → ヒープへコピー
```

**B. インライン化された場合**
```asm
bl   __rust_alloc_zeroed     ; 直接確保。memcpy なし
```

命令数 27 対 12。**A では一時オブジェクトと `memcpy` が実際に残る。最適化しても。**

**構造的な理由**: C++ のコンストラクタは「与えられたアドレスに対して」実行されるため、
`make_unique<Big>()` は一時オブジェクトを原理的に作らない（インライン化に依存しない）。
Rust は値を返してから移動先を決めるので、両者を一致させられるかは最適化器次第。

**Rust には保証された in-place 構築（placement new）が無い。** ここは C++ の優位。
A は「別クレートのファクトリを LTO なしで呼ぶ」「関数が大きい」「動的ディスパッチ」で現実に起きる。
デバッグビルドでは常に A になる。

回避策は `Box::new_uninit()`（安定化済み）。実測では A のような memcpy を生じなかった。

### 3-3. 逆にコンテナは Rust が有利

- `std::sort` は要素移動ごとに move ctor/代入を**呼ぶ**。Rust はビットのコピーのみ
- C++ の `std::vector` は **move ctor が `noexcept` でないと再確保時にコピーする**
  （強い例外保証のため）。`noexcept` 忘れが全要素のディープコピーに化ける罠がある。
  Rust にはこの罠自体が存在しない

### 3-4. まとめ

| 場面 | 有利 | 理由 |
| --- | --- | --- |
| ファクトリ + ヒープ確保 | C++ | placement new による保証された in-place 構築 |
| デバッグビルドの大きな値 | C++ | Rust は memcpy が残る |
| コンテナのソート・要素移動 | Rust | ビットコピーのみ。ユーザーコードを呼ばない |
| `vector` の再確保 | Rust | `noexcept` 忘れの罠がない |
| 自己参照・intrusive 構造 | C++ | Rust は原理的に不可、`Pin` で回避 |
| 「moved-from の使用」バグ | Rust | 状態自体が存在しない |

**trivially relocatable を全型に強制する代わりに、in-place 構築と自己参照を諦めた**
というトレードオフ。一方的な優劣ではない。

## 4. ジェネリクスと trait（ファイル非依存）

C#/Java のジェネリクス、Scala の trait との差分で整理する。

### 4-1. 単相化 vs 型消去

Java の erasure と逆で、Rust は `T` ごとに実体を生成する。帰結:

- **実行時に型情報が残らない。** リフレクションによる汎用シリアライザは書けない
  （だから serde は derive マクロでコンパイル時に生成する）
- コンパイル時間とバイナリサイズが型の数だけ増える

### 4-2. trait は状態を持てない

Scala の trait と違いフィールドを宣言できず、継承もない。
デフォルトメソッドまでは同じだが、状態は合成（フィールドとして保持し委譲）で表現する。
線形化やダイヤモンド継承の問題が原理的に起きない代わりに、mixin 的な再利用はできない。

### 4-3. 外部の型に自分の trait を実装できる

C#/Java では不可能（拡張メソッドは静的解決なので代替にならない）。
孤児ルールの範囲内、つまり「trait か型のどちらかが自分のクレートのもの」なら実装できる。

位置づけは Scala の型クラス（`implicit` / `given`）に近いが、決定的な差は
**コヒーレンスが大域的に保証される**こと。「ある型と trait の組に対する実装は
全プログラムで高々 1 つ」がコンパイラに強制される。Scala の implicit 探索順のような
問題が起きない代わりに、孤児ルールの窮屈さを負う。

### 4-4. 動的ディスパッチが opt-in

C#/Java はインターフェース経由が既定で仮想。Rust は `dyn` と書いたときだけ。
**書かなければコストがゼロ**なので、「抽象化したら遅くなる」という前提が成り立たない。

### 4-5. 無いもの

- **高階型（HKT）**: `F[_]` を抽象化できない。`Functor` / `Monad` を素直に書けない。GAT が部分的に代替
- **変性注釈**: Scala の `+T`/`-T`、C# の `in`/`out` に相当するものがなく構造から推論される。
  書けないぶん、詰まったときに理由が見えにくい
- 特殊化、SFINAE、可変長ジェネリクス（安定版には無い）

### 4-6. 関連型 vs 型パラメータ

Scala の抽象型メンバと型パラメータの使い分けと同じ判断軸。
**実装ごとに一意に決まるなら関連型**（`Iterator::Item`）、
**呼び出し側が選ぶなら型パラメータ**（`From<T>`）。

### 4-7. `dyn` のコストは思い込みで語れない（実測）

trait object を避ける理由としてよく挙がる 2 つを測ったところ、**どちらも誤り**だった。

**`Box::new(ZST)` はアロケーションしない。**
グローバルアロケータを差し替えて数えると呼び出し回数は **0**。
`size_of::<Zst>() == 0` なので確保すべきものが無く、`Box` は
ダングリングでない適当なアドレスを持つだけ。
**「状態を持たない型を `Box` に入れるのは無駄」という直感は成り立たない。**

**enum から `Box<dyn Trait>` を作る対応表は、網羅性検査を失わない。**

```rust
fn formatter(f: Format) -> Box<dyn Formatter> {
    match f {
        Format::Text => Box::new(Text),
        Format::Json => Box::new(Json),
        // Csv を書き忘れると error[E0603] ではなく E0004
    }
}
```

`error[E0004]: non-exhaustive patterns` になる。
**「trait にすると登録漏れが実行時バグになる」は、
文字列キーのレジストリにした場合の話であって、`match` で書けば起きない。**

残る `dyn` の実コストは **vtable の間接参照 1 回**と
**オブジェクト安全性の制約**（ジェネリックメソッドを持てない）だけ。
避けるかどうかは、この 2 つに見合うかで判断する。

> **この「間接参照 1 回」は過小評価だった。** 段階 3 で機械語を読んで数え直した
> 結果は 4-8 にある。

### 4-8. `Box<dyn>` のコストを機械語で数える（段階 3 で実測）

4-7 で「実コストは vtable の間接参照 1 回」と書いたが、**実際に出た命令を数えると
それより多い。** `cargo rustc --release -- --emit=asm` で aarch64 の出力を読んだ
（LTO なし、`Box<dyn Formatter>` を enum の判別子から作って 1 回呼ぶ経路）。

```asm
adrp x10, l_switch.table…        ; 判別子で引く表。中身は vtable のアドレス
ldr  x19, [x10, x9, lsl #3]      ; x19 = 選ばれた vtable
ldr  x9,  [x19, #24]             ; +24 = write メソッドの枠
blr  x9                          ; ← 間接呼び出し（1）
ldr  x8,  [x19]                  ; +0  = drop_in_place の枠
cbz  x8,  LBB95_3                ; null なら飛ばす
blr  x8                          ; ← 間接呼び出し（2）: Box の後始末
LBB95_3:
ldr  x1,  [x19, #8]              ; +8  = 型のサイズ
cbz  x1,  LBB95_5                ; ← サイズ 0 なら解放を呼ばない
… __rust_dealloc
```

読み取れること。

- **`match` は消えず、vtable の表引きになる。** LLVM は devirtualize しなかった。
  分岐 3 本を「表を引いて間接呼び出し」に畳んだ形で、判別子から具体型への対応は残る
- **間接呼び出しは 1 回ではなく最大 2 回。** メソッド本体と、`Box` の drop glue。
  `Box<dyn T>` を返す設計は、呼び出しだけでなく**後始末も vtable 経由**になる
- **ZST でも「確保しない」を静的には消せない。**
  4-7 の「`Box::new(ZST)` はアロケーションしない」は正しいが、
  `dyn` の裏では**どの型が来るかコンパイル時に決まらない**ため、
  サイズを vtable から読んで実行時に 0 と比べる分岐が残る。
  静的 dispatch なら分岐ごと消える

**C++ の仮想関数との差はここには無い。** vtable 経由という点は同じで、
drop glue が vtable に載るのは「デストラクタも仮想」という状況に対応する。
差が出るのは *opt-in* であること、つまり `dyn` と書かなければこれが一切出ないこと。

### 4-9. 「trait は操作の追加に強い」は規模の関数

expression problem の一般則（enum は変種の追加が楽、trait は操作の追加が楽）は
**正しいが、それだけでは設計を決められない。**

trait 側は **(型 × 操作) ごとに `impl` ブロックとメソッド署名という定型を払う。**
enum + `match` 側は腕 1 本で済む。したがって
**操作の本体が定型より短いあいだは、一般則と逆の結果になる。**

`tally` の出力形式で 3 案を実装して測ったところ、実際に逆になった。
数値と判断は [ADR-0002](adr/0002-output-format-abstraction.md) が正本。

**一般則を使うときは「どの規模から効くか」を添える。**
規模を確かめずに適用すると、定型のコストが見えない。

### 4-10. 孤児ルールは自由であると同時に、上流への義務でもある（2026-08-17）

4-3 は孤児ルールを**自由**の側から見た。
**制約の側から見ると、公開 API の設計則が 1 つ出てくる。**

下流が `Eq for Key` を必要としたとする。`Eq` は std のもの、`Key` は上流クレートのもの。
**どちらも自分のものではないので、下流は実装を書けない。**
newtype で包めば書けるが、その瞬間に元の型の固有メソッドが全部消える
（`Deref` で一部は救えるが、**trait 境界は救えない** —
`fn f<T: Eq>(x: T)` に newtype を渡すには newtype 側に `Eq` が要る）。

**後付けできるか**という軸で並べると、Rust の立ち位置が 4-3 とずれる。

| | 下流が「他人の型 × 他人の trait」を後付けできるか |
| --- | --- |
| C#/Java | **できない。** インターフェースは型定義時に宣言する。拡張メソッドは静的解決なので `where T : IComparable` を満たさない |
| Scala | **できる。** `given Eq[Key]` をローカルスコープに置ける。コヒーレンスが大域でないぶん自由 |
| Rust | **できない。** 孤児ルール |

**Rust の trait は書き味では Scala の型クラスに近いが、後付け可能性では C#/Java 側に立つ。**
大域コヒーレンスを保証した代償である。

**この非対称が、Rust API ガイドライン C-COMMON-TRAITS
「共通トレイトは積極的に実装せよ」の根拠である。** 作法ではなく構造的要請。
関数なら下流がラッパを書けるので「必要になるまで公開しない」でよいが、
**トレイト実装には下流側の代替手段が無い。**

#### 派生する一般則: derive には向きがある

**足すのは MINOR、外すのは MAJOR。**
（**Cargo Book の semver の章にはトレイト実装の追加・削除を扱う節が無い。**
全節を列挙して確認した。下流が壊れるのは自明なので MAJOR として扱うが、
`enum-variant-new` のようには出典を引けない。）

したがって **公開 API の設計で「切り出す前に決めなければならない」のは、
後から外せないものだけ**である。足せるものは後回しでよい。

もう 1 点、`#[derive]` と手書き実装は保証が違う。
**derive はフィールドを足したとき自動で追随するが、手書きは追随せず、
比較漏れがコンパイルを通る。** derive を保てる範囲に型を保つことには、この価値がある。

判断の記録は [ADR-0005](adr/0005-selector-public-api.md) の論点 4。

## 5. serde（対象: `core.rs` / `main.rs`）

### 5-1. 位置づけ

**標準ライブラリではない。** Rust の `std` にシリアライズ機能はなく、これは意図的。
`std` は後方互換を永続的に保証するため、進化の速い領域を取り込まない。
結果として「実質的な標準ライブラリ」の一部が crates.io 側にある。

C# の `System.Text.Json` や Java の Jackson とは**層が 1 つ違う**。
あれらは「JSON のライブラリ」だが、serde は「フォーマット非依存の抽象層」。

### 5-2. N×M を N+M に落とす装置

serde 本体が提供するのは 2 つのトレイトと、その間のデータモデル（**29 種類の型**）だけ。

- **型の側**が `Serialize` を実装し、自分をデータモデルへ写す
- **フォーマットの側**（`serde_json` など）が `Serializer` を実装し、データモデルを表現へ写す

両者は互いを知らない。型 N × フォーマット M の組み合わせを N+M の実装で済ませる。

### 5-3. リフレクションが無いから derive マクロ

Jackson も `System.Text.Json` も実行時リフレクションで動く。Rust にはそれがない（4-1 参照）。
serde はコンパイル時にコードを生成する。

- **利点**: 実行時のフィールド探索・ボクシングがなく、直書きコード同等の速度
- **代償**: コンパイル時間。`syn` / `quote` / `proc-macro2` のチェーンを引く

依存グラフにその対処が現れている（実測）:

```
serde
├── serde_core     ← "Serde traits only, with no support for derive"
└── serde_derive (proc-macro) → proc-macro2, quote, ...
```

derive を使わないクレートが proc-macro のビルドを回避できるようにする分割。

### 5-4. ゼロコピーは段階 1 の `Cow` と同じ判断

```rust
#[serde(borrow)]
note: Cow<'a, str>,     // エスケープがある時だけ所有に落ちる
```

JSON のエスケープ（`\n` 等）がある行だけ新しい文字列が要る、という構造。
`fold_case` で書いたのと同じ判断が serde の設計にも埋め込まれている。

### 5-5. 限界

1. **コンパイル時間**が中規模以降の主犯になりやすい
2. **実行時スキーマが無い。** 型を事前に書けないデータは `serde_json::Value` に落ちる
3. **29 型のモデルに収まらないフォーマットは苦手。** XML の属性/要素、YAML のアンカーは写像に無理が出る
4. **`untagged` / 内部タグ付き enum はバッファリングを要求する。**
   自己記述的でない形式（`bincode` 等）では動かない。JSON では使えるが bincode では使えない属性がある
5. **スキーマ進化・バージョニングは範囲外。** protobuf のようなフィールド番号や互換性規則はない

代替: スキーマ先行なら `prost`、デシリアライズをゼロにしたいなら `rkyv`、
コンパイル時間重視なら `miniserde` / `nanoserde`、表現力の補強に `serde_with`。

### 5-6. ネスト参照は二段あり、片方は標準で入っている（2026-08-17 に調査）

「JSON の中の値を、もっと深いところから取りたい」に対する手段は**二段ある**。
**段が違うと必要な依存も、呼び出し側の設計インパクトも別物になる。**

#### 段 1: JSON Pointer（RFC 6901）— `serde_json` に入っている

```rust
pub fn pointer(&self, pointer: &str) -> Option<&Value>
```
```rust
let data = json!({ "x": { "y": ["z", "zz"] } });
assert_eq!(data.pointer("/x/y/1").unwrap(), &json!("zz"));
assert_eq!(data.pointer("/a/b/c"), None);
```

**新しい依存が要らない。** ネストと配列添字はこれで足りる。

**ただし落とし穴が 2 つある。**

1. **エスケープ。** トークン内の `/` は `~1`、`~` は `~0` に書き換える
2. **不正な式がエラーにならない。** 先頭が `/` でなければ実装は無条件に `None` を返す。
   **綴り間違いが「そのフィールドを持たない行」と区別できない。**
   `Option` は「無かった」しか表せないので、**式の妥当性は構築時に検査するしかない**

2 番目は Rust 固有ではなく API 設計の一般則だが、
**`Option` を返す関数は「引数が不正」を表現できない**という形で現れるのが特徴的。

#### 段 2: JSONPath — 外部クレートで、戻り値の個数が変わる

| | jsonpath-rust 1.0.8 | serde_json_path 0.7.2 |
| --- | --- | --- |
| 直接依存 | `pest` `pest_derive` `regex` `serde_json` `thiserror` | `nom` `inventory` `serde` `serde_json` + 自前 2 + `thiserror` |
| 最終更新 | 2026-08-01 | 2025-02-03 |
| 準拠 | 独自（XPath 由来） | RFC 9535 準拠を掲げる |

**設計上の要点はクレート選定ではない。「1 回の問い合わせが何個返すか」である。**

JSONPath は `$.shop.orders[?(@.active)].id` に対して `[1,4]` を返す。
**0..1 だった抽出が 0..n になる。**
`Option<T>` を返していた関数が `Vec<T>` を返すようになるので、
**呼び出し側の「1 行 = 1 件」という前提が崩れる。**
集計の合計、スキップ数、出力形式の契約まで波及する。

**「機能を足す」ではなく「濃度（arity）が変わる」と捉えると、
影響範囲の見積もりを間違えにくい。**

もう 1 つ、**型に効く副作用がある。** 行ごとに式をパースするのは非現実的なので、
コンパイル済みクエリを設定の型が保持することになる。
**すると `PartialEq` / `Eq` の derive が壊れる可能性が高い**
（`crates/tally/docs/layout.md` に記録済みの
「`Regex` は `PartialEq` を実装せず derive も壊れる」と同型）。
**「重い前処理を型に持たせると derive が失われる」は、Rust で繰り返し出る形。**

## 6. エラー設計（対象: `error.rs` / `main.rs`）

- **ライブラリ層は `thiserror` で具体的な enum、バイナリ層は `anyhow`。**
  公開 API に `anyhow::Error` を出すと、呼び出し側が「ファイルが無い」と
  「JSON が壊れている」を区別できなくなる
- エラーメッセージには **修正に必要な情報**（行番号・パス・フィールド名）を含める
- `#[error(...)]` に原因を埋め込まない。`#[source]` に任せる。二重表示になるため
- **`fn main() -> Result<...>` を使わない。** エラーが `Debug` 表示になり、
  ユーザーに読めない出力になる。`ExitCode` を返して自分で整形する
- `anyhow` の `{:#}` は context チェーンを 1 行に連結する
- `anyhow` に包んだ後でも `err.chain()` + `downcast_ref` で具体型に戻せる

### 6-1. エラー型を太らせると、成功パスに課税される（段階 2 で実測）

**`Result<T, E>` の大きさは `E` の最大バリアントで決まる。** そして `Result` は
成功しても失敗しても同じ型で返る。`tally` では 1 行ごとに 3 段
（`extract` → `select` → `push_line`）返るので、**一度も失敗しない入力でも
最大バリアントぶんのスタック領域を毎行払う。**

段階 2 で `MissingField { line_no, field: String, snippet: String }` を足したとき、
`TallyError` が 40 → 56 バイトに膨らんでいた（実測）。

対処は 2 つ。

1. **`String` → `Box<str>`。** `String` は容量フィールドのぶん 24 バイト、
   `Box<str>` は 16 バイト。**以後変更しない文字列に容量は要らない。**
   これで 56 → 48 バイト。コードの読みやすさは変わらない
2. **payload ごと `Box` に入れる**（`MissingField(Box<Detail>)`）。40 バイトまで戻るが、
   一段の間接参照とパターンマッチの読みにくさを負う

段階 2 では 1 を採り、2 は見送った理由をコメントに残した。

**一般則**: 稀にしか起きないエラーに大きなデータを持たせるときは、
`size_of::<Result<T, E>>()` を測る。**エラーの詳しさは成功パスのコストで買っている。**

### 6-2. 入力由来の文字列をエラーに載せるときの注意

- **エラーメッセージに入力をそのまま埋めない。** `{:?}`（`str` の `Debug`）で出せば、
  制御文字や非表示文字がエスケープされる。追加依存は要らない
- **「JSON なら安全」は成り立たない。** JSON がエスケープを要求するのは
  C0 制御文字（U+0000..=U+001F）だけ。U+202E（RTL override）や U+007F（DEL）は
  合法な JSON 文字列を素通りする
- **stdout と stderr で扱いを変えてよい。** stdout は他のツールへ渡すデータなので
  バイト透過、stderr は人間が読む診断なのでエスケープする。
  この非対称は仕様であって漏れではない — ただし **コメントにそう書いておかないと
  漏れに見える**（コードレビューで実際に指摘された）
- 抜粋を切るときは `&line[..N]` を使わない。`char_indices().nth(N)` が返す
  バイト位置は必ず文字境界なので、そこで切る。`nth` は N+1 文字で打ち切るため
  長い行を最後まで走査しない

### 6-3. Rust は ML から「閉じた直和」だけを取った

**最初の Rust コンパイラは OCaml で書かれている。** `Result` とパターンマッチは
ML 系譜そのもので、公式の influences にも OCaml と Standard ML が並ぶ。

**しかし Rust は OCaml の多相バリアント（開いた直和）を取らなかった。**

OCaml では関数が次の型を返せる。

```ocaml
val f : unit -> (int, [> `NotFound | `Parse ]) result
```

呼び出し側は `` `NotFound `` だけ処理して **残りをそのまま上へ投げる** ことができる。
エラーの集合が、処理されるにつれて縮む。**Rust の `enum` は閉じているので、これができない。**

**これは省略ではなく選択である。** `enum` が閉じているからこそ
網羅性検査が意味を持ち、判別子のニッチ最適化が効く。
`Option<&T>` がポインタ 1 個分に収まるのも、この閉じた世界の帰結。

**帰結**: 「関数ごとに正確なエラー型を持ち、しかも合成できる」を Rust で得ようとすると、
**言語の外**（`From` + `?`、あるいは型レベル集合を模倣するクレート）に出ることになる。

### 6-4. 「関数ごとの正確なエラー型」は言語設計の未解決問題

3 つの言語が **3 通りの答え** を出しており、どれも完成していない。

| 言語 | 合成の扱い |
| --- | --- |
| **Zig** | 関数が返しうるエラーを **推論して集合にする**（人間に書かせない） |
| **Swift** | Swift 6 の typed throws（SE-0413）で言語機能にしたが、**`throws(A \| B)` のような union が無く、要求されている最中** |
| **Rust** | `enum` + `From` + `?` で、**合成の表現をライブラリの問題に押し出した** |

**Swift の事例が最も示唆的。** Rust の影響を受けた言語が型付きエラーを言語に入れた結果、
レビューで挙がった問題が Rust の議論とそのまま重なった。

- 「1 つの型しか投げられないのは使いづらい。union が要る」
- 標準ライブラリへの適用が **source compatibility** で難航
  （`rethrows` の関数が `map` / `filter` を呼んでいると、後者が typed throws を
  導入した時点で弾かれる）

**一般則: 「関数ごとに正確なエラー型」を言語機能にすると、
必ず「複数の型の合成」の表現が問題になる。**

Rust の `From` + `?` は手抜きではなく、**この問題を言語から追い出すための設計**である。

### 6-5. エコシステムの実体（2026-08 に観測）

`lib.rs` の表示を記録する。**DL 数より逆依存クレート数のほうが採用の実態に近い**
（DL は CI の再取得で膨らむ）。

| クレート | 系統 | 月間 DL | 逆依存 | 最新リリース |
| --- | --- | --- | --- | --- |
| `thiserror` | 閉じた enum + `From` | 117,492,641 | **138,986** | 2.0.20（2026-08-08） |
| `snafu` | context selector（関数ごとの型を安くする） | 5,682,851 | **3,235** | 0.9.2（2026-07-21） |
| `error_set` | Zig 由来のエラー集合 | 16,859 | **13** | 0.9.2（2026-06-30） |
| `terrors` | 型レベル集合（多相バリアント相当） | 6,230 | **4** | 0.3.3（**2025-04-22**） |

- **`snafu` は好事家の玩具ではない。** 直接依存 974 件は、大規模プロジェクトの
  第 2 択として定着している水準
- **`error_set` / `terrors` は 4 桁違う。** `terrors` は最終リリースから 1 年以上動いていない
- 順位表示（`terrors` が `#157`、`error_set` が `#355`）は DL 数と逆転している。
  **複数の指標を混ぜているので過度に読まない**

### 6-6. std が押している方向

std は **エラー集合も匿名直和も一切採っていない。** 使う手は 3 つだけ。

1. **不透明構造体 + `kind()`**（`io::Error`）
2. **小さな閉じた enum + `#[non_exhaustive]`**
3. **合成は `Box<dyn Error>` と `source()` チェーン**

そして実際に進んだのはこの線。

- **Rust 1.81（2024-09）で `core::error::Error` が安定化。**
  目的は「対象環境に関わらず、**エコシステム全体が同じ `Error` trait に収束できる**ようにする」
- `error_generic_member_access`（`source` / `backtrace` を一般化する API）は **いまだ unstable**
- Zig 由来のエラー集合は Pre-Pre-RFC の議論のままで、**RFC にすらなっていない**

**std の賭けは「型で集合を表現する」ではなく「共通の trait と source チェーン」。**
本リポジトリが `thiserror` + `From` + `?` を採るのは、この方向に沿っている
（判断は [ADR-0004](adr/0004-error-type-shape.md)）。

## 7. CLI の構造（対象: `cli.rs` / `main.rs`）

- **`main.rs` にロジックを置かない。** 置くと検証手段がプロセス起動しかなくなる
- **引数定義を `main.rs` から分離する。** `Cli::try_parse_from([...])` で
  プロセスを起動せずに引数解釈をテストできる
- **stdout はデータ専用。** 診断・進捗・サマリはすべて stderr。
  パイプで繋いだ先が壊れないことの保証になる
- **broken pipe を成功終了として扱う。** `tally big.log | head` は異常ではない
- 色付けは `IsTerminal::is_terminal()` で条件づける
- `BufWriter` は明示的に `flush` する。`Drop` は書き込みエラーを無視する

### 7-1. clap は「閉じた集合」を要求しない（実測）

`--format` のような選択肢つき引数に `derive(ValueEnum)` を使うと enum が要るため、
**「clap が enum を要求する」と思い込みやすい。誤り。**

`PossibleValuesParser` に **実行時に組み立てた候補列**を渡すだけで、
`ValueEnum` も enum も使わずに次がすべて成立する。

```rust
Arg::new("format")
    .long("format")
    .value_parser(PossibleValuesParser::new(names))   // names は Vec<&'static str>
```

- ヘルプに `[possible values: text, json, csv]` が出る
- 不正値は `ErrorKind::InvalidValue` で拒否される
- シェル補完にも候補が出る

したがって **「候補を閉じた集合にするか」は要件の話であって、clap の制約ではない。**
第三者が形式を足せる設計にしたければ、レジストリから候補を組み立てればよい。

**もう 1 つの制約:** `derive(ValueEnum)` は **unit variant しか受け付けない**
（`only supports unit variants`）。`Csv { delimiter: char }` のような
フィールド付きバリアントは書けないので、**選択肢ごとの設定値は
CLI enum の外**（`match` の腕や別の型）で持つ必要がある。

**一般則: 「ライブラリがこう要求する」と思ったら、
それが本当に制約なのか、自分の要件なのかを切り分ける。**
制約だと誤認すると、そこを支点にした設計判断がまるごと崩れる。

### 7-2. `FromStr` を実装した型は、そのまま引数の型にできる

clap の derive は、専用の `value_parser` を書かなくても
**`std::str::FromStr` による暗黙の解釈**を使う（clap の `typed-derive` 例が
「implicit parsing using `std::str::FromStr`」として示している）。

```rust
#[arg(long, value_name = "REGEX")]
pub filter: Option<Regex>,     // Regex: FromStr なのでこれだけで通る
```

**効くのは型の便利さではなく、失敗する場所が動くこと。**
`Option<String>` で受けて後から `Regex::new` すると、
**入力を読み始めてから失敗する。** `Option<Regex>` なら
引数解釈の時点（clap の終了コード 2）で止まり、パイプの上流が無駄に走らない。

**「解釈済みの型で持つ」ことで、後段が不正値の可能性を考えなくてよくなる。**
`Option<String>` を持ち回ると「まだ検証していない文字列」が型に現れないので、
どこで検証したかを人間が覚えておく必要が出る。

### 7-3. `regex` クレートは後方参照と先読みを持たない — 代わりに線形時間

**他言語の正規表現から来ると、まずここで詰まる。**

PCRE / Java / C# / JavaScript の正規表現エンジンはバックトラック方式で、
後方参照 `\1` や先読み `(?=...)` が書ける代わりに、
`(a+)+$` のようなパターンで**入力長に対して指数時間**になりうる（ReDoS）。

Rust の `regex` は有限オートマトンに基づき、**入力長と正規表現長の積に線形**。
その代償として後方参照と先読みを**構文として持たない**。

**帰結**: 利用者が正規表現を渡せる CLI（`tally --filter` がそれ）では、
**ReDoS が原理的に起きない。** 入力の正規表現に長さ制限や実行時間制限を
掛ける必要が無く、任意の入力をそのまま受けられる。

後方参照が要るなら `fancy-regex` があるが、
**バックトラックに戻るので線形保証を失う。** 利用者入力を受ける場所では選ばない。

## 8. テスト設計（対象: `tests/cli.rs`）

- **ロジックはユニットテストに寄せる。** 統合テストはプロセス起動を伴い数百倍遅い。
  統合テストに置くのは、そこでしか検証できないもの（終了コード、stdout と stderr の分離、引数の実配線）だけ
- **`HashMap` の反復順に依存したテストはいつか落ちる。** プロセスごとにシードが変わる。
  実装側で全順序を決めるのが望ましい（出力の再現性は利用者の利益でもある）
- `clippy.toml` の `allow-expect-in-tests` は **`#[cfg(test)]` モジュールにしか効かない。**
  `tests/` 配下は通常のクレートとしてコンパイルされるため、ファイル先頭で明示的に `allow` する
- nextest はテストごとにプロセスを分けるため状態が漏れない。
  **ただしドキュメントテストを実行しない**ので別途回す必要がある

### 8-1. テストの置き場所が C++ / JUnit と逆

`src/` と並行する `test/` ツリーにテストを置く慣習とは **逆**。
Rust は **テスト対象と同じファイル・同じモジュール内**にユニットテストを置く。

```rust
#[cfg(test)]
mod tests {
    use super::*;   // 親の非公開項目が全て見える
}
```

**子モジュールが親の非公開項目を見られる**という可視性規則をそのまま使っている。
`#[cfg(test)]` により通常のビルドではコンパイルされず、リリースバイナリにも混入しない。

結果として、**`friend` 宣言や `#define private public` に相当する回避策が要らない。**
C++ でテストのためだけに可視性を緩めた経験があるなら、そこが消える。

逆に `tests/` 配下は **独立したクレートとしてコンパイルされ、公開 API しか見えない。**
つまり「どちらに書くか」は好みではなく、**検査したい対象の可視性で決まる**。
非公開項目を検査したいなら選択肢は 1 つしかない。

## 9. 環境とツールチェーン（ファイル非依存）

### 9-1. devcontainer

- **ツールチェーンのバージョンが `rust-toolchain.toml` と `Dockerfile` の 2 箇所にある。**

  ファイルパーミッションではない。** 公式 rust イメージは `RUSTUP_HOME` / `CARGO_HOME` を
  既に開放済みで、コンテナ内から rustup で差し替えることは技術的には可能
- macOS の bind mount は I/O が遅い。`target/` は名前付きボリュームに逃がす。
  副作用としてホスト側の `target/` とは完全に別物になる
- イメージサイズは推測せず実測する。**当初 3.37GB → 2.38GB に削減できたが、
  主因は想定と違った**（`chmod -R` の範囲は 280MB、`lldb` が 550MB）。
  CodeLLDB 拡張は自前の lldb を同梱するので apt から入れる必要がない

### 9-2. 公開前の情報衛生

## 10. イテレータとクロージャ（対象: `core.rs` / `main.rs`）

### 10-1. `for` ループとアダプタ合成は、同じ機械語にはならなかった（実測）

段階 4 で集計を `for` ループからアダプタ合成へ書き換えた。**同じ処理を両方の形で
書き、release ビルドの機械語を比べた**（aarch64、LTO なし）。ジェネリックのままでは
lib 単体で機械語が出ないので、入力を `&[u8]`、述語を関数ポインタに固定した
非ジェネリック版を 2 つ用意して比較した。

| | 命令数 | スタックフレーム |
| --- | --- | --- |
| `for` ループ | **208** | 240 バイト |
| アダプタ合成 | **333**（+60%） | 704 バイト |

**「ゼロコスト抽象」は、この形では字義どおりには成立しなかった。**
`.map()` が `Result<(usize, String), _>` を作り、`filter` がそれを覗き、
`try_fold` のクロージャが再び分解する。中間の組を持ち回るぶんの状態が
スタックに現れている。

**言えないこと**: これは **コードサイズであって実行時間ではない。**
速度は測っていないので「ループのほうが速い」とは書けない。
本 CLI は 1 行ごとに I/O とハッシュ挿入をするので、この差が
実行時間に現れるかは別途測らないと分からない。debug ビルドも測っていない。

### 10-2. `Iterator<Item = Result<T, E>>` は、アダプタごとに扱いを決めねばならない

**他言語との最大の差はここにある。** 例外を持つ言語（Java / C#）では、
ストリームの途中で失敗すると例外が帯域外に飛び、各アダプタは失敗を意識しない。
Rust では **失敗が要素そのもの** なので、アダプタを 1 つ挟むたびに
「`Err` をどうするか」を書くことになる。

`reader.lines()` は `Iterator<Item = io::Result<String>>` を返す。段階 4 で使った 3 つ。

**`map` — 中身にだけ触る。**

```rust
.map(|(index, line)| line.map(|line| (index + 1, line)))
```

外側の `map` はイテレータの、内側は `Result` の `map`。
`Err` はそのまま通り抜ける。

**`filter` — `Err` を落としてはいけない。**

```rust
.filter(|item| match item {
    Ok((_, line)) => keep(line),
    Err(_) => true,
})
```

述語は `Err` を判定できない。**ここで `Err` を落とすと、
「読めなくなった入力」が「フィルタに合わなかった行」と区別できなくなり、
途中で切れたファイルが成功として集計される。**

**`try_fold` — `collect::<Result<Vec<_>, _>>()` の代わり。**

`collect::<Result<Vec<_>, _>>()` は「最初の `Err` で短絡する」とよく紹介されるが、
**短絡するまでの成功分はすべて `Vec` に確保される。** 入力が標準入力の
ストリームである以上、入力サイズぶんのメモリを要求する形は選べない。
`try_fold` は 1 行ずつ畳み込み、最初の `Err` で打ち切る。確保は起きない。

> **短絡することと、メモリを使わないことは別の話。** ここを混同していた。

### 10-3. アダプタの順序は書き味ではなく意味論

```rust
.enumerate()          // ← filter より前
.filter(...)
```

`enumerate` を `filter` の後ろに置くと、**除外した行のぶんだけ行番号がずれる。**
エラーメッセージの「3 行目」が入力の 3 行目を指さなくなり、利用者は該当行を開けない。

**この不具合はテストで先に観測してから直した。** 骨格の段階では
`line_no: 2`（本来 3）が出ており、アダプタの順序が意味を持つことが目に見えた。

### 10-4. `Fn` / `FnMut` / `FnOnce` を境界に選ぶのは、最適化ではなく仕様の宣言

`Iterator::filter` が要求するのは `FnMut` だが、`tally_reader` の述語は
**あえて `Fn` に絞ってある。**

三者の差は「呼び出しが自分をどう取るか」— `&self` / `&mut self` / `self`。
`Fn` に絞ると **状態を持つクロージャを渡せなくなる。**
「最初の 10 行だけ通す」ような述語が書けたら、フィルタは `--limit` と競合する
別種の機能になる。**型でそれを禁じている。**

C# の `Func<T, bool>` や Java の `Predicate<T>` にこの区別は無く、
状態を持つラムダを渡せてしまう。**「渡せない」ことを API が言えるのが差分。**
Scala も同様に区別しない。
