## 既知の落とし穴

- **`clippy.toml` の `allow-expect-in-tests` は `#[cfg(test)]` にしか効かない。**
  `tests/` 配下は通常のクレートなので、ファイル先頭で明示的に `allow` する
- **nextest はドキュメントテストを実行しない。** `cargo test --workspace --doc` を別途回す
- **ツールチェーンのバージョンが 2 箇所にある**（`rust-toolchain.toml` と `.devcontainer/Dockerfile`）。
  片方を変えたらもう片方も変える
- **コンテナの `target/` はホストと別物**（名前付きボリューム）。
  「ホストでは通るがコンテナで落ちる」の切り分け時に注意
- **`HashMap` の反復順に依存したテストは書かない。** プロセスごとにシードが変わる

## 未決事項

1. **カリキュラムの完了条件が未定義。** 名目上の終点は段階 9 だが、
   「役目を終えた」とする基準は決めていない
2. **段階 3 で `Format` を trait にすべきかは未決。**
   enum + `match` のままが正しい可能性も検討する
3. **`Selector` の公開フィールドは外部から構築できるため、追加は破壊的変更。**
   段階 5 の `tally-core` 分離時に `#[non_exhaustive]` かビルダーを検討すること。
   （段階 4 の `--filter` はここに入れない方針が確定したので、当面は増えない）
   あわせて **`strict` が `Selector` に属するべきか**も問い直す価値がある
   （抽出の性質ではなく結果に対する方針なので、呼び出し側の判断にもできる）
4. **行番号を持つエラー 3 種のうち、抜粋を載せているのは `MissingField` だけ。**
   `InvalidJson` と `UnsupportedFieldType` も同じ「何行目がどう見えたか」に
   答えるべきだが、抜粋を持たない。`LineContext { line_no, snippet }` に括り出す案がある。
   **段階 5 で `tally-core` を切り出すとバリアントの形が公開 API になる**ので、
   その前に決めること
5. **`--strict` は最初の 1 件で止まる（fail fast）。** 入力検査用途では
   「全件報告してから失敗」のほうが有用な場面がある。段階 2 では意図的に見送った。
   必要になれば `--max-errors` を足す
