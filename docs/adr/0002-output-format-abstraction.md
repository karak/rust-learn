# 出力形式の抽象化: enum + match を保つか、trait Formatter に切り替えるか

## コンテキストと問題提起

`tally` は集計結果を `--format` で選んだ形式で出力する。現状は
`cli::Format`（`Text` / `Json`）の enum を `main.rs` の `write_report` が
`match` で分岐している。段階 3 で **CSV を追加**し、あわせて
`trait Formatter` への切り替えを検討する。

現状には、抽象化の是非とは独立した問題が 2 つある。

1. `write_report` が `main.rs` にある。これは `(Report, Format) → バイト列` の
   純粋関数であり、`layout.md` が `main.rs` について禁じている
   「ロジック全般。**純粋関数にできるものは `core` へ**」に当たる
2. その結果 **整形のユニットテストが 1 つも無い**。統合テストが JSON 出力を
   部分一致で見ているだけで、内容は検証されていない

**この 2 点はどの案を選んでも直す。**本 ADR が扱うのは抽象化の形だけ。

## 意思決定の推進力（Decision Drivers）

**重みを明記する。** 重みの無い推進力の列挙は、結論をどうとでも導ける。

| # | 推進力 | 重み | 根拠 |
| --- | --- | --- | --- |
| D2 | 形式を追加するとき、更新漏れがコンパイルエラーになるか | **高** | 段階 2 で「ワイルドカードは将来の自分への沈黙」を学んだ。同じ失敗を繰り返さない |
| D7 | 形式ごとの実装が読みやすく、単位でテストできるか | **高** | 学習リポジトリとして、後から読んで理解できることが成果物の一部 |
| D1 | 段階 3 の学習目標（trait とジェネリクスの理解）に資するか | **中**（同点時の決め手） | 学習目的で技術的に劣る案を採らない。ただし互角なら学べるほうを採る |
| D3 | 操作（メソッド）を追加するコスト | **低** | **投機である。** `curriculum.md` 段階 4〜9 に formatter の操作が増える計画は無く、CSV もヘッダ行を出さないと決めたため `write_header` は不要（[ADR-0003](0003-csv-output-contract.md)） |
| D5 | 実行時コスト | **ほぼゼロ** | 出力は 1 プロセス 1 回。実測しても案を判別できない |
| D6 | 第三者クレートが形式を足せる必要 | **ゼロ** | 現時点で要求が無い。**これは要件ではなくこちらの判断である** |

### 制約ではない事項

**clap は閉じた集合を要求しない。** `PossibleValuesParser` に実行時の候補列を
渡せば、ヘルプへの候補表示・不正値の拒否・シェル補完がすべて成立する
（`docs/learning-log.md` 節 7-1）。

つまり **enum を使うかどうかは clap の制約ではなく、D6 に対するこちらの判断の帰結**である。

## 検討した選択肢

* **A. enum + 自由関数 + `match`**（現状の形。`format` モジュールへ移すのみ）
* **B. enum + 固有メソッド**（`impl Format { fn write(..) }`）
* **C. `trait Formatter` + `Box<dyn Formatter>`**（動的ディスパッチ）
* **E. ハイブリッド**: `trait Formatter` が操作を定義し、
  enum が CLI 解釈と **網羅的 match による静的ディスパッチ** を担う

**「trait + ジェネリクス単独」は選択肢にならない。** `--format` は実行時に決まるため、
ジェネリクスだけでは選択を表現できず、どこかで `match` して具体型に落とす必要がある。
それは E そのものである。

## 意思決定の結果

**A（enum + 自由関数 + `match`）を採る。** C と E のコードは削除した。

**決め手は「この規模では trait の利点が現れない」という実測**であって、
trait が劣るという一般論ではない。下記「確認の結果」の 2 つの表がその根拠。

- **D2（形式追加時の網羅性）は 3 案とも同じ。** 想定と違い、差が無かった
- **D7（形式ごとの集約）で C・E が持つ利点は、形式 1 つが 3〜5 行では現れない**
- **D3（操作追加）で C・E が明確に勝つが、重みが低いうえ実需が無い**（[ADR-0003](0003-csv-output-contract.md)）
- **D1（学習）は同点時の決め手だが、同点ではなかった。**
  かつ `dyn` から得たい学習は実装して測った時点で得ており、
  `docs/learning-log.md` 節 4-7・4-8 に残っている。**コードを残す必要はない**

**この決定は「この規模の utility だから」である。**
決定者（学習者）の実務経験として、**本格的な業務用途では E の拡張性が惜しい**
という判断が併記された。下記「追加情報」の再評価条件はこれを受けたもの。

前提として確定していたこと。

- **D6 = ゼロと判断した以上、形式の集合を閉じたまま扱ってよい。**
  そう決めたなら enum で表現することで D2（網羅性）が無料で手に入る
- **実質的な対決は A/B 対 C 対 E。** 差は D7（形式ごとのコード集約とテスト単位）に集約される
- **A と B の差は構文だけ。** 実質同一なので、以降は A に代表させる

### 確認方法（Confirmation）

**実行時コストは採否の基準にしない。** D5 がほぼゼロである以上、
実測しても案を判別できないため。代わりに次を実施して比較する。

1. **A・C・E を実際に実装する。** 3 つとも動く状態にする
2. **「CSV を 1 つ足す差分」** を各案で取り、行数と、
   **どの誤りがコンパイルエラーになるか** を記録する
3. **「操作を 1 つ足す差分」** を各案で取る（例: `write_header`）。
   D3 は投機なので採否の主因にはしないが、**差の大きさは記録する**
4. 各案の総行数と、形式 1 つあたりの実装が何行になるかを記録する
5. D5 は **学習目的（D1）として** 実測する。生成コードで
   `Box<dyn>` の間接参照と単相化の差を見る。**採否の根拠には使わない**

段階 3 の完了条件は `docs/curriculum.md` が正本。ここには重複させない。

### 確認の結果

**手順 1〜5 を実施した。** 3 案を `crates/tally/src/format/` に同居させて測り、
決定後に採らなかった 2 案を削除した。**同居していた状態はタグ
`adr-0002-baseline` に残っている。**

**行数は本番コードのみ、空行を除いて数えた。** テストは 3 案で共有した
（標本・期待値・検証を 1 箇所に置いた）ので差が出ない。
CSV の引用規則 `quote_field` も 3 案で共有しており、この数には入らない。
**共有したのは意図的で、dispatch の形と無関係な定数を案ごとに複写すると、
測りたい差が 3 倍に見えてしまうため。**

| 測ったもの | A | C | E |
| --- | --- | --- | --- |
| **形式を 1 つ足す**（CSV） | **5 行** | 10 行 | 10 行 |
| **操作を 1 つ足す**（`write_header`） | **8 行** | 10 行 | 10 行 |
| 形式 1 つあたりの実装 | `match` の腕 3〜5 行 | 型 + `impl` 9 行 | 型 + `impl` 9 行 |

**どの誤りがコンパイルエラーになるか。**

| 変更 | A | C | E |
| --- | --- | --- | --- |
| 形式を足して dispatch を書き忘れる | E0004 × 1 | E0004 × 1 | E0004 × 1 |
| 操作を足して実装を書き忘れる | **何も起きない**（関数を書かなければ気づかない） | E0046 × 3（型を列挙） | E0046 × 3（型を列挙） |

- **形式追加の検出は 3 案とも等しい。** 事前の想定どおり、差は無かった
- **操作追加の検出だけは C・E が勝つ。** trait にメソッドを足すと、
  実装していない型が名指しで列挙される。A では「その関数を書く」こと自体を
  誰も強制しない（書けば `match` が網羅検査する）

**実行時コスト（D5、採否には使わない）。**
`Box<dyn>` の経路は vtable の表引き + 間接呼び出し + drop glue + サイズ判定を
生む。詳細と機械語は `docs/learning-log.md` 節 4-8。
**1 プロセス 1 回の呼び出しでは、いずれも判断に影響しない。**

**この結果が示したこと。**

- **A が両方の軸で行数が少ない。** 「trait は操作追加に強い」という一般論は、
  **形式が 3 つ・操作の本体が 1〜3 行という現在の規模では成り立たない。**
  `impl` ブロックとメソッド署名の定型が、`match` の腕より高くつく
- 差が逆転するのは、**形式ごとの本体が長くなったとき**（D7 の重みが増したとき）。
  CSV の本体は 3 行にとどまり、その水準に達していない

## 選択肢の長所・短所

**全案に共通する前提**（個別の項目に書かない）:

- どの案でも `Format` を enum として持ち、`match` で dispatch する（D6 = ゼロの帰結）。
  したがって **D2（形式追加時の網羅性検査）はどの案も満たす**
- `derive(ValueEnum)` は unit variant しか受け付けないため、
  **CLI enum 自身に状態を持たせられない制約も全案に等しくかかる**
  （形式ごとの状態は `match` の腕で構築する。`docs/learning-log.md` 節 7-1）

### A. enum + 自由関数 + `match`（B を代表）

`format` モジュールへ移し、`Format` を引数で受けて `match` する。

* Good, because **最も記述量が少ない。** 形式 3 つ × 操作 1 つなら、これで足りる
* Good, because 読むべき場所が 1 箇所にまとまる（D7 の一面）
* Bad, because **形式ごとのロジックが 1 つの関数に同居する。**
  CSV の引用規則を読むために JSON と Text を読み飛ばす必要がある（D7 の他面）
* Bad, because 形式ごとのユニットテストが、関数全体を通したテストになる
* Bad, because 操作を増やすと `match` が増殖する（D3、ただし重みは低い）

### C. `trait Formatter` + `Box<dyn Formatter>`

trait を定義し、`Format` から `Box<dyn Formatter>` を作って動的ディスパッチする。

* Good, because 形式ごとの実装が型ごとに完全に分離し、型単位でテストできる（D7）
* Good, because 操作の追加が trait へのメソッド追加で済み、実装漏れを検出できる（D3）
* Good, because **`dyn` 固有の論点に触れられる。** オブジェクト安全性、
  vtable の位置、fat pointer のサイズ。**この学習は C を書かないと得られない**（D1）
* Neutral, because **形式が ZST なら `Box::new` はアロケーションしない**
  （`docs/learning-log.md` 節 4-7）。実コストは vtable 間接参照 1 回だけ
* Bad, because オブジェクト安全性の制約がかかる（ジェネリックメソッドを持てない）
* Bad, because 形式ごとに状態を持つ設計にすると、`Box` の確保が発生する
  （1 プロセス 1 回なので実害は小さい）

### E. ハイブリッド（trait が操作、enum が解釈と静的 dispatch）

`trait Formatter` を各形式の型が実装し、`Format` の網羅的 `match` が
具体型を選んで静的に呼ぶ。

* Good, because C の D7 の利点をそのまま持ち、vtable の間接参照が無い
* Good, because 操作の追加を trait が検出する（D3）
* Neutral, because C との差は vtable 間接参照 1 回のみ。D5 の重みはほぼゼロ
* Bad, because **A に対して型が増える。** 形式 3 つ × 操作 1 つの現状では、
  得られる D7 に対して記述量が見合うか不明
* Bad, because `dyn` を書かないため、C で得られる学習（D1）が得られない

## 追加情報

**この決定を覆すべき条件**（該当したら新しい ADR で supersede する）:

- **形式 1 つあたりの実装が概ね 20 行を超えたら E に移る。**
  これが最も起きやすい。今回 A が勝った差（形式追加で 5 行 対 10 行）は、
  本体が短いあいだだけ成立する。本体が伸びれば
  「1 つの関数に全形式が同居する」ことの読みにくさが定型の差を上回る
- **操作が 2 つ以上に増えたら E に移る。** 実測で C・E だけが持っていた利点
  （実装漏れが `E0046` で型ごとに列挙される）が効き始める。
  操作 1 つでは A のほうが 2 行少なかったが、これは操作の本体が 1 行だったため
- **第三者クレートが形式を足す要求が出たら C に移る**（D6 が変わる場合）。
  enum による閉じた集合が制約になる。`PossibleValuesParser` + レジストリの構成
- **業務用途への転用時は、上の条件を待たずに E から始めてよい。**
  決定者の実務経験による。**後から enum を trait に割るコストは、
  最初から trait で書くコストより高い**（呼び出し側の署名が変わる）。
  本リポジトリは学習用の utility なので、この予防を採らなかった

**再評価の起点は残してある。** タグ `adr-0002-baseline` に 3 案が同居した
状態があり、E へ移るときはそこから `static_variant.rs` を復元できる。
