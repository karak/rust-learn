# 出力形式の抽象化: enum + match を保つか、trait Formatter に切り替えるか

## コンテキストと問題提起

`tally` は集計結果を `--format` で選んだ形式で出力する。現状は
`cli::Format`（`Text` / `Json`）の enum を `main.rs` の `write_report` が
`match` で分岐している。段階 3 で **CSV を追加**し、あわせて
`trait Formatter` への切り替えを検討する。

現状には、抽象化の是非とは独立した問題が 2 つある。

1. `write_report` が `main.rs` にある。これは `(Report, Format) → バイト列` の
   純粋関数であり、`layout.md` の「`main.rs` はロジックを持たない」に違反している
2. その結果 **整形のユニットテストが 1 つも無い**。統合テストが JSON 出力を
   部分一致で見ているだけで、内容は検証されていない

**この 2 点はどの案を選んでも直す。**本 ADR が扱うのは抽象化の形だけ。

## 意思決定の推進力（Decision Drivers）

**重みを明記する。** 重みの無い推進力の列挙は、結論をどうとでも導ける
（初版がその状態だった）。

| # | 推進力 | 重み | 根拠 |
| --- | --- | --- | --- |
| D2 | 形式を追加するとき、更新漏れがコンパイルエラーになるか | **高** | 段階 2 で「ワイルドカードは将来の自分への沈黙」を学んだ。同じ失敗を繰り返さない |
| D7 | 形式ごとの実装が読みやすく、単位でテストできるか | **高** | 学習リポジトリとして、後から読んで理解できることが成果物の一部 |
| D1 | 段階 3 の学習目標（trait とジェネリクスの理解）に資するか | **中**（同点時の決め手） | 学習目的で技術的に劣る案を採らない。ただし互角なら学べるほうを採る |
| D3 | 操作（メソッド）を追加するコスト | **低** | **投機である。** `curriculum.md` 段階 4〜9 に formatter の操作が増える計画は無い |
| D5 | 実行時コスト | **ほぼゼロ** | 出力は 1 プロセス 1 回。実測しても案を判別できない（下記 Confirmation 参照） |
| D6 | 第三者クレートが形式を足せる必要 | **ゼロ** | 現時点で要求が無い。**ただしこれは要件ではなく、こちらの判断である** |

**初版にあった「D4 clap が閉じた集合を要求する」は削除した。事実に反する**
（改訂の記録を参照）。閉じた集合は clap の制約ではなく、D6 = 不要という
こちらの判断の帰結にすぎない。

## 検討した選択肢

* **A. enum + 自由関数 + `match`**（現状の形。`format` モジュールへ移すのみ）
* **B. enum + 固有メソッド**（`impl Format { fn write(..) }`）
* **C. `trait Formatter` + `Box<dyn Formatter>`**（動的ディスパッチ）
* **E. ハイブリッド**: `trait Formatter` が操作を定義し、
  enum が CLI 解釈と **網羅的 match による静的ディスパッチ** を担う

初版にあった「D. trait + ジェネリクス単独」は選択肢から外した。
`--format` は実行時に決まるため、どこかで `match` して具体型に落とす必要があり、
**それは E そのもの**である。別案として数えていたのは水増しだった。

## 意思決定の結果

**未定。初版の暫定結論（E）は撤回する。**

初版は「D4 により enum は消せない → よって問いは enum を残して操作をどこに置くか
→ E」という一本の論証で E を導いていた。**その D4 が偽だったため、論証ごと崩れた。**

現時点で言えるのは次まで。

- **D6 = ゼロと判断した以上、形式の集合を閉じたまま扱ってよい。**
  これは clap の制約ではなく設計判断であり、そう決めたなら enum で表現すると
  D2（網羅性）が無料で手に入る
- **実質的な対決は A/B 対 C 対 E。** 差は D7（形式ごとのコード集約とテスト単位）に集約される
- **A と B の差は構文だけ。** 実質同一なので、以降は A に代表させる

決定は、下記 Confirmation の比較を実施してから行う。

### 確認方法（Confirmation）

**初版の「実行時コストの実測で決める」は破棄する。** D5 がほぼゼロである以上、
実測しても案を判別できない。判別力の無い基準を採否条件に据えていたのは誤り。

代わりに、次を実施して比較する。

1. **A・C・E を実際に実装する。** 3 つとも動く状態にする
2. **「CSV を 1 つ足す差分」** を各案で取り、行数と、
   **どの誤りがコンパイルエラーになるか** を記録する
3. **「操作を 1 つ足す差分」** を各案で取る（例: `write_header`）。
   D3 は投機なので採否の主因にはしないが、**差の大きさは記録する**
4. 各案の総行数と、形式 1 つあたりの実装が何行になるかを記録する
5. D5 は **学習目的（D1）として** 実測する。生成コードで
   `Box<dyn>` の間接参照と単相化の差を見る。**採否の根拠には使わない**

なお段階 3 の完了条件は `docs/curriculum.md` が正本。ここには重複させない。

## 選択肢の長所・短所

### A. enum + 自由関数 + `match`（B を代表）

`format` モジュールへ移し、`Format` を引数で受けて `match` する。

* Good, because **最も記述量が少ない。** 形式 3 つ × 操作 1 つなら、これで足りる
* Good, because 形式追加時に `match` の網羅性検査が働く（D2）
* Good, because 読むべき場所が 1 箇所にまとまる（D7 の一面）
* Bad, because **形式ごとのロジックが 1 つの関数に同居する。**
  CSV の引用規則を読むために JSON と Text を読み飛ばす必要がある（D7 の他面）
* Bad, because 操作を増やすと `match` が増殖する（D3、ただし重みは低い）
* Neutral, because 形式ごとの状態（CSV の区切り文字など）は `match` の腕で作れる。
  **`derive(ValueEnum)` は unit variant しか受けないため、
  CLI enum 自身に状態を持たせられない。これは C・E でも同じ制約**

### C. `trait Formatter` + `Box<dyn Formatter>`

trait を定義し、`Format` から `Box<dyn Formatter>` を作って動的ディスパッチする。

* Good, because 形式ごとの実装が型ごとに完全に分離する（D7）
* Good, because **対応表を enum の `match` で書けば網羅性検査は失われない。**
  腕の書き忘れは `E0004` になる（初版はここを誤っていた）
* Good, because 操作の追加が trait へのメソッド追加で済み、実装漏れを検出できる（D3）
* Good, because **`dyn` 固有の論点に触れられる。** オブジェクト安全性、
  vtable の位置、fat pointer のサイズ。**この学習は C を書かないと得られない**（D1）
* Neutral, because **`Box::new(ZST)` はアロケーションしない**（実測: 0 回）。
  初版の「ZST をヒープに置くのは不当」は誤り。実コストは vtable 間接参照 1 回だけ
* Bad, because オブジェクト安全性の制約がかかる（ジェネリックメソッドを持てない）
* Bad, because 形式ごとに状態を持つなら `Box` の確保が発生する
  （ZST でなくなるため。ただし 1 プロセス 1 回）

### E. ハイブリッド（trait が操作、enum が解釈と静的 dispatch）

`trait Formatter` を各形式の型が実装し、`Format` の網羅的 `match` が
具体型を選んで静的に呼ぶ。

* Good, because C の D7 の利点をそのまま持ち、vtable の間接参照が無い
* Good, because 形式追加は `match` が、操作追加は trait が検出する
* Neutral, because **D2 と D3 を同時に満たすのは E だけではない。**
  A も B も C も、enum で dispatch する限り D2 は満たす。
  初版が E の固有の利点として挙げていたのは過大だった
* Neutral, because C との差は vtable 間接参照 1 回のみ。D5 の重みはほぼゼロ
* Bad, because **A に対して型が増える。** 形式 3 つ × 操作 1 つの現状では、
  得られる D7 に対して記述量が見合うか不明
* Bad, because `dyn` を書かないため、C で得られる学習（D1）が得られない

## 改訂の記録

**初版は敵対的レビューで中心論証が崩された。** 崩された主張と、
それぞれの検証結果を残す。**この節が本 ADR の最も価値ある部分である。**

| 初版の主張 | 検証結果 | 検証方法 |
| --- | --- | --- |
| clap の `ValueEnum` が閉じた集合を要求するので enum は消せない（D4） | **偽** | `PossibleValuesParser` に実行時の候補列を渡すだけで、ヘルプに `[possible values: ...]` が出て、不正値は `ErrorKind::InvalidValue` で拒否される。enum も `ValueEnum` も不要 |
| C は enum → `Box<dyn>` の対応表に網羅性検査が無い | **偽** | 対応表を `match` で書けば腕の欠落は `E0004: non-exhaustive patterns` になる |
| C は状態を持たない型をヒープに置くので不当 | **偽** | `Box::new(ZST)` はグローバルアロケータを 0 回しか呼ばない（実測）。`size_of::<Text>() == 0` |
| B は形式ごとの状態を持たせにくい（E は持てる） | **偽** | `derive(ValueEnum)` は unit variant しか受け付けない（`only supports unit variants`）。**制約は E にも等しくかかる** |
| E は D2 と D3 を同時に満たす唯一の案 | **過大** | enum で dispatch する限り、どの案も D2 を満たす |
| D（trait + ジェネリクス単独）は独立した選択肢 | **水増し** | 実行時選択には `match` が要り、それは E に等しい。選択肢から削除した |

**何を間違えたか（構造）:**

1. **要件と実装制約を混同した。** 「ヘルプと補完を出したい」という要件を、
   「clap が閉じた集合を要求する」という実装制約だと思い込み、
   それを論証の支柱に据えた。**支柱にする主張ほど、検証を要する**
2. **反対案への攻撃を検証しなかった。** C への Bad 3 点のうち 2 点が事実に反していた。
   自分が推す案の利点は疑うが、**退ける案の欠点は疑わなかった**
3. **推進力に重みを付けなかった。** 7 つを同列に並べたため、
   実際には D4 一本で結論を出しているのに、多角的に検討したように見えていた
4. **判別力の無い基準を確認方法に据えた。** D5 がほぼゼロと自分で書きながら、
   実行時コストの実測で採否を決めるとしていた

**この 4 つは出力形式の話に限らない。** 設計判断一般で再発しうる。

## 追加情報

判断が変わる条件:

- **D6 が変われば C が有利になる。** 第三者が形式を足す要求が出たら、
  enum による閉じた集合は制約になる。そのときは `PossibleValuesParser` +
  レジストリの構成が使える（実装可能であることは確認済み）
- **D3 が伸びれば C・E が有利になる。** ただし現時点で curriculum に予定は無く、
  **投機で設計を重くしない**
- **形式ごとの実装が大きくなれば D7 の重みが増し、C・E が有利になる。**
  CSV の引用規則を書いた時点で再評価する
