# 複数入力の集計と、その失敗の文脈

**論点ごとに、扱うときに案と評価を書き足していく文書である。**
書き方は [ADR-0005](0005-selector-public-api.md) の「この文書の書き方」に従う
（**案を先に書き溜めない。** 1 論点を扱うとき、その論点の案だけを書く）。

## コンテキストと問題提起

段階 6 で `tally` は複数のファイルを引数に取り、ファイル単位で並列に集計する
（課題は `docs/curriculum.md` 段階 6）。

**段階 5 の公開 API は「入力は最大 1 つ」を前提にしている。**
その前提は 3 箇所で明示的に先送りされていた。

| 先送りした場所 | 書かれていたこと |
| --- | --- |
| [ADR-0004](0004-error-type-shape.md) の Confirmation | `CliErrorKind::Tally` の `#[error(transparent)]` は「複数入力を扱うようになったら見直す」 |
| [ADR-0005](0005-selector-public-api.md)「実装時に決めたこと」 | `tally_reader` の引数の形は「複数入力を 1 つの集計に合流させたくなったら見直す」 |
| `docs/handoff.md` 未決事項 5 | 複数入力になったとき、どのファイルの失敗かを言えない |

**前提は [ADR-0004](0004-error-type-shape.md) の「前提」節と共有する。**
要点だけ: 判断の基準は「中規模の実務ツールで公開 API だったときの定石」、
**1.0 以前は破壊的変更を受け入れる。**

### 現状の事実（2026-09-23 に確認）

| 事実 | 場所 |
| --- | --- |
| `tally_reader` は `Counter` を消費して **`Report` を返す** | `crates/tally-core/src/count.rs`（`tally_reader`） |
| `Report` は順位づけ済みで、`limit` で **切り詰められうる** | 同（`Counter::report`） |
| `Counter` のフィールドは非公開。derive は `Debug, Default` のみ（`Clone` なし） | 同（`Counter`） |
| `strict` は `Counter` が持つ（ADR-0005 論点 1） | 同 |
| `TallyError::OpenInput` は `path` を持つ。`Read` と `Line` は持たない | `crates/tally-core/src/error.rs`（`TallyError`） |
| `LineError::line_no` は **入力ごとに 1 から数える** | `count.rs`（`tally_reader` の `enumerate`） |
| `CliErrorKind::Tally` は `#[error(transparent)]` で文脈を足さない | `crates/tally/src/error.rs` |
| 入力は `Cli::input: Option<PathBuf>` の 1 つ | `crates/tally/src/cli.rs` |
| `rayon` はワークスペースの依存表にあるが、**どのクレートも使っていない** | `Cargo.toml` |

**`Report` はマージできない。** 上位 N 件に切り詰めた 2 つの結果を足しても、
全体の上位 N 件にはならない（片方で N+1 位だったキーが、合算すると 1 位になりうる）。
**したがって、合流は `Report` になる前の `Counter` で行うしかない。**

## 論点の分割

| # | 論点 | 状態 | 依存 |
| --- | --- | --- | --- |
| 1 | `Counter` のマージの形（`strict` が食い違うときを含む） | **決定済み** | — |
| 2 | 入力 1 つぶんの集計が何を返すか（`tally_reader` の形） | **決定済み** | 1 |
| 3 | 失敗にどのファイルかを持たせる場所（core か CLI か。`OpenInput` との二重） | **決定済み** | — |
| 4 | 複数のファイルが失敗したとき、どれを報告するか | **決定済み** | 3 |
| 5 | 並列化をどちらのクレートに置くか | 未着手 | 2 |

**1 と 3 は独立。** 4 は 3 の形に、5 は 2 の形に乗る。

## 論点 1: `Counter` のマージの形（決定済み）

**ファイル単位で集計した結果を 1 つに合流させる手段を、公開 API に 1 つ足す。**

### 決定

**専用の `merge` を足す。`Extend` も `Add` も実装しない。**

```rust
impl Counter {
    /// `other` の集計を取り込む。**方針（`strict`）は `self` のものを保つ。**
    pub fn merge(&mut self, other: Counter) { /* counts / skipped / total を足す */ }
}
```

### この論点に効く事実（2026-09-23 に確認）

| 事実 | 効き方 |
| --- | --- |
| `Report` は順位づけ済みで `limit` に切り詰められうる | **合流は `Counter` でしか行えない。** 上位 N 件同士を足しても全体の上位 N 件にならない |
| `Counter` が持つのは `counts` / `skipped` / `total` / `strict` の 4 つ | 前 3 つは足せる。**足せないのは `strict` だけ** |
| `strict` が効くのは `Counter::push_line` の最中だけで、`Report` には現れない | **マージ後の `strict` は、それ以降に行を積むかどうかにしか影響しない** |
| `HashMap<K, V>` の `Extend<(K, V)>` は **値を上書きする**（`insert` と同じ） | 同じ名前で加算すると意味が反転する |
| Rust の標準に `Monoid` に相当する trait は無い | 「足せる」を型で言う手段は `Add` / `AddAssign` / `Sum` しかない |
| rayon の `reduce` が要求するのは `Fn() -> T` と `Fn(T, T) -> T` | **trait 実装は要らない。** 関数があれば足りる |

### 検討した案

#### 1a. `Extend<(String, u64)>` + `IntoIterator`（却下）

標準ライブラリの慣習に乗せる形。`counter.extend(other)` と書ける。
`FromIterator` も一緒に実装すれば `collect()` も通る。

- 利点: 既存の trait なので、**呼び出し側が総称に書ける。**
  `fn combine<C: Extend<(String, u64)>>(...)` のような関数が書ける
- 利点: `IntoIterator` を足すと `Counter` の中身を外に出す手段が手に入る
- 欠点: **`HashMap` の `Extend` は値を上書きする。** 同じ形の引数を取って
  加算する実装は、`HashMap` を知っている読み手の予想を裏切る。
  **裏切りは型では現れず、数が静かに合わなくなる**
- 欠点: **`skipped` と `total` を運べない。** 項目の列は `(キー, 件数)` の並びで、
  「取り出せなかった行が何行あったか」はそこに入らない。
  結果として `extend` の後に `skipped` を別経路で足す必要が生まれ、
  **1 回のマージが 2 つの手順に割れる**
- 欠点: `IntoIterator` を足すと、`counts` の表現（`HashMap<String, u64>`）が
  公開の約束に近づく。ADR-0005 論点 2 が非公開フィールドを採った理由に反する

#### 1b. `AddAssign` / `Add` + `Sum`（却下）

`a += b` と書ける形。`Sum` まで実装すれば `iter.sum()` が通り、
rayon にも `ParallelIterator::sum()` がある。Scala の `Monoid`（`|+|`）や
C# の `IAggregateOperators` に相当する位置づけ。

- 利点: **記法が短い。** 合流が 1 演算子で書ける
- 利点: `Sum` があると、逐次と並列の両方で同じ書き方になる
- 欠点: **演算子は単位元と結合則と可換性を約束する。**
  `Counter` の単位元は `Counter::new()` だが、
  **`strict` を持つ `Counter` にとっての単位元は `Counter::new().strict(true)`** で、
  型としては同じものが 2 つの意味を持つ。`Sum` の実装は `Default` から始めるので、
  **空の列を `sum()` すると方針が黙って `strict(false)` に落ちる**
- 欠点: 可換性が `strict` については成り立たない（`a + b` と `b + a` で
  マージ後の方針が変わる）。**観測できる `Report` は変わらない**ので実害は無いが、
  **演算子はそこまで含めて約束する記号**である
- 欠点: `Add`（消費して新しい値を返す形）は `counts` を 2 つ持つ瞬間を作る。
  `AddAssign` だけを実装して `Add` を実装しないのは、**標準の慣習に反する**
  （`Add` があって `AddAssign` が無い型はあるが、逆は珍しい）

#### 1c. 専用の `merge`（採用）

`fn merge(&mut self, other: Counter)` を足す。rayon では次のように書く。

```rust
.try_reduce(|| Counter::new().strict(strict), |mut acc, other| {
    acc.merge(other);
    Ok(acc)
})
```

- 利点: **名前が意味を言う。** 「上書きか加算か」を読み手が推測せずに済む
- 利点: `skipped` と `total` を同じ 1 回の呼び出しで運べる
- 利点: **`strict` の扱いを doc に書ける。** 演算子と違い、
  「`self` の方針を保つ」という非対称を明示できる
- 利点: `counts` の表現を公開しない
- 欠点: **糖衣が無い。** `reduce` の閉包が 3 行になる
- 欠点: 総称の関数から使えない（`Extend` のような共通の入口が無い）。
  ただし **いま総称に書きたい呼び出し側は無い**

### 対称性の検査

**却下した案の欠点を、採用案と同じ精度で疑う**（ADR-0005 の書き方に従う）。

- **1a の「予想を裏切る」は、`Extend` の意味を誤解していないか。**
  `Extend` の契約は「項目を追加する」であって「上書きする」ではない。
  `HashMap` が上書きするのは、**キーが重複したときの `HashMap` の性質**による。
  `Counter` が加算するのは、`Counter` の性質としてむしろ自然ともいえる。
  **それでも却下したのは、`skipped` と `total` を運べないほうが重い**ため。
  こちらは慣習の解釈ではなく、**1 回の合流が 2 手順に割れるという構造の話**である
- **1b の欠点は `strict` だけか。** そうである。`counts` / `skipped` / `total` だけを
  見れば、`Counter` は真にモノイドであり、演算子が最も正確な表現になる。
  **裏を返せば、`strict` を `Counter` から外せば 1b が最善になる。**
  外す案（方針と集計状態を別の型に割る）は ADR-0005 論点 1 で
  「厳格さは消費者の方針」と決めた結果としてここにある。
  **本 ADR で覆さない** — 覆すなら ADR-0005 を supersede する新しい ADR が要る
- **1c の「総称に書けない」は将来効くか。** 効くとすれば、
  `Counter` 以外にも合流できる集計器が現れたときである。
  そのときは `merge` を持つ trait を自分で定義すればよく、
  **`Extend` を今から実装しておく必要は無い**（むしろ `Extend` は
  項目の型 `(String, u64)` を約束してしまい、後から変えられない）

### 決め手

**`strict` が `Counter` にある限り、`Counter` はモノイドではない。**
演算子（1b）はモノイドであることを記号で約束するので、
**約束と実体がずれる。** ずれは `Report` には出ないが、
`Sum` の単位元が方針を落とす形で現れる。

**`Extend`（1a）は、合流を 2 手順に割る。** `skipped` を別経路で足す実装は、
片方を忘れても型検査を通る。**忘れたことが `--stats` の出力にしか出ない。**

`merge`（1c）は糖衣が無いだけで、**間違いうる余地を作らない。**

### 決定の帰結

- **公開 API が 1 つ増える**（`Counter::merge`）。`Counter` は `Clone` を持たないので、
  `other` は消費される形になる
- **`strict` の非対称を doc に書く義務が生じる。**
  「`self` の方針を保つ」「`Report` は方針に依存しないので、
  合流の順序を変えても結果は同じ」の 2 つを書く
- **結合則と可換性はテストで担保する。** 演算子を実装しないので
  コンパイラは何も確かめない。`proptest` で
  「どう分割して合流しても `Report` が一致する」を示す
  （段階 6 の完了条件に入れた）
- 論点 2（入力 1 つぶんの集計が何を返すか）は、**`Counter` を返す形が
  成立することが確定した。** マージの手段が生えたため

## 論点 2: 入力 1 つぶんの集計が何を返すか（決定済み）

### 決定

**`tally_reader` は自由関数のまま `&mut Counter` を受け、`Result<()>` を返す。**
`limit` は引数から落ち、呼び出し側が `Counter::report(limit)` を呼ぶ。

```rust
pub fn tally_reader<R, F>(
    counter: &mut Counter,
    reader: R,
    selector: &Selector,
    keep: F,
) -> Result<()>
where
    R: BufRead,
    F: Fn(&str) -> bool;
```

**これは [ADR-0005](0005-selector-public-api.md)「実装時に決めたこと」3 が
候補として挙げ、「複数入力を 1 つの集計に合流させたくなったら見直す」と
書いて先送りした形そのものである。**

### この論点の検討のしかた（記録しておく）

**案 2b の擁護論を別のエージェントに書かせ、それを統合した。**
ADR-0005 の書き方の節が警告している偏り
（**却下案を採用案より低い精度で書く**）への対策として試した手順である。

**結果として、こちらが 2a の利点として数えていた 2 項目が落ちた**（下の「共通の利点」）。
**さらに、擁護論の事実認定を 1 件補正した** — 擁護論は
「ADR-0005 が先送りした候補は 2b（メソッド化）そのものだ」と述べたが、
ADR-0005 の記述は **`&mut Counter` を受ける形**であって、自由関数のままである。
**その差が案 2d であり、本論点の結論になった。**

### この論点に効く事実（2026-09-23 に確認）

| 事実 | 効き方 |
| --- | --- |
| `tally_reader` は `Counter` を受けて `Report` を返し、内部は `try_fold(counter, ...)` | **`Counter` を受けて `Counter` を返す形は、`&mut` の畳み込みを値の受け渡しで手書きしたもの**になる |
| `Counter::push_line` は `&mut self` を取るメソッド | 「1 行積む」と「`BufRead` 一本ぶん積む」で作法が割れている |
| `Counter::report(&self, limit)` は既に独立している | **`limit` が引数から落ちるのは論点 1 の帰結。** 案の選択とは独立 |
| `Counter` は `Clone` を持たない | 値渡しの案では、失敗時に累積が `Err` とともに落ちる |
| `Counter` 型に `#[must_use]` は付いていない（`Counter::new` には付く） | 値を返す案では、**戻り値を捨てる式文が警告なしに通る** |
| `lib.rs` が「**`tally_reader` が `BufRead` を受け取るのが唯一の I/O 境界**」と名指しし、ルートに再エクスポートしている | メソッド化すると、この名前がルートの一覧から消える |
| `push_line` の doc は「**この関数が I/O で失敗しえないため** `LineError`」（ADR-0004 論点 3） | メソッド化すると、I/O で失敗する兄弟が隣に並ぶ |
| ADR-0005「実装時に決めたこと」3 が `&mut Counter` の形を候補として記録している | **先送りの解除条件（複数入力）がいま満たされた** |

### 検討した案

`Report` がマージできない（論点 1）ので、**現状維持は選択肢に無い。**

#### 2a. `Counter` を受けて `Counter` を返す（却下）

```rust
counter = tally_reader(counter, reader, &selector, keep)?;
```

- 利点: **失敗したとき累積が手元に残らない。** 部分的に積まれた `Counter` を
  誤って `report` する経路が **型として存在しない**
- 利点: 並列版の `map` の閉包が「1 つの式で `Counter` を作って返す」形に素直に嵌まり、
  **2d・2b より 1 行短い**
- 欠点: **戻り値を黙って捨てられる。** `tally_reader(counter, r, &s, k)?;` は
  `Counter` 型の式文で、`#[must_use]` が無いので警告が出ない。
  塞ぐには `Counter` に `#[must_use]` を足す必要があり、**2a を安全にするための追加の約束**になる
- 欠点: **受け直しの綴りが要る。** `&mut` の畳み込みを値の受け渡しで書く形が、
  関数の内部だけでなく **境界にも露出する**
- 欠点: 論点 4 で「失敗した入力を飛ばして続ける」系の規則を選ぶ余地を、型で潰す

#### 2b. `Counter::push_reader` に変える（却下）

```rust
counter.push_reader(reader, &selector, keep)?;
```

- 利点: **`push_line` と `push_reader` が対になる。** 「カウンタに積む」操作が
  1 行でも `BufRead` 一本でも同じ作法になる
- 利点: 方針（`strict`）と、方針が効く操作が **同じ型の上に載る。**
  ADR-0005 論点 1 の「厳格さは消費者の方針」の到達点という読み方ができる
- 利点: 位置引数が 1 つ減る（第 1 引数がレシーバの位置へ移る）。
  現行 doc の「# `counter` を引数に取る理由」の節が不要になる
- 利点: 入力源の種類が増えたとき（`push_lines` など）、
  `impl Counter` に並び、rustdoc で 1 箇所にまとまる
- 欠点: **ルートから I/O 境界の名前が消える**（擁護論自身が最大の害と認めた点）。
  `lib.rs` は「`tally_reader` が唯一の I/O 境界」と名指ししているが、
  **「I/O に触れるのはこの関数だけ」は、クレートに関数が 1 つしかないから強い。**
  「このメソッドだけ」は、I/O に触れない兄弟 4 つの中に紛れる
- 欠点: **`impl Counter` に 2 種類のエラー型が並ぶ。**
  `push_line` は `LineError`（I/O で失敗しえない）、`push_reader` は `TallyError`。
  いまは「メソッドは純粋、自由関数が I/O」という **構文上の分類が説明を肩代わりしている**
- 欠点: `Counter` が「度数を数える型」から「行の供給源を駆動して度数を数える型」になる
- 欠点: 構築の作法が 3 種になる（`strict` は消費ビルダー、`push_*` は `&mut self`、
  `report` は `&self`）。`Counter::new().strict(true).push_reader(..)` と書けない

#### 2c. 2a と 2b を両方持つ（却下）

- 利点: 呼び出し側が好きなほうを選べる
- 欠点: **入口が 2 系統になる。** 段階 5 で `anyhow` を落とした理由
  （表現が 2 系統になると、どちらに足すかがそのつど揺れる）と同じ形

#### 2d. 自由関数のまま `&mut Counter` を受ける（採用）

```rust
tally_reader(&mut counter, reader, &selector, keep)?;
```

- 利点: **手書きの畳み込みが境界から消える**（2b と同じ）
- 利点: **戻り値が `Result<()>` なので、捨てられる値が存在しない**（2b と同じ）
- 利点: **ルートに `tally_reader` が残る。** `lib.rs` の「唯一の I/O 境界」の
  名指しがそのまま生き、rustdoc のトップページで見える（2b の最大の害を回避）
- 利点: **`Counter` に I/O で失敗するメソッドが並ばない。**
  「メソッドは純粋、自由関数が I/O」という構文上の分類が保たれ、
  `push_line` の doc の理由づけ（ADR-0004 論点 3）が読みやすいまま残る
- 利点: **ADR-0005 が記録した候補そのもの。** 先送りの解除条件を満たして解除する形になり、
  「なぜこの形か」の履歴が 1 本に繋がる
- 欠点: **位置引数は 4 つのまま。** 2b のように第 1 引数がレシーバへ移る簡潔さは無い
- 欠点: **失敗後に部分的に積まれた `Counter` が観測できる**（2b と同じ。2a だけが型で防ぐ）。
  **doc に書く義務が生じる**
- 欠点: 入力源の種類が増えたとき、ルートの名前が増える（2b なら `impl Counter` に収まる）

### 共通の利点として除外したもの

**比較の軸から落とした項目を明記する。** 検討の初期にこちらが
2a の利点として数えていたが、精査すると全案に共通だった。

| 当初 2a の利点としたもの | 実際 |
| --- | --- |
| **`limit` が引数から落ちる** | **論点 1 の帰結。** `Report` がマージできない以上、どの案でも落ちる |
| **I/O 境界が 1 箇所** | `BufRead` を受け取る項目は **どの案でも 1 つ。** 自由関数かメソッドかの差しかない |

### 対称性の検査

- **2b の「ルートから名前が消える」は doc で補えないか。**
  部分的には補える（`Counter` 型の doc の冒頭に I/O 境界を書く）。
  **しかし 2d はそもそも補う必要が無い。** 補える欠点であっても、
  **補わなくてよい案があるなら、そちらが安い**
- **2a の「失敗時に累積が残らない」は、2d に対する本物の優位である。**
  2d は「途中まで積まれた `Counter` に `report` を呼べる」余地を残す。
  これは論点 3 の対称性の検査で案 3b に認めた弱点
  （包み忘れても型検査を通る）と同じ構造であり、**2 つ目を足すことになる。**
  受け入れる根拠は 2 つ。**`tally_reader` を呼ぶ経路が `aggregate` 1 つに集約されている**
  こと（論点 3 の緩和策）と、**論点 4 が規則を決めること。**
  「1 つでも失敗したら全体を失敗にする」と決めるなら、部分的な `Counter` は
  呼び出し側に届く前に捨てられる
- **2b の利点「`push_line` と対になる」を、2d は本当に失うか。** 失う。
  `push_line` はメソッド、`tally_reader` は自由関数のままである。
  **この非対称は残る。** ただし **非対称には根拠がある** —
  片方は I/O に触れ、片方は触れない。**2b はその根拠を構文から消して doc に移す**

### 決め手

**2a は「戻り値を捨てられる」「受け直しが要る」を、追加の約束（`#[must_use]`）と
綴りで補う案である。2b は「ルートから I/O 境界が消える」「エラー型が 2 つ並ぶ」を
doc で補う案である。2d はどちらも補う必要が無い。**

**残る 2d の欠点（部分的な `Counter` の観測）は、論点 4 の決定に吸収される。**

### 決定の帰結

- **`tally_reader` のシグネチャが変わる**（引数 5 → 4、戻り値 `Result<Report>` → `Result<()>`）。
  破壊的変更だが、**1.0 以前なので受け入れる**（ADR-0004 の但し書き）
- **`limit` が `tally_reader` から消える。** 「まだ順位づけされていない」ことが型で言える
- **`tally_reader` の doc に、失敗後の `counter` の状態を書く義務が生じる**
- **`lib.rs` の「使い方」と「関心事の分け方」の表を更新する**
- 論点 5（並列化をどちらのクレートに置くか）は、**`&mut Counter` を受ける形の上で決める**

## 論点 3: 失敗にどのファイルかを持たせる場所（決定済み）

### 決定

**CLI 側で包む。同時に `TallyError::OpenInput` を `tally-core` から取り除き、
CLI へ移す。**

```rust
// crates/tally-core: 開く失敗が消える。残るのは「読めない」と「行が悪い」だけ
pub enum TallyError {
    Read(std::io::Error),
    Line(LineError),
}

// crates/tally: 入力の呼び名を持つのは、入力を開いた側
pub enum InputName { Stdin, Path(PathBuf) }

pub enum CliErrorKind {
    /// 開けなかった。**標準入力では起きない**ので `PathBuf` を直接持つ
    Open { path: PathBuf, source: io::Error },
    /// 集計に失敗した。**どの入力かを必ず持つ**
    Input { name: InputName, source: TallyError },
    Write(io::Error),
}
```

**これは [ADR-0004](0004-error-type-shape.md) 論点 1 の
`TallyError` の形と、Confirmation の判明事項 2 を置き換える。**
ADR-0004 側に `Superseded by` の指し先を書いた（[ADR-0001](0001-record-architecture-decisions.md) の手順）。

### この論点に効く事実（2026-09-23 に確認）

| 事実 | 効き方 |
| --- | --- |
| `tally-core` の不変条件は「**ファイルを開かない**」（`lib.rs` のモジュールドキュメント） | **`OpenInput` はその不変条件と既に食い違っている** |
| `OpenInput` を構築している本番コードは `crates/tally/src/main.rs` の 1 箇所（`File::open` の `map_err`） | **構築しているのは CLI だけ。** core 内に構築点が無い |
| `TallyError::Read` と `TallyError::Line` は path を持たない | 読み取り途中の失敗と行の失敗が、どの入力かを言えない |
| `LineError::line_no` は **入力ごとに 1 から数える** | path が無いと **行番号まで意味を失う**（「3 行目」がどのファイルか言えない） |
| `hint_for` は `TallyError` を受け、`OpenInput` に対して `None` を返す | `OpenInput` を移すと、この枝が CLI 側の `match` へ移る |
| 標準入力には path が無い | 「どの入力か」は `PathBuf` では表せない場合がある |

### 検討した案

#### 3a. CLI 側で包む（採用。ただし単体では二重表示が残る）

`CliErrorKind::Input { name, source: TallyError }` を足し、表示で名前を前置する。

- 利点: **core は `BufRead` しか知らないまま。** 不変条件を強めこそすれ弱めない
- 利点: 標準入力を `InputName::Stdin` として同じ型で扱える。
  **`PathBuf` を `Option` にする必要が無い**
- 欠点（**素のままの 3a**）: `OpenInput` が core に残っていると、
  「開けなかった」に名前を前置したときに **path が 2 度出る**。
  段階 5 で transparent を選んだ理由がまさにこれで、
  **`Input` で包むか否かをバリアントごとに場合分けする**羽目になる
- **→ `OpenInput` を CLI へ移すと、この欠点が消える。**
  移した先では `Open { path, .. }` が自分で path を表示し、
  `Input { name, .. }` が名前を前置する。**場合分けが型の形で消える**

#### 3b. core の `TallyError` に path を足す（却下）

`Read` と `Line` にも `path: PathBuf` を持たせ、1 つの型で自己完結させる。

- 利点: **消費者が何もしなくても、失敗が自己完結する。**
  包み忘れという失敗様式が存在しない
- 利点: `LineError` を直接受け取る文脈（ADR-0004 論点 3 の帰結）でも
  どの入力かが分かる
- 欠点: **`BufRead` しか受け取らない関数が path を要求することになる。**
  `tally_reader` の呼び出し側は、メモリ上の文字列やソケットを渡せる。
  そのとき path に何を入れるかが決まらない（`Option<PathBuf>` にすると
  「持つが空」という状態が生まれ、ADR-0004 論点 1 が排除した形に戻る）
- 欠点: **`tally-core` が `std::path` に依存する理由が無くなる。**
  `OpenInput` を移せば、core から `PathBuf` が消える
- 欠点: 行の失敗すべてに `PathBuf` が載るので、`LineError` が太る
  （ADR-0004 論点 7 で大きさを実測した経緯がある）

#### 3c. core に「入力の名前」の層を足す（却下）

`TallyError::Input { name: Box<str>, source: Box<TallyError> }` のように、
core 側で名前を預かる層を作る。

- 利点: **名前の付与が core の型で表現される。** 消費者が自前で層を作らずに済み、
  `tally` 以外の消費者（linter、連携の入り口）でも同じ形になる
- 利点: 名前が文字列なので、ファイルでもソケットでも URL でも載る
- 欠点: **`Box<TallyError>` の再帰になる。** 入れ子の深さが型で決まらず、
  「名前の層が 2 つある `TallyError`」が作れてしまう
- 欠点: **`OpenInput` の path と意味が重なる。** 同じ入力について
  path と name が別々に載りうる（3a で二重表示を嫌ったのと同じ問題が、
  型の中に移るだけ）
- 欠点: core が名前を持っても、**名前を知っているのは開いた側**である事実は変わらない。
  構築点は結局 CLI になる

### 対称性の検査

- **3b の「包み忘れが存在しない」は本当に利点か。** 利点である。
  3a は `CliErrorKind::Input` で包む責任を呼び出し側に置くので、
  **包み忘れても型検査を通る。** これは実際の弱点であり、
  採用案が 3b に負けている唯一の軸である。
  **緩和策**: 入力を開いて集計する経路を 1 つの関数に閉じ、
  そこを通らずに `tally_reader` を呼ばない形にする。
  **テストで担保する**（複数入力のどれが失敗しても path が出る）
- **3a の「core は `BufRead` しか知らない」は、実際に守られているか。**
  いまは守られていない（`OpenInput` がある）。
  **採用案はその違反を消す方向なので、この利点は「守る」ではなく「直す」である。**
  段階 5 では「同じ分類に載せるための置き場所」として意図的に残した
  （`error.rs` のドキュメントにそう書いてある）。
  **その意図は、入力が 1 つで、開く主体も 1 つだったときには成立していた**
- **`OpenInput` を移すのは破壊的変更である。** `tally-core` の公開 API から
  バリアントが 1 つ消える。**1.0 以前なので受け入れる**（ADR-0004 の但し書き）。
  ただし `TallyError` は `#[non_exhaustive]` ではない（ADR-0004 論点 2）ので、
  **消費者の `match` はコンパイルエラーになる。** 黙って壊れはしない

### 決め手

**`OpenInput` は、置き場所を間違えていた。**
構築しているのは CLI だけで、core のどこからも作られない。
**`tally-core` が「ファイルを開かない」と宣言している以上、
「開けなかった」は core の語彙ではない。**

段階 5 の transparent の判断は「path が 2 度出るのを避ける」ためだった。
**その二重は、置き場所の誤りが表示に現れたものだった。**
置き場所を直すと、表示の場合分けは書かずに済む。

### 決定の帰結

- **`tally-core` から `PathBuf` が消える**（`OpenInput` が唯一の使用箇所だった）
- **`CliErrorKind` が 2 つ増える**（`Open` と `Input`）。
  `Tally` は消える。終了コードの `match` は網羅性検査で全件洗い出される
- **`hint_for` の引数が変わる。** `OpenInput` の枝が CLI 側へ移る
- **表示が変わる。** 「`path` の集計に失敗しました: 3 行目 ...」のように、
  入力の名前が前置される。`crates/tally/docs/output-format.md` は
  **stderr の文面を契約にしていない**ので、外部契約は変わらない
- **包み忘れをテストで担保する。** 3b に負けている軸なので、
  「どの入力が失敗しても名前が出る」を統合テストで押さえる
- 論点 4（複数の失敗のどれを報告するか）は、**`CliErrorKind::Input` が
  名前を持つことを前提にできる**

## 論点 4: 複数のファイルが失敗したとき、どれを報告するか（決定済み）

### 決定

**引数順で最も左の失敗を報告し、全体を失敗にする。**
短絡しない（全入力を処理してから選ぶ）。部分的な集計は出力しない。

```rust
// 失敗は「どれか 1 つ」ではなく「引数順で最初のもの」に決める
let results: Vec<Result<Counter, CliError>> = inputs.par_iter().map(..).collect();
```

**`crates/tally/docs/output-format.md` に規則を書く**（段階 6 の完了条件）。

### この論点に効く事実（2026-09-23 に確認）

| 事実 | 出典 | 効き方 |
| --- | --- | --- |
| rayon の並列 fold は **分割点が非決定的** | `docs.rs` の `rayon::iter::TryFoldWith`（「the number of results and the points of subdivision being nondeterministic」） | 短絡に任せると、**どの失敗が返るかが実行ごとに変わりうる** |
| `try_reduce` は失敗で **早期終了する** | `docs.rs` の `ParallelIterator::try_reduce` | 速いが、上の非決定性と結びつく |
| 段階 6 の完了条件に「**引数の順序を入れ替えても出力が同じバイト列**」がある | `docs/curriculum.md` 段階 6 | 出力だけ決定的で診断が非決定的なのは、その精神と食い違う |
| 現在の契約では、失敗時の stdout は空（統合テストが `stdout("")` を検査） | `crates/tally/tests/cli.rs` | 部分結果を出す案は **外部契約の変更**になる |
| 終了コードの契約は `0` / `1` / `2` の 3 つ | `crates/tally/docs/output-format.md` | 「一部失敗」を表す 4 つ目のコードは無い |
| 未決事項 4: `--strict` は fail fast。全件報告は段階 2 で意図的に見送った | `docs/handoff.md` | 「全件報告」を採るなら、そちらと足並みを揃える判断になる |

### 検討した案

#### 4a. rayon の短絡に任せる（却下）

`try_reduce` が最初に拾った失敗をそのまま返す。

- 利点: **最も速い。** 失敗を見つけた時点で残りの仕事をやめる
- 利点: 実装が最も短い（論点 1 の `try_reduce` の形そのまま）
- 欠点: **診断が実行ごとに変わりうる。** 同じ入力で 2 回動かして
  違うファイル名が出ると、**利用者は再現を取れない。**
  報告を受ける側（CI のログ、AI のハーネス）にとっても、
  「どのファイルが最初に壊れているか」が安定しないのは扱いづらい
- 欠点: **テストが書けない。** 複数が壊れている入力に対して、
  何を assert すればよいかが決まらない

#### 4b. 引数順で最も左の失敗を報告（採用）

全入力を処理し、`Vec<Result<Counter, CliError>>` を集めてから、
**最小の添字の `Err`** を選ぶ。成功ぶんは（失敗が 1 つでもあれば）捨てる。

- 利点: **決定的。** 同じ入力なら常に同じ診断が出る。テストできる
- 利点: **引数順という利用者に見える順序**で決まる。
  「最初に壊れているファイル」という言い方が、そのまま規則になる
- 利点: **論点 2 で残した弱点が閉じる。** 部分的に積まれた `Counter` は
  選ばれないので、`report` を誤って呼ぶ経路が消える
- 欠点: **短絡しない。** 1 個目が壊れていても 1000 個読む。
  **失敗が例外的な場合には実害が小さい**が、
  「壊れた入力を弾く」用途（未決事項 4 と同じ文脈）では無駄が大きい
- 欠点: **成功ぶんの `Counter` を一時的に全部持つ。** 入力数に比例した
  メモリを要求する。`try_reduce` なら合流しながら畳める
  （**段階 6 のベンチ B4（1000 ファイル）で、この差が出るかを測れる**）

#### 4c. 全件報告してから失敗（却下）

失敗したファイルをすべて stderr に出してから終了コード 1。

- 利点: **入力の検査には最も有用。** 1 回の実行で全部の問題が分かる
- 利点: 決定的にできる（引数順に並べればよい）
- 欠点: **stderr の行数が入力数に比例する。** 1000 ファイルすべてが
  壊れていれば 1000 行出る。`--max-errors` のような歯止めが要る
- 欠点: **未決事項 4 と同じ論点を、片方だけ先に倒すことになる。**
  段階 2 は `--strict` について fail fast を選び、
  「全件報告してから失敗」を意図的に見送った。
  **行について fail fast、ファイルについて全件報告、という食い違いが生まれる**
- **この案は将来また立つ。** `--max-errors` を足すときに、
  行とファイルの両方をまとめて扱うのが筋（未決事項 4 に合流させる）

#### 4d. 失敗を飛ばして続行（却下）

読めたファイルだけで集計し、失敗は stderr に出して終了コード 1。
`cat a missing b` や `wc` の作法。

- 利点: **Unix の慣習に最も近い。** 1 つ読めないだけで全部が無駄にならない
- 利点: ログの解析のような用途では、**壊れたファイルを飛ばして集計を得たい**
  場面が実際にある
- 欠点: **部分性が結果から見えない。** `wc` はファイルごとに行を出すので
  欠落が可視だが、`tally` は **全入力を 1 つの表に畳む。**
  1 ファイル読めなかった結果と、全部読めた結果が、**出力の見た目で区別できない**
- 欠点: **終了コードを見ない利用者が、黙って誤った集計を受け取る。**
  パイプの途中（`tally *.log | head`）では終了コードが見られないことが多い
- 欠点: 現在の外部契約（失敗時の stdout は空）を変える
- **この案を採るなら、明示のフラグ（`--keep-going` など）にすべきである。**
  既定の挙動にはしない

### 対称性の検査

- **4a の「速い」は、どれだけ効くか。** 失敗経路でしか効かない。
  **成功経路の速度は 4a も 4b も同じ**であり、段階 6 のベンチが測るのは成功経路である。
  したがって「速い」は **利用者が壊れた入力を繰り返し流す場合にだけ**効く利点で、
  そのときは 4c（全件報告）のほうがそもそも有用である
- **4b の「メモリが入力数に比例する」は本当か。** する。ただし
  `Counter` 1 つは `HashMap` + 3 つの整数で、**保持するのは失敗が確定するまでの間**である。
  比較対象の `try_reduce` も、並列に走る分だけ中間 `Counter` を持つ
  （分割点の数だけ）。**差は「入力数」と「同時並列度」の差**であり、
  1000 ファイルでどれだけ効くかは **測れる**（ベンチ B4）
- **4d を「慣習に反する」として退けていないか。** 退けていない。
  退けた理由は **`tally` の出力形が `cat` / `wc` と違う**ことである。
  行ごとに出すツールでは部分性が見えるが、畳むツールでは見えない。
  **慣習は形が同じときにだけ移植できる**
- **4b は「最初に壊れているファイル」以外の失敗を隠す。** 隠す。
  2 個目以降が壊れていることは、1 個目を直すまで分からない。
  **4c が解く問題であり、4b では解けない。** `--max-errors` を足すときに再考する

### 決定の帰結

- **`output-format.md` に規則を書く**（外部契約）。
  「複数の入力が失敗した場合、**引数順で最初の失敗**を報告する」
- **部分的な集計は出力しない。** 失敗時の stdout が空である契約は変わらない
- **短絡しないので、失敗経路では全入力を処理する。**
  これは意図した代償であり、`--keep-going` や `--max-errors` を足すときに再考する
- **論点 2 の弱点（部分的に積まれた `Counter` の観測）が閉じる**
- **テストで決定性を押さえる。** 2 つ以上のファイルが壊れている入力に対して、
  **引数の順序を入れ替えると報告されるファイルが入れ替わる**ことを検査する
  （「常に同じものが出る」だけでは、規則が「引数順」であることを示せない）
