# 段階 10 を立て、リポジトリの終わりを定義する

**`status` は `accepted`**（2026-10-28）。4 論点とも案のまま実装した。
Confirmation は 7 項目すべて済み。**ただし 5 は文面を直した** — 下記。

## なぜこれを ADR にするのか

**2 つの判断が絡んでいて、片方だけでは決められない。**

1. **このリポジトリの役目をいつ終わりとするか**（`handoff.md` 未決事項 1）
2. **関連型が実コードで一度も使われていない**（同 未決事項 9、`learning-log.md` 16）

**1 は 2 に依存する。** 「段階が尽きた」と「役目を終えた」が別だと言えるのは、
**未消化の概念が残っているから**である。
**2 を消化すれば、1 の答えが変わる。**

**逆に 2 だけを単位として通すと、1 は宙に浮いたままになる。**
[ADR-0010](0010-json-pointer-key.md) は段階に属さない 1 単位として通したが、
**あれは利用者向けの機能であって、カリキュラムの終わりとは関係が無かった。**

## コンテキストと問題提起

**関連型が消化されていないのは、偶然ではない。**

`curriculum.md` 段階 3 は「**関連型 vs 型パラメータ**」を扱う概念に挙げ、
課題として `trait Formatter` への切り替えを指示していた。
**同時に「enum + match のままのほうが良い可能性も検討すること」とも書いていた。**

**検討した結果、[ADR-0002](0002-output-format-abstraction.md) は enum を選んだ。**
**カリキュラムが用意した唯一の trait を書く機会が、正しい判断によって消えた。**

その後も機会は来なかった。
[ADR-0010](0010-json-pointer-key.md) は抽出を trait に割らなかった
（「外から差し替える消費者がいない」）。
**結果として、このリポジトリには利用者が定義した trait が 1 つも無い。**
`impl FromStr for JsonPointer` の `type Err` だけが関連型だが、
**これは他人が定義した trait を実装した側であって、定義した側ではない。**

**問題はこうである** — **trait を定義する機会を、
「作らないほうがよい」という既存の判断を破らずに用意する。**

## 論点 1: 段階にするか、段階に属さない 1 単位にするか（提案）

### 決定（案）

**段階 10 として立てる。**

### 検討した案

#### 1a. 段階 10 を立てる（採用）

- 利点: **終了基準（論点 2）を書く場所ができる。**
  基準はカリキュラム水準の話で、**1 つの機能の ADR には収まらない**
- 利点: **`curriculum.md` に「予」として残る。**
  後から読む人が、段階 3 で飛ばされた概念の行き先を辿れる
- 欠点: **段階が増える。** 「段階 9 が名目上の最終段階」と
  `curriculum.md` に書いてあり、**その記述を直すことになる**

#### 1b. ADR-0010 と同じく 1 単位で通す（却下）

- 利点: **軽い。** 前例もある
- 欠点: **未決事項 1 が閉じない。** 「役目を終えた」の基準は
  **段階の外に置き場が無い**
- 欠点: **ADR-0010 との違いが説明できない。** あちらは利用者向けの機能で、
  **動機が外にあった。** 今回の動機は学習の側にしか無い

### 対称性の検査

- **「段階 9 が最終」と書いた記述を直すのは、`curriculum.md` の改竄にならないか。**
  ならない。**`curriculum.md` は予であり、予は更新される。**
  腐るのは実績を書いたときである（失敗事例 4）
- **段階を足せばいくらでも先延ばしできるのではないか。** できる。
  **だから論点 2 で基準を書く。** 基準の無い段階の追加は、この ADR では認めない

## 論点 2: 「役目を終えた」とする基準（提案）

### 決定（案）

**`curriculum.md` が各段階の「扱う概念」に挙げた概念を、
すべて実コードで消化したとき。**

**現時点で残っているのは関連型 1 つだけである。**
したがって **段階 10 を終えれば基準を満たす。**

### なぜこの形にするか

**「満足したら終わり」では閉じない。**
**基準は、2 つのファイルを読めば真偽が決まる形**でなければならない —
`curriculum.md` の「扱う概念」と、`learning-log.md` の各節である。

### 検討した案

#### 2a. カリキュラムが挙げた概念の消化（採用）

- 利点: **判定できる。** 列挙は既にあり、消化の記録も `learning-log.md` にある
- 利点: **段階の数とは独立。** 段階を足しても基準は動かない
- 欠点: **`learning-log.md` 16（未解決の論点）は閉じない。**
  `Pin` と async、NLL、GAT が残る。
  **ただしこの 4 つは `curriculum.md` に一度も出てこない** —
  **カリキュラムの外にある関心事**であり、基準に含めない
- 欠点: **「消化した」の判定に幅がある。** 1 行使えば消化かどうか

#### 2b. 段階をすべて終えたら完了（却下）

- 利点: **最も単純**
- 欠点: **2026-10-17 に実際にそうなり、それでも終われなかった。**
  **却下の根拠は経験である**

#### 2c. 利用者が付いたら完了（却下）

- 利点: **外から判定できる**
- 欠点: **学習リポジトリの目的と無関係。** 利用者は目的ではない

### 対称性の検査

- **2a の「判定に幅がある」をどう閉じるか。**
  **`learning-log.md` に節があり、その節が実コードを指していること**を条件にする。
  **16（未解決の論点）に残っているものは消化していない** —
  これは既にある区別で、新しい規則ではない
- **基準を `scripts/check-docs.sh` で検査できないか。** できない。
  **「扱う概念」の列挙と `learning-log.md` の節の対応は、
  文字列の一致では取れない**（「関連型」は節題に出ない）。
  **検査にできないものは規約として書く**という `CLAUDE.md` の原則どおり、
  **なぜ足せないかをここに書いて残す**

### 決定の帰結

- **段階 10 の完了をもって、未決事項 1 と 9 を解決済みにする**
- **基準そのものは `curriculum.md` に 1 段落で書く**（予として）。
  過程はこの ADR に残る
- **`learning-log.md` 16 は閉じない。** カリキュラムの外にある論点として残る

## 論点 3: 課題を何にするか（提案）

### 決定（案）

**入力の出どころを trait にする。** `tally` 層に次を置く。

```rust
trait Input {
    type Reader: BufRead;
    fn open(&self) -> Result<Self::Reader, CliError>;
    fn name(&self) -> InputName;
}
```

実装は 2 つ — ファイルと標準入力。

### なぜこの課題か

**「抽象化が要るから」ではない。** その理由では、このリポジトリの既存の判断に反する。
[ADR-0002](0002-output-format-abstraction.md) は `Format` を trait に割る条件を
「形式 1 つあたり概ね 20 行超、操作が 2 つ以上」と定め、
[ADR-0007](0007-multi-input-aggregation.md) 論点 5 は `Execution` の条件を
「実装が 3 つ以上、`tally` 以外の消費者、エラー型の総称化」と定めた。
**`Input` は実装 2 つ・消費者 1 つで、どちらの水準にも達しない。**

**採る理由は、重複が型の違いに由来していることである。**

`input.rs` の `tally_path` と `tally_stdin` は、
**開く部分を除いてほぼ同じ**である。`tally_reader` を呼び、
失敗に入力の名前を被せ、`Counter` を返す。
**[ADR-0007](0007-multi-input-aggregation.md) 論点 3 は
「包む責任は呼び出し側にある。包み忘れても型検査は通るので、
`tally_reader` を呼ぶ経路をこのモジュールに集約する」と書いた。**
**集約すると言いながら、関数が 2 つある。**

**1 つにできないのは `BufReader<File>` と `StdinLock<'static>` が別の型だから**であって、
方針が違うからではない。**これは抽象化の不足ではなく、型の形の問題である。**

### 対称性の検査

- **`Format` と `Execution` の条件を満たさないのに trait を作るのは、
  二重基準ではないか。** **条件の向きが違う。**
  あちらの条件は「**実装が増えたら trait にせよ**」という移行の閾値である。
  こちらは「**実装は増えないが、1 つにまとめたい**」という話で、
  **数ではなく形を理由にしている**
- **関連型を使いたいから課題を選んだのではないか。** **その順序は認めない。**
  **重複は先にある** — `tally_path` と `tally_stdin` は段階 7 から
  ほぼ同じ形で並んでいる。**関連型はその解き方の候補の 1 つ**にすぎず、
  論点 4 で他の案と並べて比べる
- **`Box<dyn BufRead>` で済むのではないか。** 済む。
  **13-7 で値段も測ってある**（雑音に埋もれた）。
  **論点 4 で正面から比べる**

### 決定の帰結

- **trait は `tally` に置く。** `tally-core` には入れない
  （`tally-core` は I/O を知らない。層の規則は `crates/tally/docs/layout.md`）
- **公開 API の約束には触れない。** [ADR-0011](0011-v0-1-0-promise.md) が
  約束を `output-format.md` と `distribution.md` に限ったので、
  **この trait は契約の外側にある**
- **退出条件を先に書く** — **実装が 1 つに減ったら enum か直書きに戻す。**
  `Format` と `Execution` に監視条件があるのに
  `Input` に無い、という状態を作らない（未決事項 2 と 12 の形を増やさない）

## 論点 4: 読み手の型をどう持つか（提案）

### 決定（案）

**関連型。** `type Reader: BufRead`。

### 検討した案

#### 4a. 関連型（採用）

```rust
trait Input { type Reader: BufRead; }
```

- 利点: **「1 つの出どころに読み手は 1 つ」が型で表れる。**
  ファイルから `StdinLock` は出てこない
- 利点: **単相化される。** 間接呼び出しが残らない
- 欠点: **呼ぶ側が `I::Reader` を書くことになる場面がある**

#### 4b. 型パラメータ `trait Input<R: BufRead>`（却下）

- 利点: **1 つの出どころが複数の読み手を持てる**
- 欠点: **その自由が要らない。** `Input<BufReader<File>>` と
  `Input<StdinLock<'static>>` を同じ型に実装できてしまう
- 欠点: **壊れる場所が、定義側ではなく使用側になる。**
  実装が 1 つのあいだは推論が通り、**2 つ目を足した瞬間に
  すべての呼び出しが `E0283` で落ちる**（下の「試作で分かったこと」）。
  **関連型なら 2 つ目の実装がそもそも書けない**

#### 4e. 関連型を 2 つにする（`type Error`）（却下）

```rust
trait Input { type Reader: BufRead; type Error: Into<CliError>; }
```

- 利点: **「標準入力を開く操作は失敗しない」が型に出る**（`type Error = Infallible`）。
  4a では決して失敗しない `Result` を返すことになる
- 欠点: **`?` が自動で包む経路が戻る。**
  [ADR-0004](0004-error-type-shape.md) 論点 6 は
  `From<TallyError> for CliError` を入れない理由として
  **「この失敗に対して利用者は何ができるか、を問う瞬間が消える」**と書いた。
  **`Into<CliError>` 境界はその瞬間を再び消す**
- 欠点: **`From<Infallible> for CliError` を `match e {}` で書くことになる**

#### 4c. `Box<dyn BufRead>`（却下）

- 利点: **最も短い。** trait すら要らず、関数 1 つで済む
- 利点: **コストは測ってある** — 13-7 で雑音に埋もれた
- 欠点: **段階の目的（trait を定義する）を果たさない**
- 欠点: **1 行ごとに仮想呼び出しが残る。** 埋もれるとはいえ、
  **消せるものを消さない理由が無い**

#### 4d. `enum Source { File(BufReader<File>), Stdin(StdinLock<'static>) }`（却下）

- 利点: **ADR-0002 と同じ形。** このリポジトリの既定の選択である
- 利点: **単相化される**
- 欠点: **開く前と開いた後が同じ型になる。**
  `enum` は「開いた結果」を持つので、**「開く」を含められない**
  （含めるなら結局 `match` が 1 つ増える）
- 欠点: **段階の目的を果たさない**

### 対称性の検査

- **4c と 4d を「段階の目的を果たさない」で却下するのは、
  学習の都合を技術の判断に混ぜていないか。** **混ぜている。**
  **そしてそれは、このリポジトリでは正当である** —
  目的は動く CLI ではなく、**Rust を習得すること**である。
  **ただし混ぜたことを書き残す。** 実務では 4c か 4d が勝つ場面がある
- **4a と 4d の差は、実測で出るか。** **おそらく出ない。**
  `reader_dispatch` ベンチ（13-7）で `Box<dyn BufRead>` の差が
  雑音に埋もれているので、**4a が 4c に勝つことも測れないはずである。**
  **測って「差が無い」ことを記録する**（Confirmation 4）

**4b の欠点は、書いていたものと違った。**
書いたのは「呼ぶ側の型引数が 1 つ増える」だったが、
**実装が 1 つのあいだは推論が通り、turbofish は要らなかった。**

## 実装して分かったこと（2026-10-28）

**Confirmation 5 の文面が、書いた時点で間違っていた。**
「公開 API が変わっていない」と書いたが、
**`pub fn tally_path` と `pub fn tally_stdin` を消すのだから、
`tally` の lib API は壊れる。** 測るとそのとおりだった。

| クレート | 結果 |
| --- | --- |
| `tally-core` | 196 検査すべて通過、58 skip。`no semver update required` |
| `tally` | **`semver requires new major version`。** 関数 2 つの削除 |

**壊れているが、約束は破っていない。**
[ADR-0011](0011-v0-1-0-promise.md) が約束を `output-format.md` と
`distribution.md` の 2 文書に限ったので、
**`tally` の Rust API は契約の外側にある**（論点 3 の決定の帰結どおり）。
**だから行は「通らなかった」ではなく、「確かめる対象を書き間違えていた」である。**
文面を直し、測った値を残した。

**4a と 4c の差は、今回も雑音に埋もれた**（load average 3.28 のホスト）。

| 組 | 静的 | 動的 |
| --- | --- | --- |
| ファイル | 4.100 ms | 4.217 ms |
| メモリ | 3.848 ms | 3.875 ms |

**最速と最遅の開きが 25% あるので、2.8% の差は読めない。**
13-7 の結論（`Box<dyn BufRead>` の値段はこの機械の雑音の下）が再現した。
**関連型を選んだ理由は速度ではない。**

**実装は newtype を挟まず `Path` と `io::Stdin` に直接当てた。**
試作は `PathInput` と `StdinInput` を置いていたが、
**孤児ルールは `Input` が自クレートにあるので満たし、
包む型を足しても意味が増えない。** 型が 2 つと寿命引数が 1 つ消えた。

**代わりに `?Sized` が要った。** `Path` は unsized なので、
ジェネリック関数の既定の `Sized` 境界に引っかかる。
**`&I` を取っているのに参照先へ境界が掛かる**のは直感に反する
（`learning-log.md` 4-14）。

**rayon の境界は問題にならなかった。** `aggregate_all` は
`Fn() -> Result<Counter, CliError> + Sync` で `Send` を要求せず、
**`I::Reader` はジョブの中で作られて中で落ちる**ので境界に届かない。
**試作では自前の `Send + Sync` 付き代役で確かめていた** — 本物のほうが緩かった。

**第 3 の呼び出し側があった。** `benches/aggregate.rs` が `tally_path` を
使っていた。`cargo c` は `--all-targets` なので型検査には出るが、
**作業の指示を書いた時点では見落としていた。**
