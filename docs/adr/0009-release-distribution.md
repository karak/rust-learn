# 配布物の形と、リリースの作り方

**`status` は `proposed`。** 4 論点すべて決定したが、
**実装と Confirmation が済んでいない。** 下の「確認方法」を参照。

## なぜこれを ADR にするのか

[ADR-0001](0001-record-architecture-decisions.md) の絞り込み条件は
「**代替案を検討した記録が価値を持つものに限る**」である。

本件が条件を満たすのは 2 つの理由による。

1. **配布物は外部の契約である。** 一度公開したら、ファイル名・アーカイブの構造・
   同梱物が利用者の手順に焼き付く。**出力形式と同じ重さを持つ**
   （[ADR-0003](0003-csv-output-contract.md) が CSV にしたのと同じ）
2. **既存の道具（`cargo dist`）を採らない判断を含む。**
   [ADR-0008](0008-container-push-credentials.md) と同じく、
   **足さないと決めた記録のほうが失われやすい。**
   数ヶ月後に「`cargo dist` を使えばよかったのに」と思ったとき、ここが答えになる

**運用の手順（どう叩くか）は `README.md`、配布物の契約は
`crates/tally/docs/output-format.md` が正本。** ここには書かない。

## コンテキストと問題提起

段階 8 までは **「自分の機械で動く」ところまでしか扱っていない。**
配布は **他人の機械で動く**ことを要求するので、
**これまで暗黙だった前提が表に出る** — libc の版、シェルの種類、
man ページを置く場所。

### 現状の事実（2026-10-11〜12 に確認）

| 事実 | 確認方法 |
| --- | --- |
| **タグが 1 本だけある。`adr-0002-baseline`** | `git tag` |
| **版を表すタグは 1 本も無い** | 同上。`cargo-semver-checks` の baseline が取れない理由がこれ |
| `tally` の版は `0.1.0`、まだ公開していない | `crates/tally/Cargo.toml` |
| **CI は 4 ジョブ。リリースに関わるものは無い** | `.github/workflows/ci.yml` |
| **`tally` は位置引数で入力ファイルを可変個取る** | `crates/tally/src/cli.rs` の `inputs: Vec<PathBuf>` |
| サブコマンドは 1 つも無い | 同上 |
| `cargo-dist` は保守されている。**ただし最新版が crates.io に無い** | GitHub は `v0.33.0`（2026-09-11）、crates.io の最新は `0.32.0`（2026-05-22） |
| `cargo-dist` のリポジトリは活発。**直近 30 コミットの 18 件は依存更新** | GitHub API。人の手による変更も 2026-09 まである |
| `clap_complete` 4.6.11 / `clap_mangen` 0.3.3。どちらも clap 本体のリポジトリ | crates.io API |

### `cargo dist` が隠すものが、この段階の学習対象そのものである

段階 9 の扱う概念は **クロスコンパイルと静的リンク**である。
`cargo dist` はそこを設定 1 行に畳む。**道具としては正しいが、
畳まれた中身がこの段階の課題である。**

**これは「道具を使うな」という話ではない。**
`nextest` も `insta` も `divan` も使っている。
**違いは、それらが隠すものを学習対象にしていない**ことである。

## 論点の分割

| # | 論点 | なぜ分けるか |
| --- | --- | --- |
| 1 | リリースの仕組みを誰が書くか | 道具の採否。他の 3 つと独立に決まる |
| 2 | 補完と man ページをどこで生成するか | **CLI の表面に触れうる。** 他の論点と違い、利用者の叩き方が変わる |
| 3 | 版とタグの扱い | 誰が引き金を引くか。ADR-0008 と整合する必要がある |
| 4 | 段階の完了に「実際の公開」を含めるか | **取り消しにくい行為の範囲。** 技術的な話ではない |

## 論点 1: リリースの仕組みを誰が書くか（決定済み）

### 決定

**`.github/workflows/release.yml` を手で書く。`cargo dist` は採らない。**

### 検討した案

#### 1a. `cargo dist` に生成させる（却下）

- 利点: インストーラスクリプト、checksum、`cargo dist plan` による事前確認、
  ターゲット追加が設定 1 行。**失敗しやすい箇所を全部踏み終えた実装**が手に入る
- 欠点: **生成物が正本になる。** `release.yml` を手で直すと次の生成で消える。
  **段階 9 の学習対象（クロスコンパイルと静的リンク）が設定に畳まれる**
- 欠点: **最新版が crates.io に無い**（`0.33.0` は GitHub のみ）。
  `cargo install` で入るのは 1 つ前の版になる。
  **道具の入手経路が 2 つに割れる**のは、固定したい環境では負債になる

#### 1b. 手で書く（採用）

- 利点: **全工程が 1 ファイルで見える。** `rustup target add` から
  `tar` の組み立てまで、どの行が何をしているか読める
- 利点: **道具を 1 つ増やさない。** 未決事項 15（道具がリポジトリに固定されていない）を
  これ以上太らせない
- 欠点: **インストーラスクリプトと自動更新を持たない。** 利用者は
  アーカイブを展開して自分で置く
- 欠点: **自分で踏む。** musl の静的リンク、macOS の署名なしバイナリの扱い、
  アーカイブのパーミッション — どれも `cargo dist` が既に解いている問題である

#### 1c. `cargo dist` に生成させ、読んでから手書きに落とす（却下）

- 利点: **学習量は最大。** 「正しい実装」を先に見られる
- 欠点: **工程が 1 つ増えるだけで、成果物は 1b と同じ**になる
- 欠点: **生成物を読んで書き写すと、理解しないまま形だけ真似る危険がある。**
  段階 7 で「プロファイルで上位にあるものを置き換えても速くならない」を
  踏んだのと同じ形 — **出力を信じて中身を確かめない**

### 対称性の検査

**却下した案の欠点を、採用案と同じ精度で疑う**（ADR-0005 の書き方に従う）。

- **1a の「生成物が正本になる」は本当に欠点か。**
  `scripts/setup-git-secrets.sh` も生成的だが問題になっていない。
  **違いは、あちらは「自分が書いた正本」でこちらは「道具が書く」**こと。
  さらに **CLAUDE.md は生成物の中の行を承認なしで書き換えてよいと定めている** —
  つまり生成物であること自体は許容されている。
  **それでも却下したのは、学習対象が畳まれるほうが重い**ためである
- **1a の「最新版が crates.io に無い」は決め手になるか。** ならない。
  単独なら「0.32.0 を使う」で済む。**副次的な根拠として挙げるにとどめる**
- **1b の「自分で踏む」は、学習として望ましいのか。**
  **踏むこと自体に価値があるとは限らない。** 署名や公証は学習対象ではなく、
  ただ面倒なだけである。**だから macOS の署名はしない**（下の帰結）。
  **踏むと決めたのは、静的リンクとクロスコンパイルに限る**
- **1c の「形だけ真似る」は、読み方次第で避けられないか。** 避けられる。
  ただし **避けられたかどうかを自分では判定できない。**
  1b なら「動かない」が即座に跳ね返るので、**理解したかの検査が工程に組み込まれる**

### 決め手

**学習対象が畳まれるかどうか。** `cargo dist` の利点はすべて
「失敗を代わりに踏んでくれる」ことだが、
**段階 9 の課題は、その失敗を踏むことである。**

### 決定の帰結

- `.github/workflows/release.yml` を手で書く
- **インストーラスクリプトは作らない。** `README.md` に
  「アーカイブを展開して PATH の通った場所に置く」と書く
- **macOS バイナリの署名・公証はしない。** 学習対象ではない。
  **代わりに「初回起動で Gatekeeper に止められる」ことを `README.md` に書く**
- **`cargo dist` に移る条件を書いておく** —
  利用者が現れて「入れ方が面倒」と言われたとき、
  または対応ターゲットが 4 つを超えたとき。
  **そのときは本 ADR を supersede する新しい ADR を書く**

## 論点 2: 補完と man ページをどこで生成するか（決定済み）

### 決定

**ワークスペース内に生成専用のバイナリを置き、リリース時にだけ走らせる。**
**`tally` 本体の CLI 表面は変えない。**

### この論点に効く事実（2026-10-12 に実測）

**`tally` に `completions` サブコマンドを足すと、
`completions` という名前のファイルが引数で渡せなくなる。**

clap 4.6.6 で、`inputs: Vec<PathBuf>`（可変個の位置引数）と
`completions` サブコマンドを同居させた最小例を作って確かめた。

| 叩き方 | 結果 |
| --- | --- |
| `prog completions bash` | サブコマンドとして解釈される |
| **`prog completions`**（ファイルとして渡したい） | **`MissingRequiredArgument <SHELL>` で失敗** |
| `prog -- completions` | 位置引数として通る |
| `prog a.log b.log` | 位置引数として通る |

**2 行目が問題である。** 利用者から見ると
「`completions` というファイルを集計しようとしたら、
シェルの名前を要求された」という**無関係な診断**が出る。
**「ファイルが無い」でも「それはサブコマンドです」でもない。**

### 検討した案

#### 2a. `tally completions <shell>` / `tally man` サブコマンド（却下）

- 利点: **利用者がいつでも再生成できる。** 版とずれない
- 利点: パッケージャが扱いやすい。配布物に補完を含めなくてよい
- 欠点: **上の実測のとおり、位置引数と衝突する。**
  `completions` / `man` という名前のファイルが `--` なしで渡せなくなる
- 欠点: **CLI の形が変わる。** いま `tally` はフラグだけの道具である。
  サブコマンドを持つと `--help` の構造が変わり、**これは外部の契約の変更**になる

#### 2b. `build.rs` でビルド時に生成（却下）

- 利点: clap 公式の例がこの形。生成が必ずビルドに追随する
- 欠点: **成果物が `OUT_DIR` に出る。** 場所が
  `target/release/build/tally-<hash>/out/` になり、
  **ワークフローから拾うのに hash を探す手間がかかる**
- 欠点: **全利用者のビルドに `build.rs` が乗る。**
  `cargo install tally` する人は補完を使わないかもしれないのに、
  **毎回生成が走る**
- 欠点: **`clap_complete` が通常の依存になる。**
  いまワークスペースの依存は用途が明確なものだけで構成されている

#### 2c. 生成専用のバイナリを置き、リリース時にだけ走らせる（採用）

- 利点: **`tally` の CLI 表面を変えない。** 2a の衝突が起きない
- 利点: **利用者のビルドに何も乗らない。** `clap_complete` と `clap_mangen` は
  生成器だけの依存にできる
- 利点: **成果物の置き場所を自分で決められる。** `OUT_DIR` を探さない
- 欠点: **生成器が `Cli` 型を見る必要がある。** `tally` の `Cli` は
  現在ライブラリ側にあるので届くが、**依存の向きが 1 本増える**
- 欠点: **利用者が再生成できない。** 配布物に入っているものを使うしかない

### 対称性の検査

- **2a の衝突は、本当に実害があるか。** `completions` や `man` という名前の
  ログファイルは珍しい。**しかし珍しさは根拠にならない** —
  段階 7 で `str::trim_ascii` の垂直タブを「珍しい」で流さずテストを残したのと同じ形。
  **さらに悪いのは診断が無関係になること**で、利用者は原因に辿り着けない
- **2a の「CLI の形が変わる」は、足す方向だから互換ではないか。**
  `crates/tally/docs/output-format.md` は
  「**緩める方向は互換、厳しくする方向は破壊的**」と定めている。
  サブコマンドの追加は **一見「緩める」だが、実際には
  `completions` という引数の意味を変える**ので厳しくする側に入る
- **2b の「全利用者のビルドに乗る」は、実際どれだけの負荷か。** 小さい。
  生成は数ミリ秒である。**却下の主たる理由は `OUT_DIR` の取り出しにくさ**で、
  ビルド負荷は副次的な根拠にとどめる
- **2c の「利用者が再生成できない」は欠点として重いか。**
  **重くない。** 補完と man は版ごとに固定でよく、
  利用者が手元で作り直す理由は薄い。
  **ただし配布物に入れ忘れると誰も気づかない** — Confirmation で見る
- **2c の「依存の向きが 1 本増える」は層の規則に触れないか。**
  触れる。`scripts/check-module-deps.sh` の層の表に、
  **生成器がどの層を見てよいかを足す必要がある**（下の帰結）

### 決め手

**利用者の叩き方を変えないこと。** 2a だけが CLI の契約を動かし、
**その代償として無関係な診断を生む。** 2b と 2c は契約を動かさず、
**その中では成果物を拾いやすい 2c が勝つ。**

### 決定の帰結

- 生成専用のバイナリをワークスペースに置く。**`tally` の CLI は変えない**
- **`clap_complete` と `clap_mangen` は生成器だけの依存にする。**
  `cargo tree -p tally` に出ないことを確かめる
- **層の規則に生成器を足す。** 生成器は `tally` の `Cli` を見てよいが、
  **逆向きは禁じる**（`tally` が生成器を見ない）
- **サブコマンドを足す条件を書いておく** —
  `tally` が `completions` 以外にもサブコマンドを必要とする機能を得たとき。
  そのときは位置引数との衝突を**まとめて**設計し直す

## 論点 3: 版とタグの扱い（決定済み）

### 決定

**`v` 接頭辞つきのタグ（`v0.1.0`）の push を引き金にする。
タグはホストから打つ。`Cargo.toml` の版とタグの一致を CI で検査する。**

### 検討した案

#### 3a. タグ push を引き金にする（採用）

- 利点: **[ADR-0008](0008-container-push-credentials.md) と整合する。**
  push はホストから行うと決めてあり、**タグも push である**
- 利点: **「その版の中身」が git で決まる。** タグが指すコミットが答えになる
- 利点: **`cargo-semver-checks` の baseline が自然に生まれる**（未決事項 6）
- 欠点: **打ち間違えると取り消しにくい。** タグを消すのは汚い
- 欠点: **ドライランの経路が無い。** 試すたびに本番のタグが要る

#### 3b. `workflow_dispatch` で版を入力する（却下）

- 利点: **何度でも試せる。** タグを汚さない
- 欠点: **「その版の中身」が決まらない。** 同じ版で 2 回走らせたとき、
  どちらが正しいか git から読めない
- 欠点: **ADR-0008 の「push はホストから」と無関係な経路を作る。**
  GitHub の UI から引けるので、**どこから引いたかが記録に残りにくい**

#### 3c. 両方入れる（却下）

- 利点: 本番とドライランが分かれる
- 欠点: **分岐が増え、ドライラン側だけ腐る。**
  CLAUDE.md の失敗事例 1（同じ事実を 2 箇所に書くと片方が腐る）と同じ形
- 欠点: **`workflow_dispatch` が「タグなしで公開できる」抜け道になる**

### 対称性の検査

- **3a の「ドライランの経路が無い」は本当か。** 正確ではない。
  **プレリリースのタグ（`v0.1.0-rc.1`）が使える。**
  タグは増えるが、**本番の版を汚さない。**
  この経路があるので、3c の利点は 3a に吸収される
- **3b の「版の中身が決まらない」は、入力に SHA を足せば解けないか。** 解ける。
  **しかしそれは「タグを手で再発明する」ことである。**
  git が既に持っている機能を引数で再現する形になる
- **3c の「抜け道になる」は、権限で閉じられないか。** 閉じられる。
  **ただしこのリポジトリは 1 人で使っている**ので、権限で閉じる意味が薄い。
  **分岐が腐るほうが現実的な危険である**

### 決め手

**git が既に持っている「版の中身」の表現を使うこと。**
3b は同じものを引数で再発明し、3a はそれを使う。
**ドライランはプレリリースのタグで足りる。**

### 決定の帰結

- タグの形は `v<semver>`。`v0.1.0`、`v0.1.0-rc.1`
- **タグはホストから打つ。** コンテナからは打たない（ADR-0008）
- **`Cargo.toml` の版とタグの一致を、ワークフローの最初で検査する。**
  **ずれていたら落とす** — ずれたまま公開すると、
  `--version` の出力とダウンロード元の版が食い違う
- **既存の `adr-0002-baseline` タグとは形が違う。** 版のタグは `v` で始まる。
  **`v` の有無で機械的に区別できる**

## 論点 4: 段階の完了に「実際の公開」を含めるか（決定済み）

### 決定

**含めない。** ワークフローを作り、**タグを打たずに**検証して段階 9 を終える。
**公開するかどうかは、別の回に学習者が決める。**

### なぜこれを論点にするか

**技術的な判断ではない。** 取り消しにくい行為の範囲を決めるものである。

### 検討した案

#### 4a. 公開しない（採用）

- 利点: **取り消しにくい行為を、段階の完了条件に入れない。**
  完了のために公開を急ぐ構造を作らない
- 利点: **公開の判断を、仕組みの検証から切り離せる**
- 欠点: **全経路を通さずに「できた」と言うことになる。**
  タグ push の引き金だけは確かめられない
- 欠点: **`cargo-semver-checks` の baseline が生まれない**（未決事項 6 が残る）

#### 4b. `v0.1.0` を公開する（却下）

- 利点: **全経路が通る。** baseline も生まれる
- 欠点: **公開物が世に出る。** Releases は消せるが、
  **タグを消すのは汚く、一度でも誰かが取得したら取り消せない**
- 欠点: **「学習リポジトリの v0.1.0」が何を約束するのかを決めていない。**
  論点 1〜3 は配布物の形を決めたが、**どこまで互換を保つかは決めていない**

#### 4c. プレリリースで 1 度通す（却下。ただし条件つきで復活しうる）

- 利点: **全経路が通り、正式版の名前を使わない**
- 欠点: **`-rc.1` も公開物である。** 4b の欠点が小さくなるだけで消えない
- 欠点: **baseline にはならない**（プレリリースは比較の基準に向かない）

### 対称性の検査

- **4a の「全経路を通さない」は、段階 7 の教訓に反しないか。**
  反する側面がある。段階 7 は「検出されなかったことを安全の根拠にしない」と学んだ。
  **タグ push の引き金は、通していないので動く保証が無い。**
  **これは Confirmation に「未実施」として明記する** — 済んだことにしない
- **4b の「何を約束するか決めていない」は、決めればよいのではないか。**
  決められる。**しかしそれは本 ADR の 4 論点とは別の判断**であり、
  **配布の仕組みを作る作業に混ぜると、どちらも粗くなる**
- **4c は 4a より厳密ではないか。** 厳密である。
  **`-rc.1` を公開してよいなら 4c が最善である。**
  却下したのは「今回は公開しない」という学習者の判断によるもので、
  **技術的な優劣ではない。** 公開してよいと決まれば 4c が復活する

### 決め手

**学習者の判断。** 技術的には 4c が最も厳密だが、
**取り消しにくい行為の範囲は学習者が決めるものである。**

### 決定の帰結

- 段階 9 の完了に公開を含めない
- **タグ push の引き金が未検証であることを、Confirmation に残す。**
  「動くはず」と書かない
- **未決事項 6（`cargo-semver-checks` の baseline）は解けないまま残る**
- **4c に移る条件** — 学習者が公開してよいと決めたとき。
  **ADR を書き換えるのではなく、Confirmation の未実施項目を埋める**

### 未検証のまま残るもの（3 件）

**論点 4 の帰結である。** 「動くはず」と書かない。

1. **musl の静的リンク**（確認 1）— macOS からはビルドできない
2. **別ジョブでバイナリだけ受け取って動かす経路**（確認 3 の前半）
3. **タグ push がワークフローを引くこと**（確認 10）—
   `version` ジョブ以降のすべてが、この 1 点に乗っている

### 実装時に決めたこと（本 ADR が形を指定していなかった項目）

1. **生成器の名前を `xtask` にした。** 論点 2 は「生成専用のバイナリ」と
   決めただけで、名前と置き場所を決めていなかった。
   **Rust の慣習に合わせた**（ワークスペースのメンバとしてビルド道具を置く形）。
   用途は補完と man の生成だけに限っている
2. **補完は 4 シェルに限った。** `clap_complete::Shell` の全要素ではない。
   **全部入れると「どのシェルを約束したか」が曖昧になる**ため、明示的に並べた
3. **`LICENSE` を置いた。** `Cargo.toml` が `license = "MIT"` を宣言していたのに
   **本文が無かった。** 配布物に入れるので、宣言と中身が食い違わないようにした。
   **著作権表示は学習者が決めた**（2026-10-12）
4. **配布物の契約を `crates/tally/docs/distribution.md` に分けた。**
   本 ADR は「`output-format.md` か、そこから指された文書」としていた。
   **アーカイブの構造は「出力」ではない**ので、分けて指すだけにした

5. **プレリリースを打つ手順を書いていなかった。** 論点 3 は
   「タグと `Cargo.toml` の版が一致する」とだけ決め、
   **一致させる手順を決めていなかった。**
   `v0.1.0-rc.1` を打つには `Cargo.toml` を `0.1.0-rc.1` に上げる必要があり、
   **さらに `xtask` の `tally` 依存の `version` も直す必要がある**
   （プレリリースは `0.1.0` の要求に一致しない。`learning-log.md` 15-5）。
   手順は `docs/handoff.md` の側に置いた（状態と再開手順であるため）

### 実装中に自分のバグを 1 件出した

**ワークフローの smoke テストに、間違った期待値を書いた。**
CSV の出力を `key,count` のヘッダつきだと思い込んでいたが、
**実際の契約は `件数,キー` でヘッダを出さない**（ADR-0003）。

**手順を手で実行したから見つかった。** YAML を書いて push しただけなら、
**タグを打つまで誰も気づかなかった** — そして論点 4 でタグを打たないので、
**「検証していない期待値」がリポジトリに残っていた。**
