# `Selector` と `Key` の公開 API

**論点ごとに、扱うときに案と評価を書き足していく文書である。**
未着手の論点には「効く事実」だけが置かれている。

## この文書の書き方（先に宣言する）

**案と pros/cons は、論点を 1 つずつ扱うときに、そのつど書き足す。**
着手時点でまとめて書かない。理由は 2 つある。

1. **粗くなる。** 5 論点分の案を一度に並べると、どれも掘りが浅くなる
2. **偏る。** [2026-08-17 の振り返り](../journal/2026-08-17.md)に記録したとおり、
   ADR-0004 で **却下案のコード片から要素を 2 つ落として書き**、
   採用案の売り文句が成立しない状態を作った。
   これは段階 3 の「**退ける案の欠点を疑わなかった**」の 2 回目である。
   **案を先に書き溜めると、この偏りが検出されないまま蓄積する**

**したがって: 1 論点を扱うとき、その論点の案だけを書く。**
書いたら、却下案の記述を採用案と同じ精度で書き直してみる（振り返りの Try 2）。

## コンテキストと問題提起

段階 5 で集計コアを `tally-core` として切り出す。
**`Selector` と `Key` は、切り出した時点で公開 API になる。**

**前提は [ADR-0004](0004-error-type-shape.md) の「前提」節と共有する。**
ここには複製しない。要点だけ:

- 決定は `tally` 個体にではなく、**この設計を基に作る各種ツール**に対して下す
- 判断の基準は「いまこの規模で必要か」ではなく
  **「中規模の実務ツールで公開 API だったときの定石はどうか」**
- **1.0 以前は破壊的変更を受け入れる**

**本 ADR を段階 5 の着手前に置く理由**は、`#[non_exhaustive]` の後付けが
破壊的変更である（Cargo Book `attr-adding-non-exhaustive`）ためだった。
**ただし論点 2 で非公開フィールドを採ったので、この理由は消えた。**
それでも切り出しと同時に形を決めるほうが安いことは変わらない。

### 現状の事実（2026-08-17 に確認）

**接点はすべて 1 箇所ずつ。** どの案を選んでも本番コードの変更は小さい。
**判断は「どれが安いか」ではなく「どれが正しいか」で行う。**

| 事実 | 場所 |
| --- | --- |
| `strict` を読んでいる本番コードは 1 箇所 | `crates/tally/src/core.rs:160`（`Selector::select` の中） |
| `select` を呼んでいる本番コードは 1 箇所 | `crates/tally/src/core.rs:214`（`Counter::push_line`） |
| `Selector` を構築している本番コードは 1 箇所 | `crates/tally/src/cli.rs:87`（`Cli::selector()`） |
| `Selector` の derive | `Debug, Clone, PartialEq, Eq`（`core.rs:141`） |
| `Key` は `pub enum`、`Selector.key` も `pub` | `core.rs:14`, `core.rs:143` |

**取り消した事実**: 当初「`strict` を外すと呼び出し側が `MissingField` を
組み立てられない（情報が分かれない）」と書いたが、**誤りだった。**
`Key` も `Selector.key` も公開されており、`line` と `line_no` は
`push_line` が持っている。**必要な情報はすべて呼び出し側の手元にある。**
`docs/curriculum.md` 段階 5 にも同じ誤りを書いたので取り消した。

## 論点の分割

**5 論点はすべて独立に決められる**（下の訂正を参照）。

## 論点 1: `strict` は `Selector` に属するか（決定済み）

**問い**: 「キーを取り出せなかったときエラーにするか」は、
**抽出器の性質**か、**呼び出し側の方針**か。

### 決定

**`Selector` から外し、`Counter` が持つ（1b）。**

### この論点に効く事実

- `Selector` の doc は境界をこう定めている（`core.rs:136-140`） —
  入れてよいのは「**参加する行がどうキーを産むか**」であり、
  「**どの行が参加するか**」はパイプライン側
- `strict` は**そのどちらでもない**。「産まなかったときどうするか」である
- 段階 2 の実装記録（`docs/curriculum.md`）は、`strict` を `Selector` に畳んだ結果
  **`select` の呼び出し側を 1 箇所も変えずに済んだ**と記録している
- **`Option` は既に「値が取れた / 取れなかった」を表している。**
  `strict` を外しても `select` の戻り値の型は変わらない
  （当初この論点が論点 5 に影響すると見ていたが、**見立てが誤っていた**）

### 検討した案

| | 1a. `Selector` が持つ（現状） | 1b. `Counter` が持つ（採用） | 1c. 呼び出しごとに渡す |
| --- | --- | --- | --- |
| `strict` の置き場所 | `Selector` のフィールド | `Counter` のフィールド | `push_line` の引数 |
| 判断する場所 | `Selector::select` | `Counter::push_line` | `Counter::push_line` |
| `Selector` のフィールド数 | 3 | 2 | 2 |
| `Counter::new` | 引数なし | `new(strict: bool)` | 引数なし |
| `tally_reader` の引数 | 4 | **5** | **5** |

#### 1a. `Selector` が持つ（現状）

* Good, because 変更ゼロ
* Good, because 設定が 1 つの型に集まり、CLI から `Selector` を作れば渡すものが 1 つで済む
* Bad, because **`Selector` の doc が自ら定めた境界に当てはまらない**（上記の事実 2 点目）
* Bad, because `select` に**防御的な `match` が要る**（`core.rs:159-166`）。
  `Key` の全バリアントを列挙し「`WholeLine` はここに来ない」と注記している

#### 1b. `Counter` が持つ（採用）

* Good, because **`select` から防御的な `match` が丸ごと消える。**
  `let ... else { return Ok(None) }` の 1 行になる
* Good, because **`Key` に変種が増えても、欠損の扱いが自動的に正しい。**
  `None` は一律「取り出せなかった」なので、新しい変種に対して書き忘れる余地が無い
* Good, because **`skipped` を数えているのは `Counter` であり、
  `strict` は「`skipped` を許すか」と同義。** 概念の置き場所として自然
* Bad, because **`tally_reader` の引数が 4 → 5 になる。**
  設定が 2 経路（`Selector` と `strict`）に分かれる
* Bad, because `Counter` は `#[derive(Default)]` しているので、
  **`new(strict)` と `Default` が食い違う**
* Bad, because `push_line` がエラーを組み立てるのに
  **フィールド名を取る手段が要る**（`Key::field_name()` 相当か、`Counter` 内での `match`）

#### 1c. 呼び出しごとに渡す

* Good, because 1b の Good のうち上 2 つを同じく得る
* Good, because `Counter` に状態が増えず、`Default` との食い違いも起きない
* Bad, because **`push_line(selector, line, line_no, strict)` が読めない。** 裸の `bool` が並ぶ
* Bad, because 呼び出しごとに渡せるのに、**実際は全行で同じ値**。自由が意味を持たない
* Bad, because 1b と同じく引数が増え、フィールド名を取る手段も要る

### 対称性の検査

**却下する案を、採用する案と同じ精度で書き直した**（[2026-08-17 の振り返り](../journal/2026-08-17.md)の Try 2）。
その結果、**1a について書き足すべき事実が見つかった。**

1a の Bad に挙げた「防御的な `match`」は、コメント（`core.rs:155-158`）によれば
**意図的な設計**である。

> `_` を使わず全バリアントを書いているのは、`Key` に変種が増えたときに
> **黙って `strict` が無視される** のを防ぐため

つまり 1a はこれを**欠点ではなく利点**として設計している。
**ただしこの利点は 1b では不要になる。**
`None` が一律に「取り出せなかった」を意味するなら、無視される余地が無いため。

**1a は「変種が増えたら思い出させる」機構、1b は「変種が増えても間違えない」構造。**
後者のほうが強い保証である。**この対比が決め手になった。**

### 決め手

1. **`Selector` の doc が自ら定めた境界に、`strict` は当てはまらない。**
   段階 2 でここに置いたのは、当時 `select` の呼び出し側を変えずに済むという
   **実装の都合**だった。公開 API を確定させる今が、都合と設計を分ける機会
2. **1a の「思い出させる機構」は 1b では不要になる。**
   防御が要らなくなるのは、防御を維持するより良い

### 決定の帰結

- **`Selector` は「どこからどう取るか」だけの型になる。**
  doc に書いた境界と実体が一致する
- **`tally_reader` の引数が 5 本になる。** これを許容する。
  「設定をまとめる型を作る」は別の判断であり、本 ADR では扱わない
- `Counter::new` が引数を取るので、**`Default` derive との関係を実装時に決める**
  （`Default` を外すか、`new()` を別に残すか）
- **`Key` からフィールド名を取る手段を足す。** 公開 API が 1 つ増える

### 訂正: 当初書いた「判断が変わる条件」は誤りだった

**当初こう書いた。**

> `strict` を `Counter` に置くと、**数えない利用者は欠損の方針を持てない。**
> `Counter` を経由しない `select` の利用者が現れたら、この決定を再検討する。

**これは誤り。** 「取り出せなかったときどうするか」は、
**`select` を使う者が必ず決めなければならない問い**である。
`Selector` に置けば **全消費者に 1 つの答えを強制する**ことになる。
各消費者が自分の方針を持つのが正しい。

**消費者が増えるほど 1b が正しくなる。**
射程を広げた前提（[ADR-0004](0004-error-type-shape.md) の「前提」節）のもとでは、
この決定は**弱まるどころか強まる。**

残る代償は「各消費者が同じ 3 行を書く」という軽い重複だけであり、
これは受け入れる。

## 論点 2: `Selector` の構築と可変性（決定済み・2 軸に分割した）

**当初この論点を「構築をどう制御するか」の 1 軸として立てたが、
直交する 2 つを混ぜていた。** 分けて扱う。

| | **軸 A: 構築の制御** | **軸 B: 可変性** |
| --- | --- | --- |
| 問い | 外部にリテラル構築を許すか | 所有者による書き換えを許すか |
| 手段 | `#[non_exhaustive]` の有無 | フィールドの非公開化 + `self` を消費する更新 |
| 効く相手 | フィールド追加時の破壊性 | 構築後の不変条件の維持 |

### 軸 A に効く事実

- **後から `#[non_exhaustive]` を付けるのは破壊的変更。** 切り出し前が最後の機会
- `#[non_exhaustive]` を構造体に付けると、外部からリテラル構築ができなくなり、
  **更新構文（`..base` / `..Default::default()`）も使えなくなる**
  （lang-team#143 で緩和が議論中だが未実施）
- **クレート内部からは従来どおりリテラルで書ける。** 既存のテストヘルパ
  （`core.rs:310` の `sel` ほか）は無修正で通る
- **切り出し後、`cli.rs` は `tally-core` にとって外部になる。**
  `#[non_exhaustive]` を付けると `cli.rs:87` のリテラル構築が書けなくなり、
  コンストラクタの整備が選択肢ではなく前提条件になる
- ADR-0004 で整理した軸: **「誰がその型を使い、閉じることで何を得るか」で決める。**
  `Selector` は**構築される**型なので、`#[non_exhaustive]` が奪うのは
  リテラル構築であって網羅性検査ではない

### 軸 B に効く事実

- **`Selector` は既に事実上イミュータブル**（2026-08-17 に確認）。
  `select` は `&self` を取り、構築後に書き換えている箇所は本番・テストとも無い
- **Rust にはフィールドを不変と宣言する手段が無い。**
  OCaml のレコード（既定で不変）、Scala の `val`、C# の `readonly`/`init`、
  Java の `final` に相当するものが無く、
  `pub` フィールドは所有者が `mut` 束縛を持てば書き換えられる
- **代わりに借用規則が同じ役目を果たす。** `&T` を渡した時点で
  受け手に書き換える手段は無い（内部可変性を持たない型に限る）。
  **型を封じることで追加で得られるのは「所有者自身による書き換えの禁止」だけ**
- **`Selector` に現在いかなる不変条件も無い。** 単なる設定レコードである
- 既存コードは値と状態を**受け取り方で書き分けている** —
  `Selector::select(&self)` と `Counter::push_line(&mut self)`

### 決定

**軸 B で B2（非公開フィールド + ビルダー）を採る。軸 A は自動的に解決する。**

```rust
#[derive(Debug, Clone, PartialEq, Eq)]
pub struct Selector {
    key: Key,
    ignore_case: bool,
}

impl Selector {
    /// 既定は大小を区別する。
    pub fn new(key: Key) -> Self { Self { key, ignore_case: false } }

    /// 大文字小文字を区別せずに集計する。
    #[must_use]
    pub fn ignore_case(mut self, yes: bool) -> Self { self.ignore_case = yes; self }

    pub fn key(&self) -> &Key { &self.key }
}
```

**`#[non_exhaustive]` は付けない。冗長だから。**

### 軸の答えは独立しない — B2 は A1 を包含する

`#[non_exhaustive]` が与える利益（フィールド追加が非破壊）は、
**フィールドを非公開にした時点で自動的に手に入る。**

| 変更 | 判定 | Cargo Book の節 |
| --- | --- | --- |
| **非公開フィールドが既に 1 つ以上ある**構造体にフィールドを足す | **MINOR** | `struct-private-fields-with-private` |
| 全フィールドが `pub` の構造体に非公開フィールドを足す | MAJOR | `struct-add-private-field-when-public` |

非公開フィールドが 1 つでもあれば外部からリテラル構築できないので、
**`#[non_exhaustive]` を付ける意味が無くなる。**
これは `#[non_exhaustive]` 以前に使われていた `_priv: ()` イディオムと同じ論理である。

**したがって実質的な選択肢は 4 通りではなく 3 通りだった。**

| 組み合わせ | 実質 |
| --- | --- |
| A2 × B1 | 現状（全 `pub`、属性なし） |
| A1 × B1 | `#[non_exhaustive]` + `pub` フィールド |
| **B2**（A の値は無関係） | 非公開フィールド + アクセサ。**A1 を付けても冗長** |

### 検討した案

#### A2 × B1. 現状維持（全 `pub`、属性なし）（却下）

* Good, because 追加コードがゼロ
* Good, because **リテラルがフィールド名を明示するので自己文書的**
* Bad, because **フィールドを足すと `cli.rs` とテストの `sel` が壊れる**
* Bad, because 入口が rustdoc に現れない
* Bad, because **表現の選択を固定する。** Rust API ガイドライン C-STRUCT-PRIVATE:
  「フィールドを公開するのは強い約束である。表現の選択を固定し、
  型が検証や不変条件を維持することを妨げる」

#### A1 × B1. `#[non_exhaustive]` + `pub` フィールド（却下）

* Good, because フィールド追加が非破壊になる
* Good, because **`cli.rs` の 5 行の構築が 1 行になり、読みやすくなる**
* Bad, because **`cli.rs` がリテラルを書けなくなる。**
  切り出し後、`cli.rs` は `tally-core` にとって外部になるため。
  コンストラクタ整備が選択肢ではなく前提条件になる
* Bad, because 外部で更新構文が使えない
* Bad, because **B2 を採れば同じ利益が得られるうえ、B2 の利益は得られない。**
  この案が B2 に勝る点が無い

#### B2. 非公開フィールド + ビルダー（採用）

* Good, because **フィールド追加が非破壊**（A1 の利益を包含する）
* Good, because **設定源が複数段（CLI + 設定ファイル + API ペイロード）なので、
  部分適用とマージがビルダーで自然に表現できる**
* Good, because 将来の不変条件に対して**唯一の入口が確保される**
* Good, because 表現を隠せる。後で内部形式を変えても外部に影響しない
* Good, because **主要クレートの設定型がこの形**
  （`clap::Command`、`regex::RegexBuilder`、`csv::ReaderBuilder`）
* Bad, because メソッドが増える（`new` / `ignore_case` / `key` の 3 つ）。
  **うち `new` は A1 でも必要なので、B2 固有の増分は 2 つ**
* Bad, because **`Counter::push_line` が `selector.key` を読む。**
  同一モジュールなら非公開でも届くが、`tally-core` でモジュールを分けるなら
  `pub(crate)` かアクセサ経由になる

### 対称性の検査

**今回の危険は、早い段階で口頭合意した A1 を不当に不利に書くことだった。**
A1 の Good を書き直したところ、**「`cli.rs` の 5 行が 1 行になる」を
Bad 側にだけ数えていた**ことが分かったので、両側に数え直した。

逆に **B2 の Bad を過大に書いていないか**も確認した。
「メソッドが 4 つ増える」と当初書いたが、**`new` は A1 でも必要**なので
B2 固有の増分は 2 つである。訂正した。

### 決め手

**射程を広げた前提（[ADR-0004](0004-error-type-shape.md) の「前提」節）で結論が変わった。**

当初は「投機で設計を重くしない」を根拠に A2 × B1 を推した。
しかし **その基準は案件規模が小さいため常に「不要」を返し、
軽量かつ粗雑な方向にしか倒れない。**

新しい基準（**中規模の実務ツールでライブラリの公開 API だったときの定石**）で見ると:

1. **`Selector` はフィールドが増える型である**ことが、投機ではなく既定路線になった
   （linter のルールが増えれば正規化オプションが増える）
2. **設定源が複数段**なので、部分適用とマージの手段が要る
3. **設定型を非公開フィールド + ビルダーで組むのは Rust の定石**であり、
   API ガイドラインも主要クレートもその形

### 決定の帰結

- **`cli.rs` の構築が `Selector::new(key).ignore_case(flag)` になる。**
  5 行が 1 行になり、読みやすくなる
- **テストヘルパ `sel` / `sel_ci` がビルダー経由に変わる。**
  構造体更新構文（`..sel(key)`）は使えなくなるが、
  `sel_ci` は `sel(key).ignore_case(true)` と書けるので**むしろ短くなる**
- **ゲッタは要るぶんだけ足す。** `key()` は `push_line` と外部消費者が要る。
  `ignore_case` の読み取りは現在誰も必要としないので置かない（**後から足すのは非破壊**）
- **ビルダーメソッド名とゲッタ名が衝突する。**
  `ignore_case(bool) -> Self` を採ったので、
  読み取りが必要になったら `ignores_case()` のような別名にする
- **`#[non_exhaustive]` は付けない。** 非公開フィールドで同じ利益が得られるため

---

**なお「イミュータブルを既定の設計指針とするか」は repo 全体の規約であり、
本 ADR の範囲外。** `crates/tally/docs/layout.md` は
**クレート固有のコード配置ルール**なので、そこは正本にならない。
置き場所は `CLAUDE.md` の「文書の書き分け」に従って決める。

**この方向は 2026-08-17 に見送りとした。** 一律に不変を課すと
`Counter` のような蓄積する型と衝突し、標準ライブラリの流儀
（`Vec::push` / `String::push_str` / `HashMap::entry`）とも合わないため。
**軸 B は `Selector` 固有の判断として扱う。**

## 論点 3: `Key` の拡張余地をどう扱うか（決定済み・2 軸に分割した）

**問い**: `Key` にバリアントが増えることを想定するか。想定するなら何を約束するか。

**論点 2 と同じく、直交する 2 軸がある。**

| | **軸 C: 判別を外部に許すか** | **軸 D: ペイロードの型を約束するか** |
| --- | --- | --- |
| 問い | 外部が `match Key` を網羅的に書けるか | `JsonField` の中身が `String` だと約束するか |
| 手段 | `#[non_exhaustive]` / 不透明化 | バリアントを newtype で包む |
| 効く相手 | **バリアント追加**時の破壊性 | **表現変更**時の破壊性 |

**2 軸に分ける理由**は、拡張候補が**どちらの軸にも当たり得る**からである。
JSONPath は「新しいバリアント」（軸 C）にも
「`JsonField` の `String` を路径式に格上げ」（軸 D）にもなり得る。
1 軸で見ると片方を見落とす。

### 決定

**軸 C は 3b（`#[non_exhaustive] pub enum`）、軸 D は D1（`JsonField(String)` のまま）。**

```rust
/// 各行からどの値を取り出すか。**バリアントは今後増える**（軸 C）
#[non_exhaustive]
#[derive(Debug, Clone, PartialEq, Eq)]
pub enum Key {
    WholeLine,
    /// 中身は `String` のまま。**newtype で包まない**（軸 D）
    JsonField(String),
}
```

### この論点に効く事実（2026-08-17 に確認）

- **`Key` は構築される型でもあり、判別される型でもある。**
  CLI が構築し（`cli.rs:79-80`）、`extract`（`core.rs:31`）と
  `select`（`core.rs:156-165`）が `match` する。
  論点 2 の `Selector`（構築されるだけ）とは圧力の向きが違う
- **ただし `select` の `match` は論点 1b で消える。**
  決定後に残る本番の `match` は `extract` の 1 箇所だけになる
- **`Key` を構築しているテストは 20 箇所以上ある**（`core.rs` の各テストと
  `cli.rs:109,116,140`）。構築側を変える案は、ここに機械的な変更を要求する
- **`Key` は `Serialize` / `Deserialize` を derive していない**（`core.rs:13`）。
  derive は `Debug, Clone, PartialEq, Eq` の 4 つ
- **`serde` は derive 機能つきで既に依存にある**（`Cargo.toml:18`）。
  射程の回答は設定源を「CLI 引数 + 設定ファイル + API ペイロード」としており、
  **`Key` は遠からず `Deserialize` を要求される**
- `core.rs:155-158` のコメントは、**`Key` に変種が増えたら `select` が
  コンパイルエラーになることを意図的に頼りにしている**と明言している。
  **`#[non_exhaustive]` は定義元クレート内では無効なので、この検査は保たれる**
- **enum のバリアントのフィールドは常に公開である。** 非公開にする構文が無い
  （C#/Java の sealed クラス階層や Scala の case class なら、
  サブクラス側でフィールドを private にできる）。
  **したがってペイロードを制御する唯一の手段は、ペイロードの型自体を不透明にすること。**
  軸 D が newtype の話にしかならないのはこのため

### 軸 C の検討した案

#### 3a. 現状維持（開いた `pub enum`）（却下）

* Good, because 外部が網羅的に `match` でき、**バリアント追加をコンパイルエラーで知れる**
* Good, because `Deserialize` を derive したときそのまま効く
* Bad, because **バリアント追加が MAJOR**（Cargo Book `enum-variant-new`）
* Bad, because 拡張候補が既に見えている型で、破壊を既定路線にしている

#### 3b. `#[non_exhaustive] pub enum`（採用）

* Good, because **バリアント追加が MINOR** になる
* Good, because **構築側は何も変わらない。**
  `#[non_exhaustive]` を enum に付けてもバリアントは外部から構築できる
  （構造体に付けた場合と違い、`cli.rs` もテストも無修正）
* Good, because **定義元クレート内では無効なので、`extract` の網羅性検査は保たれる**
* Bad, because 外部の `match` に `_ =>` が要る。**外部は網羅性を失う**
* Bad, because `Deserialize` を derive しても、**未知のバリアント名は実行時エラーにしかならない**。
  型で守れる範囲は変わらない

#### 3c. 不透明化（`pub struct Key(KeyKind)` + コンストラクタ）（却下）

* Good, because 軸 C と軸 D を**同時に閉じる**。中の表現を完全に変えられる
* Good, because 論点 2 の `Selector` と**形が揃う**
* Good, because 検証の置き場所が構築時に一本化される
* Bad, because 外部が一切覗けない。
  「どのキーで集計したか」をレポートに出す用途で**新しい API が毎回要る**
* Bad, because **`Key` は本質的に直和であり、その構造は外部仕様そのものである。**
  `Selector` は積（設定レコード）で表現の選択が実装都合だったが、
  `Key` の直和は `output-format.md` が扱う `--json-field` の対応物にあたる
* Bad, because `Deserialize` を手書きすることになる
  （**ただしこの Bad は下の「対称性の検査」で不当と判定した**）

### 軸 D の検討した案

#### D1. `JsonField(String)` のまま（採用）

* Good, because 追加コードがゼロ。構築が `Key::JsonField(name)` のまま
* Good, because `Deserialize` を derive したときそのまま効く
* Bad, because **`String` を外部仕様として固定する。**
  `JsonField` の中身の格上げとして拡張が来たら MAJOR
* Bad, because **空文字列を受け付ける。**
  現状 `value.get("")` は `None` を返すので黙ってスキップになる

#### D2a. 透過な newtype、serde の derive は付けない（却下）

* Good, because 内部表現を後から変えられる
* Good, because 第三者の路径型が来ても**公開依存にならない**（ADR-0004 論点 4 と同じ論理）
* Good, because 検証の置き場所が確保され、D3 へ非破壊で進める入口になる
* Bad, because 構築サイトが変わる（本番 1 + テスト 20 箇所以上）。
  **ただしコンストラクタに寄せれば短くなるので、これは軽い**
* Bad, because **守る対象（中身の格上げ）が、調査の結果ほぼ起きないと分かった**（下記）

#### D2b. newtype + `#[serde(transparent)]`（選択肢として立たない）

**`Key` 自身が `Deserialize` を持たない以上、`FieldName` 単体の実装は誰も呼べない。
現時点では死んだコードである。**

さらに **D2a → D2b は非破壊**であり、後から無償で手に入る。

- トレイト実装の追加は原則 MINOR
- **孤児ルールにより、下流が `FieldName` に `Deserialize` を実装することはできない**ので衝突も起きない
- **`#[serde(transparent)]` を後から付けたときのワイヤ形式は、
  `String` を直接持っていた場合と同一**（`"lvl"` のまま）

**したがって D2b はロックインを何も生まない。「いま derive するか、要るときにするか」の差しかない。**

#### D3. 検証つき newtype（`try_from` / `new -> Result`）（却下）

* Good, because D2a の利益に加えて**空フィールド名を型で弾ける**
* Bad, because **設定の失敗という、いま未定義の分類を開くことになる。**
  ADR-0004 が決めた `LineError` は行の失敗であって別系統
* Bad, because **空フィールド名を弾くべきかがまだ決まっていない。**
  「そのフィールドを持つ行が無い」と区別する意味があるかは未検証

### 決め手: 拡張手段を調べたら、軸 D の守備範囲が空だった

**「JSON の情報量を上げる」には二段あり、DX と設計インパクトが違う。**

#### 段 1: JSON Pointer — 依存ゼロで手に入る

`serde_json` に既に入っている（`Value::pointer`、RFC 6901）。

```rust
pub fn pointer(&self, pointer: &str) -> Option<&Value>
```

- **戻り値が 0..1 で、いまの `extract` と同じ。** シグネチャも `Counter` も無変更
- **新しい依存が要らない**（クレート選定スキルの手順 1 に該当）
- ただし **先頭が `/` でないと無条件に `None` を返す。**
  綴り間違いが「フィールドが無い行」と区別できず、黙ってスキップになる

**そして `pointer` は先頭 `/` を要求するので、`JsonField("lvl")` と
`JsonPointer("/lvl")` は意味が違い、互換に畳めない。**
すなわち **`JsonField` の中身の格上げではなく、新バリアントとして来る。**

#### 段 2: JSONPath — 集計モデルが変わるので本 ADR の範囲外

| | jsonpath-rust 1.0.8 | serde_json_path 0.7.2 |
| --- | --- | --- |
| 直接依存 | `pest` `pest_derive` `regex` `serde_json` `thiserror` | `nom` `inventory` `serde` `serde_json` + 自前 2 + `thiserror` |
| 最終更新 | 2026-08-01 | 2025-02-03 |
| 準拠 | 独自（XPath 由来） | RFC 9535 準拠を掲げる |

**採否以前に、JSONPath は `Key` の論点ではない。**

1. **戻り値が 0..n になる。** 公式例は `$.shop.orders[?(@.active)].id` に `[1,4]` を返す。
   **1 行が複数のキーを産む**ので、`extract` の戻り値、
   `Counter::push_line` の「1 行 = 1 カウント」、`skipped` の意味、
   `Report` の合計と行数の関係が変わり、
   **`crates/tally/docs/output-format.md` の外部契約に触れる**
2. **行ごとにパースはできないので、コンパイル済みクエリを `Key` が持つことになる。**
   すると `Key` の `PartialEq, Eq` derive が壊れる可能性が高い。
   `crates/tally/docs/layout.md` に記録済みの
   「`Regex` は `PartialEq` を実装せず derive も壊れる」と同型（**論点 4 で扱う**）

**採用するなら別 ADR が要る。**

#### 結論

**現実的な拡張（JSON Pointer）は新バリアントとして来る。
それは軸 C の 3b が既に非破壊にした形であり、軸 D は要らない。**

軸 D の残る利益は「検証の入口」だが、**それは新バリアント側の話である。**
JSON Pointer を足すなら「先頭が `/` でない」を黙って `None` にするのは
受け入れがたいので `JsonPointer(PointerExpr)` のような検証つき newtype が要る。
**しかしそれは、既存の `JsonField(String)` を今 newtype で包む理由にはならない。**

### 対称性の検査

**却下する案を、採用する案と同じ精度で書き直した。2 件の不整合が見つかった。**

1. **`Deserialize` の扱いが案によって逆だった。**
   D2b を却下する根拠に「`Key` が `Deserialize` を持たないので死んだコード」を使いながら、
   3c の Bad には「`Deserialize` を手書きすることになる」を実コストとして数えていた。
   **同じ仮定の上で、片方は「まだ無いから利益は無い」、
   もう片方は「いずれ来るからコストになる」と扱っていた。**
   3c の当該 Bad は不当なので取り消した。
   **ただし 3c の却下は変わらない。** 決め手は直和構造が外部仕様であることと、
   3b が既にバリアント追加を非破壊にしていることであって、`Deserialize` ではない
2. **D2 を推した当初の決め手が、調査で消えた。**
   「`#[serde(transparent)]` はワイヤ形式を固定したまま Rust 型の自由を買う」と書いたが、
   **後から無償で手に入るものは、いま払う理由にならない。**
   根拠を「意味論的に新バリアントで来るはず」から
   **「調べた結果、`pointer` の先頭 `/` 要求により互換に畳めない」**へ置き換えた

### 決定の帰結

- **`Key` に `#[non_exhaustive]` を付ける。**
  構築側（`cli.rs`、テスト 20 箇所以上）は無修正
- **外部の `match Key` に `_ =>` が要る。** これを受け入れる。
  射程の回答「拡張は in-tree のみ」により、外部は主に構築側であるため
- **`extract` の網羅性検査は保たれる。** 定義元クレート内では属性が無効なため
- **`JsonField(String)` は変えない。** newtype で包まない
- **`Key::JsonPointer` を足すなら、そのバリアントには検証つき newtype を検討する。**
  本 ADR では決めない
- **JSONPath は別 ADR。** 集計モデル（1 行 = 1 カウント）と
  `output-format.md` の外部契約に触れるため

## 論点 4: derive をどこまで公開の約束にするか（未着手）

**問い**: `PartialEq` / `Eq` を公開 API の約束として持ち続けるか。

**この論点に効く事実**:

- `crates/tally/docs/layout.md` に既に記載がある —
  「`Regex` は `PartialEq` を実装せず derive も壊れる」。
  **将来フィールドを足すときの制約になっている**
- `cli.rs:138` のテストが `assert_eq!(cli.selector(), Selector { .. })` を使うが、
  **これはクレート内なので `#[non_exhaustive]` でも動く。**
  外部に `PartialEq` を約束する必要があるかは別問題
- Rust API ガイドラインは「共通トレイトは積極的に実装せよ」（C-COMMON-TRAITS）
  と述べるが、**実装した時点で将来のフィールドを制約する**
- **論点 3 で同型の問題が `Key` 側にも見つかった。**
  JSONPath を採るならコンパイル済みクエリを `Key` が持つことになり、
  `Key` の `PartialEq, Eq` derive が壊れる可能性が高い。
  **jsonpath-rust / serde_json_path の解析済み型の derive は未確認。**
  本論点で確かめる
- **論点 2 で `Selector` のフィールドを非公開にした。**
  外部はリテラル比較を書けないので、`PartialEq` を公開の約束にする意味が変わる可能性がある

**案と評価は、この論点を扱うときに書く。**

## 論点 5: `select` の戻り値の形（決定済み）

**問い**: `Result<Option<Cow<'_, str>>>` という現在の形を保つか。

### 決定

**外から見える形は変えない。不変条件の一元化は内部で行う。**

1. **`LineError::new(line_no, line, kind)` を作り、抜粋の生成をそこへ集約する**
2. **`Key::extract`（非公開）は `LineErrorKind` を返す。**
   `Selector::select` が 1 回だけ文脈を付ける
3. **`Counter::push_line` の `MissingField` も同じコンストラクタを通す**

`Selector::select` のシグネチャは変えない。

```rust
pub fn select<'a>(&self, line: &'a str, line_no: usize)
    -> Result<Option<Cow<'a, str>>, LineError>
```

### この論点に効く事実

- **論点 1 の決定はこの形を変えない。** `Option` が既に
  「値が取れた / 取れなかった」を表しており、
  `strict` を `Counter` へ移しても意味は変わらない
- **ただし `None` の読み手が変わる。** これまでは `strict` が有効なら
  `None` が呼び出し側に届かなかったが、今後は常に届く。
  **`None` の意味を doc で明示する必要がある**
- 戻り値の型は [ADR-0004](0004-error-type-shape.md) の論点 3 でも触れており、
  そちらは **エラー型を `LineError` に絞る**という決定を済ませている。
  **本論点は成功側（`Option` の意味）の話であり、重複しない**
- **`snippet` は非公開**（`core.rs:121`）。その doc は
  「必要になるまで surface を広げない」と明記している
- **`Key::extract` も非公開**（`core.rs:30`）。ここを変えても外部に出ない
- エラーの発生地点は 3 つ:
  `extract` の `InvalidJson`（`core.rs:35`）、
  `extract` の `UnsupportedFieldType`（`core.rs:47`）、
  `push_line` の `MissingField`（論点 1b の帰結）

### 検討した案

#### 5a. 外から見える形を変えない（採用）

* Good, because **呼び出し側の構文が変わらない。** `?` を書くだけでよい
* Good, because **公開範囲を広げなくてよい**（`snippet` を非公開のままにできる）
* Good, because 戻り値に現れる公開エラー型が 1 つで済む
* Bad, because **`Selector::select` が「入力の何行目か」を受け取り続ける。**
  抽出そのものには不要な知識で、論点 1 で `strict` を外した理由と同じ形の混入が残る

**不変条件の一元化は、この案の内側で達成できる**（上記の決定 1〜3）。
5a を採ることと、不変条件が散らばることは**別の話である**。

#### 5b. 位置を外し、呼び出し側に文脈を付けさせる（却下）

```rust
pub fn select<'a>(&self, line: &'a str) -> Result<Option<Cow<'a, str>>, LineErrorKind>
```

* Good, because **`Selector` が位置を知らなくなる。** 論点 1 と論拠が一致する
* Bad, because **呼び出し側が `map_err` を書くことになる。**
  公開 API は利用者のものであり、内部の純粋さのために利用者の構文を重くする
* Bad, because **`snippet` か `LineError::new` を公開しないと成立しない。**
  外部の呼び出し側は抜粋を作る手段を持たない。
  `snippet` の doc に記録された「必要になるまで surface を広げない」に反する
* Bad, because 戻り値に現れる公開エラー型が 2 つになる

### 検討中に訂正した自分の誤りが 2 件

**いずれも 5b を有利に見せる向きの誤りだった。**

1. **「5b なら `LineError` の構築が 1 箇所になる」は誤り。**
   `MissingField` は `push_line` が別に組み立てるので、**5b でも 2 箇所**。
   数え直したのは、5a 側を同じ精度で書き直したとき
2. **「5b の代償は `map_err` の 1 行だけ」も誤り。**
   `snippet` が非公開である以上、**公開範囲の拡大が必須**。
   これは記録済みの方針と衝突する、はるかに重い代償

**今日 3 度目の「推す案に有利な数え方」である**
（[振り返り](../journal/2026-08-17.md)の Problem 2 と同型）。

### 重さの比較

| | 5a 現状 | **5a + 一元化（採用）** | 5b |
| --- | --- | --- | --- |
| 外部の呼び出し構文 | 変化なし | **変化なし** | **`map_err` が要る** |
| 外部に公開が必要なもの | — | **なし** | **`snippet` か `LineError::new`** |
| 戻り値に現れる公開エラー型 | 1 | **1** | **2** |
| 抜粋を計算する箇所 | 3 | **1** | **1** |
| `LineError` を構築する箇所 | 3 | **2** | **2** |
| `extract` が位置を知るか | 知る | **知らない** | 知らない |
| `select` が位置を知るか | 知る | 知る | **知らない** |

**5b が最後まで残す利点は最下行の 1 つだけ。**
その対価が「外部に `map_err` を書かせる」と「公開範囲を広げる」。

### 決め手

**5b が主張していた機構上の利得は、すべて 5a の内側で得られる。**
抜粋の一元化も、不変条件の一元管理も、抽出の位置非依存も。

残る差は `select` が `line_no` を受け取り続ける点だけであり、
**これはエラーに文脈を付けるためであることが実装 1 行で明示される。**
doc に書けば足りる。

**公開 API は利用者のものである。** 内部の純粋さのために
利用者の構文を重くする取引は、この規模では見合わない。

### 決定の帰結

- **`LineError::new` を作る。** 抜粋の生成規則がここ 1 箇所になる
- **`Key::extract` から `line_no` 引数が消える。** 抽出そのものは位置を知らない
- **`select` の doc に `None` の意味を明示する。**
  論点 1b により `None` が常に呼び出し側へ届くようになるため
- **[ADR-0004](0004-error-type-shape.md) の論点 1 の帰結を訂正する。**
  「抜粋の生成箇所が増える」は偽になる（`LineError::new` に集約されるため）
