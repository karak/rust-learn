# 学びを本にするフェーズを立てる

**`status` は `proposed`。** 8 論点とも案である。
Confirmation は 1 件も済んでいない。

## なぜこれを ADR にするのか

**このリポジトリの役目は、2026-10-28 に一度終わっている。**
[ADR-0012](0012-stage-10-associated-types.md) 論点 2 が終了基準を定め、
段階 10 でそれを満たした。`docs/handoff.md` の「次の作業」は **無い** と書いてある。

その handoff は、続ける場合の条件も書いている —
**「やることが思いつくから足す」ではなく、基準をどう変えるのかを先に書くこと。**
これはその文書である。

**ただし、今回は段階を足すのではない。** 学ぶ側を続けるのではなく、
**学んだものを他人に渡す側に回る。** 基準そのものが入れ替わる。

**判断の過程に価値がある。** 置き場所・ビルダ・読み手・章の軸・コードの置き方は、
どれも後から変えると全章に波及する。
**しかも検討の記録が無ければ、数ヶ月後に「なぜ tally の実装順で書かなかったのか」を
再発明することになる**（`CLAUDE.md` の失敗事例 2 と同じ形）。

---

## コンテキストと問題提起

**このリポジトリは、学びを 3 種類の文書に分けて持っている。**

| 文書 | 持っているもの |
| --- | --- |
| `docs/curriculum.md` | 何をどう学ぶか（予） |
| `docs/stage-log.md` | 実際にやったら何が起きたか（実） |
| `docs/learning-log.md` | 言語の性質と他言語との差分 |

**どれも読み手が自分（と Claude）である。** 前提知識は
`.claude/learner-profile.local.md` に置いてあり、追跡対象外である。
**`learning-log.md` は「差分」しか書いていない** — 共通部分をなぞらないという
`CLAUDE.md` の方針が効いているので、**前提を共有しない人間には読めない。**

**問題はこうである** — **この 3 文書が持っている内容を、
前提を共有しない人間が自分で辿れる形に作り直す。**

辿れるとは、読むだけでなく **手を動かして確かめられる**ことを指す。
だから本はハンズオンであり、`tally` が題材になる。

## 論点 1: どこに置くか（提案）

### 決定（案）

**同じリポジトリの `book/` に置く。**

**あわせて、文書の検査の対象から `book/` を外す仕組みを作る** —
リポジトリ直下に `.docscheckignore` を置き、
`scripts/check-docs.sh` と `scripts/check-module-deps.sh` の両方が読む。

### 検討した案

#### 1a. 同じリポジトリの `book/`（採用）

**題材のコードと本文が同じコミットに入る。** `tally` を直したのに
本の説明が古いままになる、が構造的に起きにくい。

**費用は検査の衝突である。** `scripts/check-docs.sh` は
`git ls-files '*.md'` で全 Markdown を舐めるので、
**本の原稿が「文書の書き分け」の検査に掛かる。**
本は `docs/` の規律とは別の規律で書かれるので、これは誤検知になる。

**だから除外設定を作る。** 両方の検査スクリプトが同じファイルを読む形にすれば、
**除外の理由が 1 箇所に集まる**（`CLAUDE.md`「規約ではなく検査にする」の
延長。除外もまた規約なので、ファイルに書いて機械に読ませる）。

#### 1b. 別リポジトリ（却下）

**検査の衝突は起きない。** 本のリポジトリには本の規律だけを置ける。

**却下の理由は、題材が分かれること。** 本は `tally` を動かしながら読む。
別リポジトリにすると、**読者は 2 つを clone し、版を合わせる**必要がある。
**`tally` の版と本の版がずれたときに気づく仕組みが無い。**

#### 1c. `docs/` の下（却下）

**`docs/` は「同じ事実を 2 箇所に書かない」が効いている場所である。**
本はその事実を **意図的に書き直したもの**なので、同居させると
「どちらが正本か」が毎回問題になる。**ディレクトリを分けて、
本は正本ではないと宣言するほうが安い。**

## 論点 2: 何でビルドするか（提案）

### 決定（案）

**Docusaurus を使う。**

### 検討した案

#### 2a. Docusaurus（採用）

**Node と npm が要る。** 依存の数は mdBook より桁で多い。
生成物は静的 HTML なので、GitHub Pages への配置は同じ。

**採った理由は、書く側の慣れである。** これは技術的優位ではない。
**学習者が使い慣れており、迷いなく書けることを優先した。**

#### 2b. mdBook（却下）

**Rust 製で、このリポジトリのツールチェーンだけで完結する。**
Rust の本を Rust の道具で作るのは筋が通っており、**Claude はこちらを薦めた。**

**却下は学習者の選択による。** 慣れの差が、書き続けられるかどうかに効く。
**本は書き上がらなければ価値が 0 なので、この軸を優先した。**

#### 2c. 手書きの静的サイト生成（却下）

**本を書く作業が、サイト生成器を書く作業に化ける。**
`CLAUDE.md`「規約ではなく検査にする」と同じ理由で既製品を採る。

## 論点 3: 誰に向けて書くか（提案）

### 決定（案）

**実務経験のある中堅のプログラマに向ける。**

| 前提する | 前提しない |
| --- | --- |
| 仕事でコードを書いて届けた経験 | 体系的な言語理論の知識 |
| C++ を実務で触ったことがある | テンプレートメタプログラミングや規格の細部 |
| 変数・制御構文・関数・型の一般論 | 複数パラダイムの横断的な理解 |
| Git / CI / テストの一般論 | 型クラス、HKT、変性といった語彙 |

### 検討した案

#### 3a. `CLAUDE.md` の読み手をそのまま使う（却下）

`CLAUDE.md` の「説明の方針」は、**C#/Java/Scala の型システムを引き合いに出せる**
読み手を前提している。孤児ルールを「Scala の型クラスに近い」で済ませている。

**却下の理由は、母数が小さいこと。** その前提を満たす読者には、
**そもそもこの本は要らない**（差分だけを読めばよく、それは `learning-log.md` にある）。

#### 3b. C++ の実務経験だけを前提に落とす（採用）

**C++ の実務経験は残す。** メモリ・所有権・生存期間の説明は
C++ を第一軸にするのが最も情報量が多い、という `CLAUDE.md` の判断は変えない。

**落とすのは知識の体系性である。** 「テックリードから中堅の職業プログラマへ」。
`const T&` と `T&` は知っているが、**変性や型クラスという語は知らない**読者を想定する。

**帰結**: 型システムの語彙は、使う前にその場で説明する。
Scala や C# との対比は、**対比そのものが説明になる場合にだけ**使う。

#### 3c. プログラミング初学者まで落とす（却下）

**題材が持たない。** `tally` は CLI ツールであり、
並列化・エラー設計・契約文書まで含んでいる。
**初学者向けに書き直すと、題材を捨てることになる。**

## 論点 4: 章をどの軸で並べるか（提案）

### 決定（案）

**言語機能を軸にする。`tally` の実装順序には従わない。**
**並べ方の基準は「学びの階段の落差を最小にすること」。**

### 章の構成（案）

| 部 | 章 | 扱う機能 |
| --- | --- | --- |
| I 値 | 1 | 所有権と move |
| | 2 | 借用（`&T` / `&mut T`） |
| | 3 | `String` と `&str`、スライス |
| II 型で表す | 4 | enum と網羅的な `match` |
| | 5 | `Result` と `?`、`Option` との違い |
| | 6 | 構造体・メソッド・可視性 |
| III 抽象 | 7 | コレクションと順序 |
| | 8 | イテレータとクロージャ |
| | 9 | trait と境界、単相化と `dyn` |
| | 10 | ライフタイム注釈 |
| IV 外へ | 11 | エラー型の設計と公開 API |
| | 12 | 並列化とその前提（`Send` / `Sync`） |

**`serde` と `clap` には章を立てない。** 4 章と 9 章の素材として出す。
**クレートの使い方は言語機能ではない**ので、軸に乗らない。

**性能と配布は付録にする。** 面白いが、**言語機能の階段から外れている。**

### 検討した案

#### 4a. `tally` の実装順序に従う（却下）

**段階 0 から 10 までの順序をそのまま章にする。**
`stage-log.md` がそのまま目次になるので、書くのが最も安い。

**却下の理由は、階段の落差が制御できないこと。**
段階 2 は `Selector` の設計（trait を採らない判断）で、
段階 3 は trait の検討である。**実装の都合で決まった順序は、
学ぶ側の難易度順とは関係が無い。**

**しかも実装順は「正しい判断の記録」であって「教材」ではない** —
`CLAUDE.md` の失敗事例 4 が、まさにこの混同で起きている
（カリキュラムに実績を書くと、実績が教義として読まれる）。

#### 4b. 言語機能の軸（採用）

**落差を最小にできる。** 所有権 → 借用 → `&str` と進めば、
各章が 1 つだけ新しいことを要求する。

**費用は、`tally` のコードを章の順に切り直す手間である。**
どの章でも `tally` の一部を見せるが、**見せる順序は実装順ではない。**

#### 4c. ライフタイムを早く出す（却下）

借用の直後（3 章あたり）にライフタイム注釈を置く案。
**「借用を説明したのだから、その寿命も説明すべき」**という筋は通る。

**却下の理由は、省略規則が効いてしまうこと。**
9 章までのコードは **ライフタイム注釈を 1 つも書かずに通る。**
**必要の無い記法を先に教えると、読者は「いつ書くのか」を学べない。**
**10 章で、省略が効かない例に当たってから出す。**

## 論点 5: 章のコードをどう置くか（提案）

### 決定（案）

**章ごとに独立した小さなクレートにし、ワークスペースのメンバにする。**
置き場所は `book/code/chNN`。

### 検討した案

#### 5a. 章ごとに独立したクレート（採用）

**既存の `cargo c` が全章を型検査する。** `members` に足すだけで、
**本のコードが壊れたら CI が落ちる**（`CLAUDE.md`「規約ではなく検査にする」）。

**章をまたいで積み上げない。** 7 章のコードは 6 章のコードに依存しない。
**章を飛ばした読者が詰まらないためである。**

**費用は重複である。** 似たコードが章ごとに現れる。
**これは意図的に払う** — 動く全体は `crates/tally` のほうであり、
**本のコードは「その章だけで読み切れること」を優先する。**

#### 5b. 1 つのクレートに全章のモジュールを置く（却下）

重複は減る。**却下の理由は、章が互いを壊すこと。**
`missing_docs` と clippy pedantic が全モジュールに掛かるので、
**ある章のための単純化が、別の章の警告を生む。**

#### 5c. コードはコード片だけで、コンパイルしない（却下）

**最も安い。** そして **腐る。**
`CLAUDE.md` の失敗事例 4（テスト名の表が数日腐った）と同じ形で、
**誰も気づかないまま、動かないコードが教材として残る。**

## 論点 6: 本に書かないもの（提案）

### 決定（案）

**本は正本ではない。** 次の 3 つを書かない。

| 書かないもの | 理由 | 正本 |
| --- | --- | --- |
| `tally` の現在の実装状態 | 腐る。版が進むたびに本が嘘になる | コードと `git log` |
| 却下した設計案とその理由 | 本に書くと ADR と二重になる | `docs/adr/` |
| リポジトリの運用（ブランチ・CI・引き継ぎ） | 読者のリポジトリの話ではない | `CLAUDE.md`、`docs/handoff.md` |

**`GLOSSARY.md` は作らない。** 用語の正本は
`crates/tally/docs/output-format.md` と 2 つの `layout.md` に既にある。
**4 つ目の語彙の出どころを増やすと、どれかが腐る**
（`CLAUDE.md`「同じ事実を 2 箇所に書かない」）。

### 検査にできるか

**`CLAUDE.md` は「新しい『書かないもの』を決めたら、検査に足せるかを問う」と
定めている。** 3 つのうち **2 つは足せる。**

| 書かないもの | 検査 |
| --- | --- |
| リポジトリの運用 | `book/` 配下に `--ff-only`、`handoff`、`git switch` が出たら落とす |
| 却下した設計案 | `book/` 配下に「却下」「代替案」が出たら落とす |
| 実装の現在状態 | **足せない。** 「いまこうなっている」は文字列では見分けられない |

**足せない 1 件は、理由をここに残す。**

## 論点 7: 本から ADR をどう指すか（提案）

### 決定（案）

**GitHub の URL で指す。リポジトリ内の相対リンクは使わない。**

### 検討した案

#### 7a. 相対リンク `../../docs/adr/NNNN-....md`（却下）

`scripts/check-docs.sh` の相対リンク検査は通る（ファイルが実在するため）。

**却下の理由は、サイトのビルドが落ちること。**
Docusaurus は Markdown のリンクをサイト内の経路として解決しようとする。
`docs/adr/` はサイトに含まれないので、**リンク切れとして扱われる。**

#### 7b. GitHub の URL（採用）

**サイトのビルドが通り、読者がブラウザで辿れる。**

**費用は、検査が効かないこと。** `check-docs.sh` の相対リンク検査は
**相対リンクの形しか見ない**ので、**URL の切れは拾えない。**
**ADR を消さない限り切れない**ので、この費用は受け入れる。

#### 7c. ADR の内容を本に書き写す（却下）

論点 6 がこれを禁じている。

## 論点 8: これから得る学びをどこに書くか（提案）

### 決定（案）

**Rust 言語の学びは、もう `docs/learning-log.md` に足さない。**
**本を書く過程の学びは `docs/journal/` に書く。**

**あわせて、VO のピアと日次で学びを同期する。**
送るのは 2 つだけ — **その日に何を書いたか**と、**過程で何がうまくいかなかったか。**
**Rust 言語の学びは送らない**（相手の関心ではない）。

### 理由

**`learning-log.md` は学ぶ側の文書である。**
[ADR-0012](0012-stage-10-associated-types.md) で終了基準を満たした時点で、
**この文書に足すべき新しい差分は、カリキュラムの外にしか無い。**

**本を書く過程で得るのは、別種の学びである** —
どう説明すると伝わるか、Claude とどう進めると速いか。
**これは `CLAUDE.md` の分類 10（進め方の反省）であり、`docs/journal/` に属する。**

### 既知の衝突

**`scripts/check-docs.sh` の検査 4 と衝突する。**
あの検査は「journal に出た rustc のエラーコードは `learning-log.md` にもある」ことを
要求する。**本を書く過程の journal がエラーコードに触れると、CI が落ちる。**

**この ADR では直さない。** `docs/handoff.md` の未決事項に立てる。
**実際に落ちてから、どちらを変えるかを決める**
（検査を `book/` 由来の journal に当てないか、例外的に `learning-log.md` へ足すか）。

## 帰結

- **このリポジトリは、学ぶ場所から教える場所に変わる。**
  `curriculum.md` と `stage-log.md` は **凍結**し、本の素材として読む
- **`cargo t` と `cargo lint` が本のコードも見る。** 章が増えるとビルドが遅くなる
- **CI のジョブが 2 つ増える**（本のビルドと、GitHub Pages への配置）
- **本は正本ではない。** 設計判断について本が言うことは、すべて `docs/adr/` に従う
- **終了基準が無い。** 段階と違い、本には「ここまで書いたら終わり」が無い。
  **12 章を書き終えたら、そのとき改めて決める**

### 確かめて分かったこと（2026-10-31）

**6 は意図せず確かめられた。** 本の「はじめに」に
「検討した代替案と却下理由は ADR に記録してある」と書いたところ、
**検査がそれを違反として拾った。**
**正本の所在を述べた文も、字面としては却下案への言及である。**
文を言い換えて通した。**検査が粗いのではなく、本文の側が紛らわしかった。**

**2 は片側が空振りする。** `scripts/check-module-deps.sh` の対象は
`crates/` 配下に固定されているので、**今日の除外設定（`book/`）は何にも当たらない。**
**それでも読ませてある** — 除外の正本を 1 つに保たないと、
対象が増えたときに片方だけ除外を知らない状態になるため。
**「落ちることを確かめる」形の検証は、まだできていない。**

**文書の検査の側は、除外が効いていることを数で見た。**
`git ls-files '*.md'` に pathspec を渡すと、`book/` 配下の 2 件が 0 件になる。

**論点 6 の検査では拾えない漏れが、もう 1 種類あった。**
演習の案内に `cargo t -p book-ch01` と書いていた。
**`cargo t` はこのリポジトリの `.cargo/config.toml` に定義した別名**であり、
