# コンテナから GitHub へ push しない

**`status` が `proposed` なのは、Confirmation の一部がコンテナの再ビルドでしか
確かめられないため。** 下の「確認方法」を参照。

## なぜこれを ADR にするのか

[ADR-0001](0001-record-architecture-decisions.md) の絞り込み条件は
「**代替案を検討した記録が価値を持つものに限る**」である。

本件は 4 案あり、**採るのは「機能を足さない」案**である。
機能を足した記録より、**足さないと決めた記録のほうが失われやすい。**
数ヶ月後に「コンテナから push できない。直せばいいのに」と思ったとき、
ここが答えになる。**直さなかったのではなく、直さないと決めた。**

**運用の結論（何をするか）は `CLAUDE.md` が正本。** ここには書かない。
本 ADR が持つのは **検討した代替案と却下理由**だけである。

## コンテキストと問題提起

2026-08-19 に「ホストの SSH 鍵をコンテナへ複製する」設計を入れた
（`devcontainer.json` の mounts と `scripts/setup-git-auth.sh`）。
**一度も実地で動かさないまま `main` に載った。**

### 観測した事実（2026-09-25 にホストで確認）

| 事実 | 確認方法 |
| --- | --- |
| **アカウントに SSH 公開鍵が 1 本も登録されていない** | `curl -s https://github.com/karak.keys` が HTTP 200 で **0 バイト** |
| `~/.ssh/config` は `github.com` に `~/.ssh/github_rsa` を指定している | `~/.ssh/config` |
| **その鍵はパスフレーズ付き** | `ssh-keygen -y -P "" -f ~/.ssh/github_rsa` が失敗する |
| **ssh-agent に identity が 0 件** | `ssh-add -l` が `The agent has no identities.` |
| ホストで `ssh -T git@github.com` が通らない | `Permission denied (publickey)` |
| **ホストからの push は HTTPS で通る** | remote は HTTPS、`credential.helper=osxkeychain`、`gh auth status` が `karak`。2026-08-23 以降ここから実際に push している |
| `.git` と作業ツリーはホストとコンテナで共有されている | `/workspaces/rust-learn` は bind マウント |

**最初の 1 行が設計を無効にする。** 複製していたのは **GitHub が知らない鍵**だった。
パスフレーズを解いても、agent をフォワードしても通らない。

**「鍵を持っていること」と「鍵が使えること」を検証しないまま設計を書いた。**
2026-08-23 にはパスフレーズと空の agent までは突き止めたが、
**そこで止めて「鍵は登録されている」を暗黙の前提にしていた。**

### 解くべき問題は、見かけより小さい

**「コンテナから push したい」の前に、それが何を足すのかを問う必要がある。**

`.git` が共有されているので、**コンテナで commit してホストから push すれば
もう成立している。** コンテナ側の push が足すのは
「ターミナルを切り替えなくてよい」だけである。

## 決定

**コンテナへ資格情報を渡さない。コンテナから GitHub へ push しない。**

`devcontainer.json` の `~/.ssh` マウントと `scripts/setup-git-auth.sh` を削除する。

## 検討した案

### A. 資格情報を渡さない（採用）

コンテナは commit まで。push はホストから行う。

- **新しい秘密を作らない。** 鍵も token も増えない
- **`url.insteadOf` が不要になる。** remote は HTTPS のまま、
  `setup-git-auth.sh` ごと消える
- **`fetch` は引き続き通る**（public リポジトリの匿名読み取り）
- 代償は、push のときにホスト側のターミナルへ移ること

### B. ed25519 を deploy key（write）として登録する

パスフレーズ無しの鍵を新規作成し、**このリポジトリの deploy key** に登録して、
読み取り専用でマウントする。

- 非対話で確実に通る。**被害はこのリポジトリに閉じる**
- **却下理由**: 平文の秘密鍵がホストとコンテナの両方に残り、**失効の期限が無い。**
  得られるのはターミナルを切り替えない便利さだけで、割に合わない

### C. アカウント鍵をパスフレーズ付きで登録し、ssh-agent をフォワードする

鍵の実体はコンテナに入らず、socket 越しに署名だけ頼む。

- **秘密の実体がコンテナに入らない。** 4 案で最も安全
- **却下理由 1**: **アカウント全体に効く鍵**になる。このリポジトリのためだけに
  作るなら B と同じ範囲で済むはずのものを、広い権限で作ることになる
- **却下理由 2**: **agent の状態に依存する。** ホストで `ssh-add` し忘れれば
  無音で失敗する。`devcontainer up` CLI では socket の bind mount も別途要る
  （VS Code の拡張は自動でやるが、**手段によって挙動が変わるのは避けたい**）

### D. fine-grained PAT を credential helper に渡す

SSH をやめ、rust-learn 限定・期限つきの token を使う。

- SSH をやめるので設計は最も短い。**被害はこのリポジトリに閉じる**
- **却下理由**: **期限切れの再発行が定期的に発生する。**
  学習リポジトリに恒久的な運用タスクを 1 つ増やすことになる

## 対称性の検査

**「ホストから push できなくなったら」を考えると、この決定は崩れるか。**

崩れない。ホストの資格情報が失われたら、**どの案でもコンテナ側に鍵を作り直す
必要が出る。** A は「作らない」を既定にしているだけで、
必要になった時点で B か D を足せる。**A は他の案を閉ざさない。**

逆に B・C・D は、**入れた瞬間に「その鍵はまだ有効か」を見張る責務が生まれる。**
今回まさにそれを怠って、1 か月以上「動くつもりの動かない設計」を持っていた。

## 決め手

1. **得られるものが小さい。** `.git` が共有なので push は既に成立している
2. **どの案も新しい秘密を 1 つ作る。** B と D は平文の資格情報、
   C はアカウント全体に効く鍵。**便利さの対価として恒久的な資格情報を増やす**
3. **失敗しても静かにならない。** 資格情報の無いコンテナで push すれば、
   git がその場で明確に落ちる。**git-secrets とはここが違う**
   （あちらは「入っているのに何も検査しない」状態になりうるので、
   `postCreateCommand` で落とす）
4. **持たない仕組みは腐らない。** 今回の失敗は「動かす当てのない仕組みを
   実地検証なしに持った」ことだった

## 決定の帰結

- **`scripts/setup-git-auth.sh` を削除する**
- **`devcontainer.json` から `~/.ssh` の bind マウントと
  `postCreateCommand` の呼び出しを外す**
- **`url.insteadOf` は置かない。** remote は HTTPS のまま。
  `.git/config` を触らない理由（ホストと共有）は変わらないが、
  **触る動機のほうが消えた**
- `CLAUDE.md` と `README.md` の記述を直す。
  とくに README の「push にはホストの `~/.ssh` が要る」は**端的に誤り**である
- **`setup-git-secrets.sh` は残す。** あちらは資格情報ではなく検査であり、
  コンテナ内で動く必要がある
- **覆すなら新規 ADR。** 覆したくなる条件を先に書いておく —
  **コンテナが CI や自動化の実行場所になったとき。**
  「人間がホスト側のターミナルを持っている」という前提がそこで崩れる

## 確認方法（Confirmation）

| # | 確認すること | 見方 | 状態 |
| --- | --- | --- | --- |
| 1 | `setup-git-auth.sh` への参照がどこにも残っていない | `git grep setup-git-auth` が 0 件 | **済**（2026-09-25） |
| 2 | コンテナを再ビルドして `postCreateCommand` が成功する | 再ビルドのログ | 未 |
| 3 | コンテナで commit でき、それをホストから push できる | 実際に 1 単位を通す | 未 |
| 4 | **コンテナからの push が明確に失敗する**（静かに成功しない） | コンテナで `git push` を叩く | 未 |

**2〜4 はコンテナの再ビルドが要る。**
2026-09-25 時点でホストの Docker デーモンが起動していないため未実施。

**4 を確認事項に入れているのは、決め手 3 がそこに乗っているため。**
「失敗が見える」が成り立たなければ、この決定の根拠が 1 本欠ける。
