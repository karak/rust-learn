# JSON Pointer でキーを取り出す

**`status` は `proposed`。** 4 論点のうち論点 1 は学習者が決めた。
残り 3 つは本文の案を提示した状態であり、**実装はまだ無い。**

## なぜこれを ADR にするのか

[ADR-0001](0001-record-architecture-decisions.md) の絞り込み条件は
「**代替案を検討した記録が価値を持つものに限る**」である。

本件が条件を満たすのは 2 つの理由による。

1. **[ADR-0005](0005-selector-public-api.md) 論点 3 の見立てが、
   段階 7 の改善と衝突している。** 論点 3 は
   「JSON Pointer は `serde_json` に既にあり依存ゼロ」と結論したが、
   それは `Value::pointer` を前提にしている。
   **段階 7 は `Value` を作らない方向へ `extract` を作り直した。**
   「依存ゼロ」は正しいまま、「追加コストゼロ」ではなくなった。
   **この衝突をどちらに倒したかは、記録しないと失われる**
2. **ADR-0005 が「新バリアント側の話」として送った宿題を受け取る。**
   論点 3 の軸 D は検証つき newtype（D3）を却下したが、
   その理由の 1 つは「**設定の失敗という、いま未定義の分類を開くことになる**」だった。
   JSON Pointer を足すなら、その分類を定義せずには済まない

**抽出の実装そのものは `crates/tally-core/docs/layout.md`、
利用者への契約は `crates/tally/docs/output-format.md` が正本。**
ここには決定の過程だけを書く。

## コンテキストと問題提起

`--field lvl` は **トップレベルの 1 フィールド**しか取れない。
入れ子になった JSON の行（`{"req":{"status":500}}`）からは何も取れず、
黙ってスキップされる。

### 現状の事実（2026-10-20 に確認）

| 事実 | 確認方法 |
| --- | --- |
| `Key` は `#[non_exhaustive]`。**バリアント追加は非破壊のはず** | `crates/tally-core/src/select.rs` |
| **その非破壊性は実地で確かめていない** | `docs/learning-log.md` 16 節 |
| `LineErrorKind` も `#[non_exhaustive]`。バリアント追加は非破壊 | `crates/tally-core/src/error.rs` |
| **`extract` は `serde_json::Value` を作らない** | `select.rs` の `PickField`。段階 7 の改善 2 |
| **`Value` の構築と破棄が `extract` の費用の大半だった** | 構築 31.5% + 破棄 15.8%（`docs/stage-log.md` 段階 7） |
| `Value::pointer` は `&Value` を要求する | `serde_json` 1.0.151 の API |
| **`--strict` は `--field` を `requires` している** | `crates/tally/src/cli.rs` |
| 引数の誤りは終了コード 2 で、集計を始める前に返す | 同上（`--filter` の `Regex` が同じ形） |
| **設定の失敗を表す型はまだ無い。`LineError` は行の失敗である** | `crates/tally-core/src/error.rs` |

| 論点 | 問い | 状態 |
| --- | --- | --- |
| 1 | 取り出しをどう実装するか | **決定済み**（学習者、2026-10-20） |
| 2 | ポインタをどの型で持ち、不正をどこで弾くか | 案を提示 |

## 論点 1: 取り出しをどう実装するか（決定済み）

### 決定

**既存のストリーミング seed を入れ子に一般化する**（1b）。
`Value` は作らない。

### この論点に効く事実

- **`extract` の戻り値は `Cow`。** エスケープの無い文字列は**入力を借用したまま返る**。
  `Value` を経由するとこの経路が消え、常に所有することになる
- **段階 7 の改善 2 は、まさにこの `Value` を外す作業だった。**
  同じクレートの同じ関数に、測って外したものを別経路として戻すことになる
- **`--field` の経路は、どの案でも影響を受けない。** 衝突するのは新バリアントの中だけ

### 検討した案

#### 1a. `Value::pointer` をそのまま使う（却下）

* Good, because 実装が数十行で済む。**RFC 6901 の準拠を `serde_json` に委ねられる**
* Good, because ADR-0005 論点 3 が想定していた形そのもので、見立てとの差が出ない
* Bad, because **行ごとに全フィールドを確保して捨てる。**
  段階 7 が測って外したコストを、別の経路として意図的に戻すことになる
* Bad, because **戻り値が常に `Cow::Owned` になる。**
  借用のまま返る経路が、この バリアントだけ消える

#### 1b. ストリーミング seed を入れ子に一般化する（採用）

* Good, because **`Value` を作らない。** 段階 7 の設計がバリアント間で揃う
* Good, because 借用のまま返る経路が残る
* Good, because **学習の収穫が最も大きい。** 再帰する `DeserializeSeed` は
  `--field` の 1 段では出てこなかった形である
* Bad, because **実装量が最大。** 配列添字を支えるなら `SeqAccess` 側にも分岐が要る
* Bad, because **RFC 6901 の準拠を自分で負う。** `serde_json` に委ねられない
* Bad, because 再帰する seed は読みにくい。`layout.md` に読み方を書く必要がある

#### 1c. 1 段だけ seed、2 段以上は `Value`（却下）

* Good, because よくある指定（`/lvl`）は既存の経路のまま速い
* Bad, because **同じ機能に経路が 2 本できる。**
  「どちらを通ったかで性能が変わる」を利用者に説明する必要が出る
* Bad, because **測定の対象が倍になる。** 段階 7 の作法（改善前後を 1 回の
  `hyperfine` に並べる）が、経路ごとに要る

### 決め手

**学習者の判断。** 1a が最も小さく、1c が最も実利的だが、
**段階 7 で測って外したものを戻さないことと、
再帰する seed を一度書くことに価値を置いた。**

### 判断が変わる条件

**RFC 6901 の準拠で自前の実装が `serde_json` とずれたとき。**
ずれが見つかって埋められないなら、1a へ倒すほうが正しい。
そのときは本 ADR を supersede する。

## 論点 2: ポインタをどの型で持ち、不正をどこで弾くか

### 提案する決定

**検証つき newtype `JsonPointer` を `tally-core` に置く**（2c）。
**不正なポインタは引数解釈の時点で弾き、終了コード 2 で返す。**

### この論点に効く事実

- **`Value::pointer` は、先頭が `/` でないと無条件に `None` を返す。**
  `--pointer lvl` の綴り間違いが「そのポインタを持たない行」と区別できず、
  **全行スキップで度数 0 という結果が静かに出る**
- ADR-0005 軸 D は「**JSON Pointer を足すなら検証つき newtype が要る**」と
  結論しながら、`JsonField` を包む理由にはならないとして D3 を却下した。
  **本 ADR はその「新バリアント側」である**
- **`--filter` に前例がある。** `Regex` を型で受け、解釈の時点で検証させている。
  入力を読み始めてから失敗しない

### 検討した案

#### 2a. `JsonPointer(String)` のまま（却下）

* Good, because 追加コードがゼロ
* Bad, because **先頭 `/` の欠落を黙って全行スキップにする。**
  ADR-0005 がこの形を「受け入れがたい」と書いている
* Bad, because 検証の置き場所が無い

#### 2b. 透過な newtype（検証しない）（却下）

* Good, because 内部表現を後から変えられる
* Bad, because **2a の欠点が 1 つも消えない。**
  型が増えただけで、不正なポインタは通る

#### 2c. 検証つき newtype（採用案）

* Good, because **不正なポインタが型として存在できない。**
  `Key::JsonPointer` を持てた時点で、ポインタは構文として正しい
* Good, because **検証を 1 回で済ませられる。**
  行ごとにセグメントへ分ける必要が無い（内部表現は実装の自由）
* Bad, because **設定の失敗という分類を開く。** ADR-0005 D3 が避けた点である

### 設定の失敗をどこに置くか

**`LineError` には載せない。** あれは行の失敗であり、行番号と抜粋を持つ。
ポインタの誤りは **行とは無関係に、1 回だけ起きる。**

| 置き場所 | 判断 |
| --- | --- |
| `LineErrorKind` にバリアントを足す | **却下。** 行の失敗ではない。行番号も抜粋も付けられない |
| `TallyError` にバリアントを足す | **却下。** `TallyError` は閉じており、追加は消費者の網羅性検査を落とす |
| **`JsonPointer` のコンストラクタが返す専用のエラー型** | **採用案。** 失敗の形が 1 つしかないので型も 1 つで足りる |

**`tally` 側では clap の値パーサが受け、終了コード 2 になる**（`--filter` と同じ形）。

## 論点 3: 見つからない値と使えない値をどう扱うか

### 提案する決定

**`--field` の意味論を踏襲する。** 新しい扱いを 1 つだけ足す。

| 行の形（ポインタが `/req/status`） | 扱い | 理由 |
| --- | --- | --- |
| `{"req":{"status":500}}` | `500` を数える | 本来の経路 |
| `{"req":{}}` | **スキップ** | 「そのフィールドを持たない行」と同じ |
| `{"req":"ok"}` | **スキップ** | 途中が辿れない。`Value::pointer` も `None` を返す |
| `{"req":{"status":null}}` | **スキップ** | 既存の `null` の扱いに揃える |
| `{"req":{"status":[1]}}` | **エラー** | 集計に使えない形。既存の `UnsupportedFieldType` と同じ判断 |
| `[1,2]`（オブジェクトでない） | **スキップ** | 既存の `visit_seq` の扱いに揃える |

**エラーの文面にはポインタを出す。** `LineErrorKind` は `#[non_exhaustive]` なので
**バリアント追加は非破壊である。** 既存の `UnsupportedFieldType { field }` に
ポインタ文字列を詰めると、`field` という名前が嘘になる。

### 配列の添字と RFC 6901 のエスケープ

| 記法 | 扱い | 理由 |
| --- | --- | --- |
| `/items/0` | **支える** | 配列の n 番目。入れ子の JSON では普通に要る |
| `/items/-` | **検証で拒否する** | RFC 6901 では「最後の次」で、**常に存在しない。** 書けるのに必ず空振りする記法を通さない |
| `~0` → `~`、`~1` → `/` | **支える** | RFC 6901 の定義。これが無いと `/` を含むキーを指せない |
| `~` の後ろが `0` でも `1` でもない | **検証で拒否する** | RFC 6901 で不正 |
| 空のポインタ `""` | **検証で拒否する** | 文書全体を指す。それが欲しければ `--field` を省けばよい |

## 論点 4: CLI にどう出すか

### 提案する決定

**`--pointer <PTR>` を足し、`--field` と排他にする**（4b）。

### 検討した案

#### 4a. `--field` が `/` で始まったらポインタと解釈する（却下）

* Good, because フラグが増えない
* Bad, because **フィールド名が `/` で始まる JSON を指せなくなる。**
  今まで指せていたものが指せなくなるのは破壊的変更である
* Bad, because **引数の意味が値の形で変わる。** 誤りの診断が難しくなる

#### 4b. `--pointer` を足し、`--field` と排他にする（採用案）

* Good, because **どちらの意味で解釈されるかが引数の名前で決まる**
* Good, because clap の `conflicts_with` で排他を表明でき、
  **実行時ではなく引数解釈の時点で拒否できる**
* Bad, because 似た目的のフラグが 2 つになる。ヘルプで区別を書く必要がある

#### 4c. `--field` を可変個にして path として扱う（却下）

* Good, because エスケープの問題が消える
* Bad, because **RFC 6901 から外れる。** 標準の記法を捨てて独自記法を作ることになる

### `--strict` との関係

**`--strict` の `requires = "field"` を、`field` か `pointer` のどちらかに広げる。**
**広げ忘れると `--pointer` と `--strict` を同時に指定できない。**
ここは引数解釈のテストで押さえる。

## 対称性の検査

- **1b の「学習の収穫」を、1a の側にも当てたか。**
  当たらない。1a で学べるのは `Value::pointer` の呼び方だけで、
  これは段階 1 の水準である。**非対称は実在する**
- **2c の「設定の失敗を開く」を、ADR-0005 は却下の根拠にした。
  本 ADR で採るのは一貫しないのではないか。**
  一貫する。ADR-0005 が守ろうとしたのは
  「**まだ要らない分類を、要るかどうか分からないまま開かないこと**」である。
  **本 ADR では要る。** 先頭 `/` の検証を置く場所が他に無い
- **論点 3 が「スキップ」に倒す項目は、`--strict` で救えるか。**
  救える。`--strict` は「キーを取り出せない行があればエラー」なので、
  **入力の健全性を検査したい利用者はそちらを使う。**
  既定を厳しくする必要は無い
- **論点 4 の 4a を却下した理由（値の形で意味が変わる）は、
  2c の検証と矛盾しないか。** 矛盾しない。
  2c は「**その値が正しいか**」を見る。4a は「**どの引数として扱うか**」を値で決める。
  前者は検証、後者は多重定義であり、別の話である

## 決定の帰結

- **`Key` のバリアントが 3 つになる。** `#[non_exhaustive]` の非破壊性を
  `cargo-semver-checks` で実地に確かめる機会が生まれる（未決事項 3 と 6）
- **`tally-core` に設定の失敗という分類が生まれる。** 今までは行の失敗だけだった
- **`output-format.md` の契約は変わらない。** 1 行が産むキーは 0..1 のままである
- **関連型つきの trait には割らない。** 抽出の実装は `Key` の中に閉じており、
  外から差し替える消費者がいない。**学習のために抽象を足すのは本末転倒である**
  （未決事項 9 の消化は、必要が立ってから）
- **JSONPath（ADR-0005 の段 2）には進まない。** 戻り値が 0..n になり
  `output-format.md` の契約に触れる。採るなら別 ADR である
