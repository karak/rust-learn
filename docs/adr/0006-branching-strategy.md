# ブランチ運用と `main` への載せ方

**`status` が `proposed` なのは、Confirmation の一部が「実際に 1 単位を通す」ことでしか
確かめられないため。** 下の「確認方法」を参照。

## なぜこれを ADR にするのか

[ADR-0001](0001-record-architecture-decisions.md) の決定は
「**アーキテクチャ上の**意思決定を ADR として記録する」であり、
ブランチ運用はコードの構造ではない。**それでもここに書く理由を述べる。**

ADR-0001 の帰結に置かれた実際の絞り込み条件は
「**代替案を検討した記録が価値を持つものに限る**」であって、コードかどうかではない。
本件は 3 論点に計 10 案（3 + 4 + 3）あり、しかも
**却下する案の 1 つ（squash merge）は業界の既定値**である。
「なぜ既定値を採らなかったか」は、数ヶ月後の自分が最も疑う箇所になる。

**運用の結論（何をするか）は `CLAUDE.md` が正本。** ここには書かない。
本 ADR が持つのは **検討した代替案と却下理由**だけである。
`crates/*/docs/layout.md` の表と ADR の関係（結論は表、過程は ADR）と同じ分担。

## コンテキストと問題提起

48 コミットのあいだ、**すべての変更が `main` に直接コミットされてきた。**
段階 5 の実装（2026-08-19）で **25 ファイル・コード + 8 文書**の変更が一度に出て、
これを `main` に直接載せるべきかを問う機会になった。

### 観測した事実（2026-08-19 に確認）

| 事実 | 確認方法 |
| --- | --- |
| コミット 48 件、**マージコミット 0 件** | `git log --oneline \| wc -l`、`git log --merges \| wc -l` |
| ブランチは `main` のみ。タグは `adr-0002-baseline` の 1 つ | `git branch -a`、`git tag -l` |
| **1 コミットあたり 1〜4 ファイル。** 意味の単位が小さい | `git show --name-only` を直近 10 件 |
| CI のトリガは `push: [main]` と `pull_request` | `.github/workflows/ci.yml` |
| **PR は一度も作られていない** | `git log --format=%s \| grep -E '\(#[0-9]+\)'` が 0 件（GitHub の squash merge は `(#N)` を付ける）。かつ全コミットの committer が `karak` で、GitHub の merge ボタンが使う `GitHub <noreply@github.com>` が 1 件も無い |
| **`gh` が devcontainer に入っていない** | `command -v gh` |
| `main` への push が双方向で 2 回 reject された | `docs/journal/2026-08-17.md` |

**この 7 行のうち 3 つが、そのままでは矛盾している。**

1. **CI の設定は PR 前提で書かれているのに、PR が 1 件も無い。**
   `push: branches: [main]` だけなので、**トピックブランチに push しても CI は回らない。**
   48 コミットのあいだ、CI が回るのは常に「`main` に載ったあと」だった
2. **`CLAUDE.md` と `docs/handoff.md` は「CI の稼働状況は `gh run list` を見ること」と
   書いているが、`gh` が入っていない。** 指示が実行できない
3. **2026-08-17 の Try 1 は「push の前に必ず `git fetch` する」だった**が、
   それは**規約であって仕組みではない。** 守り忘れれば同じことが起きる

### 解くべき問題は 3 つ

| # | 問題 | 実害 |
| --- | --- | --- |
| A | 並行するワークツリーが同じ `main` を進める | push が reject される（2026-08-17 に 2 回） |
| B | 未完成の状態が公開される | セッションが途中で切れると、中途半端な `main` が public に残る |
| C | CI が事後にしか回らない | 壊れた状態が `main` に載ってから発覚する |

## 論点の分割

**3 論点は独立に決められる。** ただし論点 3 は論点 1 の結論に乗る
（ブランチを作らないなら「載る前に CI を回す」という問い自体が立たない）。

| # | 論点 | 決定 |
| --- | --- | --- |
| 1 | `main` への直コミットを許すか | **許さない。常にブランチを切る** |
| 2 | `main` へ載せる方法 | **ローカルで rebase → `--ff-only`** |
| 3 | `main` に載る前に CI を回す手段 | **全ブランチの push で CI を回す。PR は任意** |

## 論点 1: `main` への直コミットを許すか

### 決定

**許さない。作業は常にブランチで行う（1b）。**

### この論点に効く事実

- 問題 A は **実証済み**である。推測ではない
- **`git worktree` はブランチの重複チェックアウトを禁じている。**
  ブランチを切れば、2 つのワークツリーが同じ ref を進めることが**構造的に起こらない**
- 2026-08-17 の race は「並行作業に気づいていなかった」のではない。
  **気づいていたうえで、`fetch` から push までの数分で前提が崩れた**

### 検討した案

#### 1a. 直コミットを許す（現状）

* Good, because **手数がゼロ。** `commit` して `push` するだけ
* Good, because 小さな変更が即座に `main` に載る。1〜4 ファイルの
  コミット 48 件という現在の粒度は、この軽さに支えられている
* Bad, because **問題 A が構造的に残る。** 2026-08-17 に 2 回起きた
* Bad, because **問題 B が避けられない。** `main` が常に作業中の状態を映す
* Bad, because **問題 C が避けられない。** CI は `main` に載ったあとしか回らない

#### 1b. 常にブランチを切る（採用）

* Good, because **問題 A が構造的に消える。** 各ワークツリーが別 ref を進める
* Good, because 問題 B が消える。`main` は「載せてよいと判断した状態」だけになる
* Good, because 問題 C を解く土台ができる（論点 3）
* Bad, because **1 単位あたり 5 コマンド程度増える**
* Bad, because 単独開発では過剰に見える。レビュアーが他にいない

#### 1c. 並行作業しているときだけブランチを切る

* Good, because **手数が最小。** 大半の作業は単独なので、ほぼ 1a のまま
* Good, because 「必要なときだけ払う」という筋の通った形をしている
* Bad, because **「並行しているか」を知る手段が無い。**
  `git worktree list` はローカルのワークツリーしか見えず、
  別クローン・別マシン・クラウドのセッションは見えない
* Bad, because 2026-08-17 の race は **並行を知っていたのに起きた。**
  条件付きの規則では防げなかった事例そのものである
* Bad, because **条件付きの規則は毎回判断を要求する。** 判断は間違う

### 対称性の検査

**却下する 1a を、採用案と同じ精度で書き直した。**

1a の Good に挙げた「小さいコミットが即座に載る」は、**軽視すべきでない。**
このリポジトリの履歴の細かさ（1 コミット 1〜4 ファイル）は資産であり、
それは「思いついたらすぐ `commit` して `push`」という軽さが作った。
ブランチを挟むと、**「まとめてから載せる」方向に圧力がかかる**。

**この圧力は論点 2 で打ち消せる。** `--ff-only` を採ればブランチ上の
コミットがそのまま `main` に載るので、粒度は変わらない。
**1a の利点を失わずに 1b を採れる**ことが確認できた。

### 決め手

1. **問題 A は実証済みで、1c では防げなかったことも実証済み。**
   「知っていれば避けられる」類の失敗ではなかった
2. **1a の唯一の実質的な利点（コミット粒度の細かさ）は、論点 2 で保全できる**

### 決定の帰結

- **`main` への直 push は規約違反になる。** ただし GitHub 側のブランチ保護は
  設定していない（`gh` が無く、この場から設定できない）。
  **規約だけで運用する。** 保護を掛けるかは別途の判断
- **1 ブランチの大きさを決める必要がある。** 「1 セッション」を単位にしない
  — セッションは中断される（`docs/handoff.md` が存在する理由がそれ）。
  **「まとまって `main` に載せてよい変更」を単位にする**

## 論点 2: `main` へ載せる方法

### 決定

**ローカルで `rebase` してから `git merge --ff-only`。**
**squash merge とマージコミットは採らない。**

### この論点に効く事実

- **マージコミットは 48 コミット中 0 件。** `git log --oneline` が一直線の
  物語になっており、`docs/journal/` の日付順の記録と対応が取れる
- **段階 5 の変更は 25 ファイル**で、コード・ADR 2 本・文書 8 本にまたがる。
  squash すると「実装した」「ADR を `accepted` にした」「文書を直した」が
  1 コミットに潰れる
- **[ADR-0001](0001-record-architecture-decisions.md) は
  「ADR は決定の記録であり歴史である」と書いている。**
  履歴の側でそれが読めなくなるのは筋が通らない
- `docs/journal/` は「何をどの順でやったか」を書いている。
  **履歴がその順序を持たなくなると、突き合わせられなくなる**

### 検討した案

| | 2a. `--ff-only`（採用） | 2b. マージコミット（`--no-ff`） | 2c. squash merge | 2d. GitHub の rebase-merge |
| --- | --- | --- | --- | --- |
| `main` の履歴 | 一直線。**今と同じ** | マージコミットが混ざる | 1 単位 1 コミット | 一直線 |
| 個別コミット | 残る | 残る | **消える** | 残る |
| 単位の境界 | 履歴に残らない | **残る** | 残る | 残らない |
| CI が回った SHA | **そのまま載る** | そのまま載る | 別物になる | **別物になる** |
| 追加ツール | 不要 | 不要 | GitHub / `gh` | GitHub / `gh` |

#### 2a. ローカルで rebase → `--ff-only`（採用）

* Good, because **履歴の見た目が今と一切変わらない。** 移行コストがゼロ
* Good, because **コミット粒度が保たれる**（論点 1 の対称性の検査を参照）
* Good, because **`rebase` が機械的に強制される。**
  2026-08-17 の Try 1「push の前に必ず `git fetch` する」が、
  規約から**仕組み**になる。忘れると `--ff-only` が失敗して止まる
* Good, because **CI が回った SHA がそのまま `main` に載る**（論点 3 と噛み合う）
* Bad, because **単位の境界が履歴に残らない。**
  「段階 5 の実装はどこからどこまでか」を履歴からは読めない
* Bad, because **push 済みのブランチを rebase すると `--force-with-lease` が要る。**
  自分のブランチなので安全だが、手順が 1 つ増える
* Bad, because revert が単位単位でできない。コミットを個別に revert することになる

#### 2b. マージコミット（`--no-ff`）

* Good, because **単位の境界が履歴に残る。** `git log --first-parent --oneline` が
  「単位の一覧」になり、`docs/curriculum.md` の段階と対応させて読める
* Good, because 個別コミットも残る。squash と違い粒度を失わない
* Good, because **revert が 1 コマンドで済む**（`git revert -m 1 <merge>`）
* Bad, because **これまで 0 件だったマージコミットが混ざり、履歴の読み方が
  途中で変わる。** 48 コミットぶんの一貫性が切れる
* Bad, because `git log --oneline` にノイズが増える
* Bad, because **単独開発では単位の境界を履歴に刻む価値が薄い。**
  `docs/curriculum.md` の（済）と `docs/journal/` の日付が既にその役目を持っており、
  **3 箇所目になる**

#### 2c. squash merge

* Good, because **`main` の履歴が「1 単位 = 1 コミット」になる。**
  `git log --oneline` がそのまま変更単位の一覧になる
* Good, because **作業中の試行錯誤が履歴に残らない。**
  「書いて消した」「数字を直した」が外から見えず、意図だけが残る
* Good, because revert が 1 コミットで済む。**業界の既定値であり、最も摩擦が少ない**
* Bad, because **このリポジトリの主要な資産を壊す。**
  段階 5 の 25 ファイルが 1 コミットになると、
  「どの文書の変更がどの主張を壊したか」を bisect で追えない
* Bad, because **`docs/journal/` との対応が切れる。**
  journal は順序を持つ記録であり、履歴が順序を失うと突き合わせられない
* Bad, because CI が回った SHA が `main` に載らない

#### 2d. GitHub の rebase-merge

* Good, because ボタン 1 つ。PR の UI に乗る
* Good, because 履歴は一直線に保たれる
* Bad, because **`gh` が入っていない。** ブラウザが要る
* Bad, because **GitHub の rebase-merge は commit を作り直すので、
  CI が検査した SHA と `main` に載る SHA が別物になる**
* Bad, because 2a でできることを、外部サービスに依存して行うことになる

### 対称性の検査

**2c（squash）は業界の既定値なので、却下理由を厳しく見た。**

squash が既定値になっている理由は「トピックブランチのコミットが汚いから」である。
`wip`、`fix typo`、`address review comments` が並ぶ履歴を `main` に入れたくない。

**このリポジトリではその前提が成立しない。** 48 コミットのメッセージは
すべて意味の単位で書かれており（「ADR-0005 の論点 4 を決定し、全論点の決定を完了する」）、
**潰す価値のある汚れが無い。** squash の利点は
「汚れているコミットを隠せる」ことであり、汚れていなければ利点も無い。

**逆向きも見た。** 2a の Bad「単位の境界が残らない」は、2b なら解決する。
これは 2b の実質的な優位である。**それでも採らないのは、境界の記録が
既に 2 箇所（curriculum の（済）、journal の日付）にあるためで、
`CLAUDE.md` の「同じ事実を 2 箇所に書かない」に照らして 3 箇所目を作らない**、
という判断である。**2b が劣っているのではなく、この repo には要らない。**

### 決め手

1. **squash の利点は「汚いコミットを隠せる」ことで、ここには隠すべき汚れが無い。**
   既定値を採らない理由はこれ 1 つで足りる
2. **`--ff-only` は `rebase` を強制する。** 2026-08-17 の Try を仕組みに変換できる。
   規約を増やさずに問題 A を閉じられる
3. **履歴の様式が変わらない。** 48 コミットぶんの読み方を維持できる

### 決定の帰結

- **`main` は今後もマージコミット 0 件を保つ。** これが破れたら運用が崩れた合図
- **push 済みのブランチを rebase したら `--force-with-lease` を使う。**
  `--force` は使わない（相手の push を消しうる）
- **単位単位の revert ができない。** 必要になったら
  `git revert <最初のコミット>..<最後のコミット>` を使うことになる。
  **この不便さが実際に問題になったら、2b への移行を新しい ADR で検討する**

## 論点 3: `main` に載る前に CI を回す手段

### 決定

**CI の push トリガを全ブランチに広げる。PR は任意（3b）。**

### この論点に効く事実

- **現在の CI は `push: branches: [main]` と `pull_request`。**
  PR を作らない限り、トピックブランチには CI が回らない。
  そして **PR は 48 コミットのあいだ 1 件も無い**（根拠は上の事実の表）
- **`gh` が devcontainer に入っていない**のに、`CLAUDE.md` と
  `docs/handoff.md` は `gh run list` を案内している
- **レビュアーは他にいない。** 「敵対的レビュー」は実際に行われているが
  （ADR-0002 は中心論証が崩れて全面改訂された）、**それは会話の中で起きており、
  GitHub の PR 上ではない**
- 論点 2 で `--ff-only` を採ったので、**ブランチの tip の SHA がそのまま `main` になる**

### 検討した案

#### 3a. PR を必須にする

* Good, because 既存の CI 設定（`pull_request`）がそのまま生きる。**YAML を触らない**
* Good, because **差分の URL とレビューコメントが残る。**
  会話の中の議論と違い、後から辿れる形で残る
* Good, because 「マージする」という明示的な瞬間ができる
* Bad, because **`gh` を devcontainer に入れる必要がある。**
  入れないとブラウザ作業になり、エージェントのセッションからは操作できない
* Bad, because **単独開発ではレビュー機能が空回りする。**
  自分の PR を自分で承認する
* Bad, because GitHub の merge ボタンを使うと SHA が変わる（論点 2 の 2d）。
  ローカルで `--ff-only` するなら、PR は「マージせずに閉じる」ことになり不自然

#### 3b. 全ブランチの push で CI を回す（採用）

* Good, because **`gh` もブラウザも要らない。** `git push` だけで CI が回る
* Good, because **CI が検査した SHA がそのまま `main` に載る**（`--ff-only` なので）
* Good, because **CI 設定の死んだ半分が生きる。**
  48 コミットのあいだ `pull_request` トリガは一度も発火していなかった
* Good, because 手数が最小。論点 1 で増えた手数をこれ以上増やさない
* Bad, because **作業中の push でも CI が回る。** WIP を push すると無駄に走る
* Bad, because 差分の URL が残らない。PR を任意で作れば得られるが、既定では無い
* Bad, because 同一リポジトリで PR を作ると `push` と `pull_request` が
  **二重に走る。** PR が任意運用なので稀だが、ゼロではない

#### 3c. 現状維持（`main` の push でのみ CI）

* Good, because **設定変更がゼロ。** 触らないことの価値は常にある
* Good, because CI の実行回数が最小
* Bad, because **問題 C が全く解けない。** `--ff-only` で `main` に載せた
  その瞬間に初めて CI が回る。**事前検査になっていない**
* Bad, because ブランチを切る意味が半分になる。
  問題 A と B は解けるが C は残る
* Bad, because `pull_request` トリガが死んだまま残り、
  **設定と実態の不一致が続く**

### 対称性の検査

**3a を却下する理由が「`gh` が無い」だけなら弱い。** `gh` は入れられる。

そこで **`gh` を入れた前提で 3a を再評価した。** それでも残る欠点が 2 つある。

1. **PR の主要な価値（第二の目による事前レビュー）が、この repo では
   PR 上で発生していない。** ADR-0002 の全面改訂を招いた敵対的レビューは
   会話の中で起きた。PR を作っても、レビューは相変わらず会話で行われ、
   **PR は CI を回すためだけの容器になる**
2. **論点 2 で `--ff-only` を採ったことと噛み合わない。**
   PR を作ってローカルで `--ff-only` すると、PR は自動で closed になるが
   「マージした」という記録は GitHub 上に残らない。
   逆に GitHub の merge ボタンを使うと SHA が変わる。**どちらかが歪む**

**逆に 3b の Bad「差分の URL が残らない」も見直した。**
これは実は失われていない。`git log` と `git diff` で同じものが得られ、
**GitHub 上でも `main` のコミット単位で差分が読める。**
失われるのは「単位でまとめた差分」だけで、それは論点 2 で
「単位の境界を履歴に残さない」と決めたことの帰結であり、二重に数えるべきでない。

### 決め手

1. **PR の主要な価値がこの repo では PR 上で発生していない。**
   CI を回すためだけに PR を作るなら、CI を直接回せばよい
2. **`--ff-only` と組むと、CI が検査した SHA がそのまま `main` に載る。**
   3a・2d の経路ではこれが崩れる

### 決定の帰結

- **`.github/workflows/ci.yml` の push トリガを `["**"]` に広げる**
- **`pull_request` トリガは残す。** fork からの PR では push イベントが
  発火しないため、公開リポジトリとして残す価値がある。
  同一リポジトリの PR で二重に走ることは受け入れる
- **`gh` を入れる動機が消える。** ただし `CLAUDE.md` と `docs/handoff.md` の
  「`gh run list` を見ること」は**実行できない指示として残っている。**
  文言を直す（`gh` は任意であると明記する）
- **WIP を push すると CI が回る。** これを嫌うなら push を控えるだけでよく、
  規約にはしない

## 確認方法（Confirmation）

**「実際に 1 単位を通す」ことでしか確かめられない項目がある。**
それらが済んだら `status` を `accepted` にする。

| # | 確認すること | 見方 | 状態 |
| --- | --- | --- | --- |
| 1 | ブランチを切って段階 5 の変更をコミットできる | `git log main..<branch>` | **未**（本 ADR を書いた時点では、変更はまだ `main` の作業ツリー上にある） |
| 2 | トピックブランチの push で CI が回る | GitHub Actions の実行履歴 | 未 |
| 3 | `git merge --ff-only` が成功する（= rebase を忘れていない） | コマンドの終了状態 | 未 |
| 4 | **`main` のマージコミットが引き続き 0 件** | `git log --merges --oneline \| wc -l` | 未 |
| 5 | **`main` に載った SHA が、CI が回った SHA と一致する** | Actions の SHA と `git log` を突き合わせる | 未 |
| 6 | `CLAUDE.md` に運用手順が書かれ、本 ADR と重複していない | 両方を読む | **済** |

**この ADR を書いた時点で `status` を `proposed` にしているのは、1〜5 がすべて未実施だからである。**
**「運用を決めた」と「運用が動いた」を混同しない**（2026-08-19 の Try 7 と同じ）。

**2〜5 は次に `main` へ載せるときに確かめる。**
**4 は一度きりの確認ではなく、以後ずっと成り立つべき性質**である。

### 初回適用で分かったこと（2026-08-19）

**ブランチは着手前に切らないと、事後には分けられない。**

本 ADR を決めた時点で、作業ツリーには 4 単位ぶんの変更が既に載っていた
（段階 5 の実装 / 本 ADR / curriculum の分離 / learning-log の仕分け）。
**単位ごとにブランチへ分けようとしたが、できなかった。**

理由は「同じファイルを複数の単位が触っている」こと。
`CLAUDE.md`・`ci.yml`・`handoff.md`・`journal/2026-08-19.md`・`learning-log.md` の
5 ファイルが 2 単位以上から編集されており、**分けるには hunk 単位の切り分けと、
中間状態のファイル内容の再構成が要る。** 中間状態は CI を通る保証が無く、
「各ブランチで CI を通す」という本 ADR の目的そのものを崩す。

**したがって初回は 1 ブランチにまとめ、コミットを単位ごとに分けた。**
`--ff-only` を採ったので **コミット粒度は保たれる**（論点 2 の対称性の検査）。
失われたのは「単位ごとに CI が回る」ことだけである。

**これは本 ADR の欠陥ではなく、適用の順序の問題**である。
`CLAUDE.md`「ブランチ運用」の手順 1 が
「`git switch -c` してから作業する」で始まるのは、この理由による。
**次回からは着手前に切る。**
