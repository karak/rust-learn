# エラー型の形: 判別とフィールド取り出しの人間工学

**まだ `accepted` ではない。** 論点の決定はすべて済んでいるが、
**論点 7 の実測と Confirmation の実施が残っている。**
それらを終えてから `accepted` にする（[ADR-0001](0001-record-architecture-decisions.md) の手順）。

## コンテキストと問題提起

段階 5 で集計コアを `tally-core` として切り出す。**その作業と同時に形を決める。**

理由は「切り出すと契約になるから」ではない。下の前提のとおり、
**下流が既知の小集合である以上、切り出した後で形を変えることもできる。**
そうではなく、**どうせ全呼び出し側を書き換えるなら、切り出しと同時が最も安い**から。

現状の `TallyError` には 2 つの問題がある。

1. **行番号を持つ 3 バリアントのうち、抜粋を持つのは `MissingField` だけ。**
   「何行目がどう見えたか」に答えられるものと答えられないものが混在する
2. **`field` の型が `String` と `Box<str>` で揃っていない**

### 前提: 想定する利用者

**この CLI の想定は「自分または小規模プロジェクト専用の補助ツール」である。**
公開ライブラリではない。この前提が論点 2 の結論を決めるので、先に明示する。

**素性の知れない下流が存在しない場合、破壊的変更はコストではない。**
呼び出し側を全部握っているなら、シグネチャを変えたときにコンパイラが
修正箇所を列挙してくれる。これは損失ではなく作業リストである。

## 論点の分割

**各論点は独立に決められる。** 依存がある箇所だけ明記する。

| # | 論点 | 状態 | 結論 |
| --- | --- | --- | --- |
| 1 | 共有文脈を外側の構造体に括り出すか | **決定済み** | 括り出す（`LineError`） |
| 2 | `#[non_exhaustive]` を付けるか | **決定済み** | 付けない |
| 3 | 失敗の単位ごとに戻り値の型を分けるか | **決定済み** | 分ける（`LineError` を返す） |
| 4 | `serde_json::Error` を `#[source]` として公開するか | **決定済み** | 公開する（安定 API でないと明記） |
| 5 | ライブラリのエラーと CLI 固有のエラーを分けるか | **決定済み** | 分ける（CLI 固有の型を持つ） |
| 6 | 対処の示唆（hint）を型で持つか | **決定済み** | 持つ（範囲を絞る） |
| 7 | エラー型の大きさの変化 | **未測定** | 測定義務。実装後に測る |

**すべての決定は済んだ。** 残るのは論点 7 の実測と、下記 Confirmation の実施。
**これらを終えてから `accepted` にする**（[ADR-0002](0002-output-format-abstraction.md) と同じ手順）。

**本 ADR の範囲外**: `Selector` の公開 API（`#[non_exhaustive]` + コンストラクタ）は
別の判断であり、別 ADR で扱う。エラー型の形とは独立している。

## 論点 1: 共有文脈を外側の構造体に括り出すか（決定済み）

### 決定

**括り出す。** 行に紐づく失敗を `LineError` にまとめ、
共有する文脈（行番号・抜粋）を構造体のフィールドに、
判別と個別データを内側の `kind` enum に置く。

```rust
pub enum TallyError {
    OpenInput { path: PathBuf, source: io::Error },
    Read(io::Error),
    /// 行に紐づく失敗。**必ず行番号と抜粋を持つ**
    Line(LineError),
}

pub struct LineError {
    pub line_no: usize,
    pub snippet: Box<str>,
    pub kind: LineErrorKind,
}

pub enum LineErrorKind {
    InvalidJson { source: serde_json::Error },
    UnsupportedFieldType { field: Box<str> },
    MissingField { field: Box<str> },
}
```

### 却下した案: 各バリアントに `LineContext` を埋める

```rust
pub enum TallyError {
    OpenInput { path: PathBuf, source: io::Error },
    Read(io::Error),
    InvalidJson { ctx: LineContext, source: serde_json::Error },
    UnsupportedFieldType { ctx: LineContext, field: Box<str> },
    MissingField { ctx: LineContext, field: Box<str> },
}
```

**同じ情報を持つが、取り出しの人間工学が違う。**

| やりたいこと | 各バリアントに埋める | 外側に括り出す（採用） |
| --- | --- | --- |
| 行番号を取る | **行を持つ全バリアントを `match`** | **`Line(e)` を 1 回剥がして `e.line_no`** |
| 種類で分岐する | `match err` | `match err.kind` |
| 行エラーを 1 つ足す | 文脈フィールドを**書き忘れうる** | 書きようがない（構造体が持つ） |

**1 行目は「`match` 不要」ではない。** `TallyError` には行を持たないバリアント
（`OpenInput` / `Read`）があるので、どちらの案でも最初の `match` は要る。
差は **その後に何回 `match` するか**で、採用案は 1 回、却下案はバリアントの数だけ。
**`LineError` を直接受け取る文脈（論点 3 の帰結）でのみ `match` がゼロになる。**

**決め手は 3 行目。** 今回の問題（`MissingField` にだけ抜粋がある）は
まさに「足すときに書き忘れた」形で発生している。**同じ誤りが二度できない形**を選ぶ。

### 帰結

- **「行番号を持つが抜粋を持たない」状態が型として存在しなくなる**
- `match` が 2 段になる（`TallyError::Line(e)` → `e.kind`）
- `field` の型を `Box<str>` に統一する（`UnsupportedFieldType` が `String` だった）
- **抜粋の生成箇所が増える。** これまで `snippet(line)` を呼んでいたのは
  `MissingField` を作る 1 箇所だけだったが、`InvalidJson` と
  `UnsupportedFieldType` でも作ることになる。
  **確保が増えるのは失敗時のみ**なので、成功パスのコストは変わらない
  （`docs/learning-log.md` 節 6-1 で測った「成功パスへの課税」とは別の話）
- **`Key::extract` が行そのものを必要とする。** 抜粋を作るために引数の `line` を
  使うことになる。現状すでに受け取っているので、シグネチャは変わらない
- **`Display` と `source()` の合成規則を決める必要がある。** これは本 ADR では
  未決のまま実装に持ち越す。現状は 1 行の Display に外側の文脈（行番号・抜粋）と
  内側のデータ（フィールド名）が同居しており、**2 段に分けると
  どちらの層が何を描画するかを決めないと文言が変わる。**
  `core.rs` の「抜粋の制御文字は生のまま表示されない」は
  **単一のエラーの `to_string()`** を検査しているので、
  抜粋の描画を `source()` 側へ落とすとこの検査が壊れる。
  **Confirmation で押さえる**

## 論点 2: `#[non_exhaustive]` を付けるか（決定済み）

### 決定

**付けない。** enum にもバリアントにも構造体にも付けない。

### 根拠

`#[non_exhaustive]` は **素性の知れない下流を守るための機構**であり、
その対価を下流が払う。**払う対価は付ける対象で違う。**

| 付ける対象 | 下流に課される制約 |
| --- | --- |
| enum | **`_ =>` を強制する**（網羅性検査を失う） |
| enum のバリアント | パターンに `..` を強制する（バリアントの網羅性は残る） |
| 構造体 | リテラル構築を禁じ、パターンに `..` を強制する |

**網羅性を失うのは enum に付けた場合だけ。** ただし本 ADR で扱う
`TallyError` / `LineErrorKind` はいずれも enum なので、この対価が効く。

想定利用者（前提を参照）では守るべき未知の下流がいない。
**対価だけを払って便益を受け取らない取引になる。**

### 帰結

- **バリアントを足すと呼び出し側がコンパイルエラーになる。** これは望ましい挙動として受け入れる
- 公開ライブラリに転用する場合、**後から `#[non_exhaustive]` を付けるのは破壊的変更**
  （Cargo Book の `attr-adding-non-exhaustive`）。転用時は最初に付け直す必要がある
- `std::io::Error` の「不透明構造体 + `kind()`」は採らない。
  **あの形が成立するのは `ErrorKind` が Copy でデータを持たないから**であり
  （matklad の分析）、`tally` の種類は `field` を伴うので前提が違う

### `Selector` と方針が割れることについて

**同じクレートの中で、`Selector` には `#[non_exhaustive]` を付ける方針、
エラー型には付けない方針を採る。** 一見すると不整合なので理由を書く。

**両者は使われ方が逆である。**

| 型 | 外部での主な使われ方 | `#[non_exhaustive]` の効果 |
| --- | --- | --- |
| `Selector` | **構築される**（`Selector { .. }`） | リテラル構築を禁じ、**フィールド追加を非破壊にする** |
| `TallyError` / `LineErrorKind` | **判別される**（`match err`） | 網羅性検査を取り上げ、**`_ =>` を強制する** |

**構築される型では、閉じていることに利益が無い。** 外部が全フィールドを
書けなければならない理由は無く、コンストラクタを通せば足りる。

**判別される型では、閉じていることこそが利益である。**
バリアントが増えたときに呼び出し側が止まることを、こちらは望んでいる。

**つまり非対称なのは方針ではなく、型の役割のほう。**
`Selector` の判断は別 ADR で扱うが、根拠はこの表と同じになる。

## 論点 3: 失敗の単位ごとに戻り値の型を分けるか（決定済み）

`Selector::select` は I/O では失敗しえないが、現在は `TallyError` を返している。
`LineError` を括り出す（論点 1）と、`Result<_, LineError>` に絞れる。
**論点 1 を採っても、この変更をしない選択はできる。** 独立した判断である。

### 決定

**分ける（3a）。** 行に紐づく処理は `LineError` を返し、
`tally_reader` だけが `TallyError` を返す。変換は `From<LineError> for TallyError` 1 つ。

```
Key::extract       → Result<Option<Cow>, LineError>
Selector::select   → Result<Option<Cow>, LineError>
Counter::push_line → Result<(), LineError>
tally_reader       → Result<Report, TallyError>   // ? で自動変換
```

**決め手は 2 つ。**

1. **`core.rs` が既にコメントで掲げている不変条件を、型に移すだけである。**
   モジュールドキュメントは「**I/O を一切持たない**ように切り出してある」と宣言しているが、
   エラー型の側ではそれが表現されていない。新しい設計を持ち込むのではなく、
   **既存の主張を型システムに担保させる**変更
2. **テストへの追加コストがほぼゼロ**（下記）

### 実測: テストへの影響

論点 1 を採る時点でテストは書き換わる。**3a による限界費用を読んで確認した。**

| テストの経路 | 3a の影響 |
| --- | --- |
| `strict_err` → `tally_reader` を呼ぶ | **無し**（`tally_reader` の戻り値型は変わらない） |
| `missing_field_err` → エラーを `match` | 論点 1 で**どのみち書き換わる**。3a による追加分は無し |
| `select_one` → `select(..).expect(..)` | **無し**（エラー型を名指ししていない） |
| 上記以外のエラー系テスト・統合テスト全件 | **無し。** すべて `tally_reader` 経由 |

**3a のコストは本番コードのシグネチャ 3 本と `From` 実装 1 つに閉じる。**
うち **`Key::extract` は非公開**なので、外部から見えるシグネチャの変化は 2 本。

### 案 3a. 分ける（`select` は `LineError` を返す）

* Good, because **シグネチャが「この関数は I/O で失敗しない」を表明する。**
  読み手が本文を読まずに知れる
* Good, because 呼び出し側が `match` するとき、ありえないバリアントが選択肢に出ない
* Bad, because 型が 1 つ増え、`?` による変換（`From<LineError> for TallyError`）が要る
* Bad, because **失敗の単位が増えるたびに型が増える。** 小さな CLI では冗長になりうる

### 案 3b. 分けない（`select` は `TallyError` を返し続ける）

* Good, because 変更が最小。`?` がそのまま通る
* Good, because 型が 1 つで済み、`match` の書き口が 1 通り
* Bad, because **シグネチャが嘘をつく。** `select` が `OpenInput` を返すことはないのに、
  型はその可能性を表明している
* Bad, because 呼び出し側が「この関数は実際どれを返すのか」を本文で調べる羽目になる。
  段階 2 で「約束を書いたコメントは検証可能な主張」と学んだが、
  **これは型が書いている検証可能な主張が偽である状態**

### 検討した代替案（`From` + 入れ子以外の実現手段）

**3a は「入れ子の enum + `From`」で実現するが、それが唯一の手ではない。**
外側の人間工学を上げる系統を 3 つ検討し、いずれも却下した。

| 系統 | 仕組み | 却下理由 |
| --- | --- | --- |
| **エラー集合**（`error_set`） | 部分集合関係から `From` を自動生成し、**入れ子を作らずに `match` を平らに保つ** | **解く問題が存在しない。** 論点 1 で共有文脈を外側の構造体に置いたので、入れ子は `TallyError::Line(LineError)` の 1 段しかない。「入れ子の網」が発生しない |
| **型レベル集合**（`terrors::OneOf`） | 匿名直和。`narrow` / `broaden` で**処理した分だけ集合が縮む**（OCaml の多相バリアント相当） | **集合を縮ませたい場面が無い。** 本クレートの失敗の集合は静的に決まっており、呼び出し文脈で変わらない |
| **context selector**（SNAFU） | バリアントごとに selector 型を生成し、`?` の各地点で変換と文脈付与を同時に行う | **文脈を積む深さが 2 段しかない。** 1 バリアントあたりの記述量が `thiserror` の 2 倍以上になる代償に見合わない |

**却下理由はいずれも「規模」であって、「その手法が劣る」ではない。**
これは [ADR-0002](0002-output-format-abstraction.md) で
「一般則は規模の関数」と書いたのと同じ形の議論である。

**判断が変わる条件**:

- **失敗の階層が 3 段以上になったら `error_set` を再検討する**（入れ子の網が生じる）
- **同じ関数の戻り値のエラー集合を、呼び出し側で縮めたくなったら `terrors`**。
  ここは Rust の `enum` が閉じているために言語では表現できない領域
  （`docs/learning-log.md` 節 6-3）

各系統の採用実態と、std がどちらへ賭けているかは
`docs/learning-log.md` 節 6-4〜6-6。**ここには重複させない。**

### 決定の帰結

- `pub type Result<T, E = TallyError>` という共通エイリアスが**全関数には効かなくなる**。
  `LineError` を返す関数はこのエイリアスに乗らない。
  **既定値をどちらにするかは実装時に決める**
- `Counter::push_line` は公開 API なので、**外部から見えるシグネチャが変わる**
- **`#[from]` による変換が `?` の全経路で成立するかは、実装して確かめる。**
  型推論が期待どおりかは、通すまで断定しない

## 論点 4: `serde_json::Error` を `#[source]` として公開するか（決定済み）

`LineErrorKind::InvalidJson { source: serde_json::Error }` は、
**`serde_json` を公開依存にする。**

### 決定

**公開したまま（4a）、安定 API でないことを doc コメントに明記する。**

**根拠は論点 2 と同じ。** 4a の代償は「`serde_json` が major を上げたとき、
こちらも major を上げる必要が生じる」だが、**下流が既知の小集合である以上、
この損失は発生しない。** 版を上げる相手が自分だけなら、版を上げること自体が費用ではない。

得られるものは実利がある。`{:#}` のエラーチェーンに
**serde_json の位置情報（行内の何文字目か）が乗る。**
`tally` は行番号までしか持たないので、**行内の位置は serde_json しか知らない。**

**ただし表示が紛らわしい。** `tally` は 1 行ずつ渡すので、
`serde_json::Error` の `line()` は**常に 1** になる。
Display には「at line 1 column N」と出るため、
**tally の行番号と衝突して読める。** 実装時に文言を確かめること。

### 案 4a. 公開したまま、安定 API でないと文書化する

* Good, because `{:#}` のエラーチェーンに **serde_json の詳細な位置情報**
  （行内の何文字目か）が乗る。利用者にとって実利がある
* Good, because 変更がゼロ
* Bad, because **`serde_json` が major を上げると、こちらも major を上げる必要が生じる。**
  自分のコードが 1 行も変わっていなくても
* Bad, because 文書化は自己申告であり、機械的な柵にならない

### 案 4b. 隠す（メッセージ文字列に変換して保持する）

* Good, because 公開依存が消え、依存の更新が自分の版に波及しない
* Bad, because **`source()` チェーンが切れる。** 原因を辿る手段が文字列だけになる
* Bad, because 位置情報を落とすか、自前で抜き出して持ち直すことになる

### 決定の帰結

- **doc コメントに「この `source` の型は安定 API ではない。エラー処理の分岐に
  使わないこと」と書く。** これは自己申告であって機械的な柵ではない。
  そのことを承知のうえで採る
- **公開ライブラリへ転用する場合、ここが最初の再検討対象になる。**
  `#[non_exhaustive]`（論点 2）と同じく、**転用時にまとめて見直す項目**
- **`Cargo.toml` の依存に `serde_json` が公開依存として現れる。**
  RFC 3516（public/private dependencies）の `public = true` と
  `exported_private_dependencies` lint が安定化したら、明示する

## 論点 5: ライブラリのエラーと CLI 固有のエラーを分けるか（決定済み）

### 決定

**分ける。** CLI 固有のエラー型を持ち、**`(エラー) → 終了コード` を純粋関数にする**
（cargo の `CliError`、jj の `CommandError` と同じ形）。

**決め手はテストである。** 下の「テストへの影響」の表のとおり、
5a では終了コードの網羅がプロセス起動の数に比例し、
かつ **「テストを書き忘れる」が検出されない。**
5b なら変換の `match` が網羅性検査を受けるので、**忘れるとコンパイルが止まる。**
これは論点 1 で採ったのと同じ論法（同じ誤りが二度できない形を選ぶ）である。

**現状**: ライブラリは `TallyError`（`thiserror`）、バイナリは `anyhow::Error`。
終了コードは `main.rs` の `is_broken_pipe` のような述語関数で個別に判定している。

### 案 5a. 現状維持（`anyhow` + アドホックな判定）

* Good, because **追加の型がゼロ。** 失敗の経路が 3 つしかない現状に見合う
* Good, because `context()` でメッセージを積め、`{:#}` で連結表示できる
* Good, because 新しい失敗を足すのに型を触らなくてよい
* Bad, because **「どの失敗がどの終了コードか」の一覧が存在しない。**
  判定がコードに散り、述語関数が増える
* Bad, because **分類が `downcast_ref` に依存する。** 型が増えると連鎖が伸び、
  網羅性検査が効かない（漏れてもコンパイルは通る）
* Bad, because 対処の示唆（論点 6）を載せる場所が無い
* Bad, because **判定ロジックが `main.rs` にある。**
  ただし **これは規約違反ではない。**
  `crates/tally/docs/layout.md` は `main.rs` に「引数解釈の呼び出し、I/O、
  **終了コード**、ログ初期化」を置いてよいとしており、`is_broken_pipe` は
  終了コードの決定に読める。禁じているのは「ロジック全般。
  **純粋関数にできるものは `core` へ**」のほう。
  **`is_broken_pipe` は純粋関数にできるので、そちらとは緊張がある。**
  しかし現行の分掌（ライブラリ層は `thiserror`、バイナリ層は `anyhow`）では
  `anyhow::Error` を取る関数を lib へ移せない。
  **移設先が無いから `main.rs` にある**のであって、怠慢ではない

### 案 5b. CLI 固有のエラー型を持つ（cargo / jj の形）

* Good, because **`(エラー) → 終了コード` が純粋関数になる。**
  終了コードの決定を lib 側に置けるので、`main.rs` の方針違反も同時に解消する
* Good, because 終了コードの一覧が 1 箇所に集まり、
  `crates/tally/docs/output-format.md` の契約（`0` / `1` / `2`）と突き合わせられる
* Good, because 対処の示唆をフィールドとして持てる（論点 6）
* Good, because lib のエラーが増えたとき、**変換の `match` がコンパイルエラーで漏れを教える**
  （論点 2 で `#[non_exhaustive]` を付けないと決めたので、この検査が効く）。
  **ただし効く範囲は `TallyError` 由来の分類だけ。**
  BrokenPipe は `TallyError` からは出ず、`main.rs` の stdout 書き込み
  （`write_report` と `flush`）が返す生の `io::Error` が経路である。
  その分類は `io::ErrorKind`（std 側で `#[non_exhaustive]`）を見ることになるので、
  **ここに網羅性検査は効かない**
* Bad, because **型が 1 つ増える。** 現状の失敗の経路は 3 つしかない
* Bad, because `anyhow` の `context()` の手軽さを一部手放すか、
  両方を併用して**エラーの表現が 2 系統になる**
* Bad, because 変換関数の置き場所を決める必要がある（`cli.rs` か新規モジュールか）

### テストへの影響（この論点の実質）

**このリポジトリのテスト方針は「統合テストはそこでしか検証できないものだけ」。**
論点 5 はこの方針に直接効く。

| 検査したいこと | 案 5a | 案 5b |
| --- | --- | --- |
| 終了コードの決定規則（網羅） | **統合テストのみ。** 経路ごとにプロセス起動 | **ユニットテスト。** 純粋関数に入力を並べる |
| 終了コードが実際に返ること | 統合テスト | 統合テスト（**1〜2 件で足りる**） |
| BrokenPipe を成功として扱う | 統合テスト（パイプの構成が要る） | ユニットテストで規則を、統合で配線を。**ただし網羅性検査は効かない**（`io::ErrorKind` は std 側で `#[non_exhaustive]`） |
| 新しい失敗を足したときの漏れ | **テストを書き忘れると気づけない** | **変換の `match` がコンパイルエラー** |

**要点は 2 つ。**

1. **5a では終了コードの網羅がプロセス起動の数に比例する。**
   失敗の経路が増えるほどテストが遅くなる。段階 6 以降で経路は増える見込み
2. **5a では「テストを書き忘れる」が検出されない。** 5b では
   変換の `match` が網羅性検査を受けるので、**忘れるとコンパイルが止まる。**
   これは論点 1 で採ったのと同じ論法（「同じ誤りが二度できない形を選ぶ」）

**ただし 5a でもユニットテスト自体は不可能ではない。**
`main.rs` に `#[cfg(test)] mod tests` を書けば実行される。
**問題は書けないことではなく、書くとロジックが `main.rs` に居座ることを追認する点にある。**

### 決定の帰結

- **終了コードの決定規則がユニットテストで網羅できる。**
  統合テストは「配線されていること」の確認だけに減らす
- **`is_broken_pipe` に移設先ができる。** これまでは `anyhow::Error` を取るため
  lib へ移せなかった。`layout.md` の「純粋関数にできるものは `core` へ」に沿える
- **実行時エラーの終了コードが 1 箇所に集まる。**
  **ただし全部ではない。** 引数の誤り（`2`）は `Cli::parse()` が `run` の前に
  返すので、この関数を通らない。`output-format.md` の契約
  （`0` / `1` / `2`）のうち、**`2` は clap 側に残る**
- **論点 6（hint）の置き場所が確保された。** ライブラリ側に
  「`--strict` を外せ」のような CLI の語彙が漏れる心配がなくなる
- 型が 1 つ増える。変換関数の置き場所を決める必要がある（実装時に決める）
- **`anyhow` を残すか、CLI 固有の型に一本化するかは実装時の判断。**
  併用するとエラーの表現が 2 系統になるので、そこは意識して決める

## 論点 6: 対処の示唆（hint）を型で持つか（決定済み）

### 決定

**持つ（6a）。** CLI 固有のエラー型に `Option<&'static str>` 相当の hint を載せる。
**ただし書く範囲を絞る。**

- **書くのは「利用者の操作で解決できる失敗」だけ。**
  例: `--strict` によるフィールド欠損、引数の誤り
- **入力そのものが壊れている場合には書かない。**
  `InvalidJson` に対する「JSON を直せ」は情報量がゼロ
- **既定は `None`。** 示唆の無い失敗のほうが多い

### 根拠

**文言の価値ではなく、設計時の強制的な問いかけとしての価値を採る。**

hint のフィールドがあると、論点 5b の変換（エラー → 終了コード）を書くときに
**「この失敗に対して利用者は何ができるか」が視界に入る。**

**論点 1 と同じ論法ではない。** 論点 1 は書き忘れが**型として不可能**だが、
hint は `None` と打鍵すれば済む。**弱い類推であることを認めておく。**

したがって帰結として次を課す。**コンストラクタや `Default` で hint を
既定値にしない。** 既定化した瞬間、打鍵の強制すら消えて価値がゼロになる。

### 承知のうえで受け入れる代償

- **示唆を書けるのは現時点で実質 1 件**（`MissingField` に対する `--strict`）。
  「1 件のためにフィールドを増やすのは過剰」という反論は成り立つ。
  [ADR-0002](0002-output-format-abstraction.md) の
  「投機で設計を重くしない」とは逆方向の判断である点を明記しておく
- **示唆の質が悪いと害になる。** 「`--strict` を外せ」は、
  入力の検査が目的の利用者にとっては誤った助言。**範囲を絞る規則はこのため**
- 文言は仕様変更で腐る。`--strict` の意味が変われば hint も変える必要がある

### 案 6a. 持つ（採用）

jj は `CommandError` に **hint**（利用者が次に何をすればよいか）を持たせている。
「何が起きたか」ではなく「どうすればよいか」を型のフィールドにする発想。

```
error: 2 行目からフィールド `lvl` を取り出せません: "{\"other\":1}"
hint: --strict を外すと、この行はスキップされます
```

* Good, because 診断の質が上がる。**CLI の価値の大半はエラーメッセージにある**
* Good, because 「示唆を持つ場所」が型にあると、書き忘れが目に見える
* Bad, because 文言の保守対象が増える
* Bad, because 示唆の無い失敗にも `Option` の分岐が付いて回る

### 案 6b. 持たない

* Good, because 型が小さく保たれ、変換の `match` が終了コードだけを決める
* Good, because 文言の保守対象が増えない
* Bad, because 示唆を出したくなったとき **`eprintln!` を散らすことになる。**
  論点 5b で終了コードについて避けたのと同じ形の散逸
* Bad, because 「この失敗に対して利用者が何をすればよいか」を
  **設計時に問わなくなる**

### 決定の帰結

- **置き場所は CLI 固有の型。** ライブラリ側に「`--strict` を外せ」のような
  CLI の語彙は漏れない（論点 5b の帰結）
- **hint は stderr にのみ出す。** stdout はデータ専用という既存の契約
  （`crates/tally/docs/output-format.md`）を変えない
- **示唆を書ける失敗が増えたら、範囲を絞る規則のほうを見直す。**
  規則が実態に合わなくなったら、それは規則の側の問題

## 論点 7: エラー型の大きさ（未測定）

段階 2 で **`Result<T, E>` の大きさは最大バリアントで決まり、
その `Result` は 1 行につき 3 段返る**ことを実測した
（`docs/learning-log.md` 節 6-1）。**失敗しない行もこの大きさを払う。**

論点 1 の変更は各バリアントの構成を変えるため、大きさが変わる。

**憶測で書かない。** `size_of::<TallyError>()` と `size_of::<LineError>()` を
実装後に測り、変更前の値と並べて記録する。**測る前にこの節へ数値を書かない。**

## 確認方法（Confirmation）

1. 論点 1: **`LineError` を受け取る文脈で「行番号を取る」コードが
   `match` を含まないこと**をコードで示す（`TallyError` からは `Line(e)` を
   1 回剥がす必要がある。それは想定どおり）
2. 論点 3: `Selector::select` のシグネチャが `Result<_, LineError>` になっていること
3. 論点 5: **終了コードの決定規則がユニットテストで網羅されていること。**
   統合テストは配線の確認だけに減らす
4. 論点 6: hint が **stderr にのみ出ること**を統合テストで検査する。
   **2 方向とも見る** — stdout の完全一致で「混ざっていない」ことを、
   stderr の部分一致で「実際に出ている」ことを言う。片方だけでは足りない
5. **`Display` と `source()` の合成規則を決め、
   「抜粋の制御文字が単一エラーの `to_string()` に載る」ことを保ったか確かめる。**
   ここは本 ADR が決めずに実装へ持ち越した唯一の項目
6. 論点 7 の実測値を記録する

段階 5 の完了条件は `docs/curriculum.md` が正本。ここには重複させない。
