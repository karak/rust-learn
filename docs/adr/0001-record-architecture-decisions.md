# 1. アーキテクチャ意思決定を ADR として記録する

- ステータス: Accepted
- 日付: 2026-08-16

## コンテキスト

このリポジトリは学習用だが、設計判断が積み上がってきた。
`crates/tally/docs/layout.md` に「押さえておくべき設計判断」の表があるものの、
**表は結論しか持たない。** 検討した代替案、却下した理由、判断が変わる条件が残らない。

実際に問題が起きた。段階 2 の整理で `Selector` の doc に書いた
「後続のフラグを足しても壊れない」という主張が偽だと判明したが、
**そう判断した根拠も、何を検討しなかったかも記録に無かった**ため、
指摘を受けるまで誤りに気づけなかった。

段階 3 は「trait にすべきか」という、結論より過程に価値がある判断を含む。

## 決定

**アーキテクチャ上の意思決定を ADR として `docs/adr/` に記録する。**

- ファイル名: `NNNN-kebab-case-title.md`（4 桁連番）
- 形式は判断の性質で選ぶ。複数案の厳密な比較は **MADR**、
  単純な因果関係の記録は **Nygard**

### ステータスと改訂の扱い

ステータスは `Proposed` → `Accepted` → `Deprecated` / `Superseded` と遷移する。
**改訂できるかどうかはステータスで決まる。**

| ステータス | 中身の変更 | やり方 |
| --- | --- | --- |
| **Proposed** | **可**。まだ決定ではなく草案である | **改訂履歴を付けて同じファイルを更新する。** 何をどう変えたかを残す |
| **Accepted** | **不可**。決定の記録であり歴史である | **新しい ADR を作り**、古いほうを `Superseded by ADR-NNNN` にする |

`Accepted` でも、誤字の修正や記述の明確化といった **決定を変えない編集** は
行ってよい。その場合は **改訂履歴に「明確化」と明記する**。
判断が変わったのか、書き方を直しただけなのかが後から区別できることが重要。

`layout.md` の表は「いま守るべきこと」の一覧として残し、
**その判断に至った過程は ADR を参照する**、という分担にする。

## 帰結

- 「なぜそう決めたか」と「何を捨てたか」が残る。数ヶ月後の自分が再検討できる
- 判断が変わったときも、変わった事実そのものが履歴になる
- `Proposed` のうちは自由に直せるので、**レビューを受けてから確定させる**運用になる。
  実際 ADR-0002 は敵対的レビューで中心論証が崩れ、`Proposed` のまま全面改訂した
- 一方、記述のコストが増える。**すべての判断を ADR にはしない。**
  代替案を検討した記録が価値を持つものに限る
