**Rust 固有の意思決定** に絞った順序。
各段階に「`tally` に加える機能」を割り当ててあり、読むだけで終わらないようにしてある。

各段階の完了条件は共通して:
`cargo fmt --all` / `cargo lint`（`pedantic` 込み）/ `cargo t` が通ること。

## 段階 1: 所有権・借用・ライフタイム（済）

**扱う概念**: move / `Copy`、`&` と `&mut` の排他性、ライフタイム注釈が
「関係の記述」であること、`Cow`、スライスと `Vec` の関係。

**課題**: `tally` に `--ignore-case` を足す。
`Cow` を維持したまま実装すること（大文字小文字が同じなら借用のまま返す）。
安易に全行 `to_lowercase()` すると、この課題の意味が消える。

**確認**: `cargo lint` を通し、アロケーションが増えないことを説明できる。

**参照**: `.claude/skills/rust-ownership-coach/`

### 実装の記録

`crates/tally/src/core.rs` の `needs_lowering` / `fold_case` / `Selector`。

学んだことは 3 つ。

1. **`Cow` を保つ判定は「大文字か」ではなく「小文字化で変化するか」。**
   `'ǅ'` (U+01C5) は Titlecase なので `char::is_uppercase()` は `false` を返すが、
   `to_lowercase()` では `'ǆ'` に変わる。前提そのものをテストで固定してある
   （`タイトルケース文字も畳まれる` の冒頭の assert）。
2. **`to_lowercase()` は 1 文字とは限らない。**
   `'İ'` (U+0130) は 2 文字に伸びるため、ASCII 前提の in-place 変換は使えない。
   ASCII に限れば長さが変わらないので `make_ascii_lowercase` で
   2 度目のアロケーションを避けられる。
3. **フラグを `Key` に足さず `Selector` に畳んだ。**
   「どこから取るか」と「どう正規化するか」は別の関心事で、
   混ぜると段階 2・4 でフラグが増えたときにシグネチャが壊れる。

**証跡**（段階 1 完了時点で `cargo t` が全件通過。件数は増えるので記載しない）:

| 保証する内容 | テスト |
| --- | --- |
| 借用が維持される（本課題の主眼） | `core::tests::小文字化で変化しない値は借用のまま返る` |
| 変換が必要なときだけ所有値になる | `core::tests::小文字化が必要な値だけが所有値になる` |
| Titlecase も畳まれる | `core::tests::タイトルケース文字も畳まれる` |
| 長さが変わる文字でも壊れない | `core::tests::小文字化で長さが変わる文字も壊れない` |
| 値には効きフィールド名には効かない | `core::tests::ignore_case_は値に効きフィールド名には効かない` |
| CLI として配線されている | `cli::ignore_case_で大文字小文字をまとめて集計する` ほか 2 件 |

## 段階 2: エラーモデル（済）

**扱う概念**: `Result` と `?` の変換、`From`、`thiserror` と `anyhow` の役割分担、
エラーチェーン、`io::ErrorKind`。

**課題**: `--strict` フラグを足す。既定ではスキップしている
「フィールドが無い行」を、`--strict` 時はエラーにする。
エラーには行番号と、その行の先頭 40 文字を含める。

**確認**: 統合テストで終了コードと stderr の文言を検証する。

**参照**: `.claude/skills/rust-error-handling/`

### 完了条件（着手前に定義）

- [x] `--strict` 指定時、キーを取り出せない行で**失敗し、終了コードが 1** になる
- [x] エラーメッセージに **行番号** と **その行の先頭 40 文字** が含まれる
- [x] 抜粋が**マルチバイト文字の途中で切れても panic しない**
- [x] 抜粋に含まれる**制御文字がそのまま端末へ出ない**（ログインジェクション対策）
- [x] **`--strict` 未指定時の挙動が変わらない**（既存テストが無修正で通る）
- [x] `cargo fmt --all --check` / `cargo lint` / `cargo t` が通る

### 実装の記録

`error.rs` の `TallyError::MissingField`、`core.rs` の `snippet()` と `Selector::strict`。

学んだことは 4 つ。

1. **段階 1 で `Selector` に畳んだ設計が実際に効いた。**
   `--strict` の追加で `select` の呼び出し側を **1 箇所も変えずに済んだ**。
   `Key` に bool を足す案を採っていれば、抽出と正規化と厳格さが 1 つの型に混ざっていた。
2. **`char_indices().nth(n)` が返すバイト位置は必ず文字境界。**
   `&line[..40]` はマルチバイト文字の途中に当たると panic する。
   境界を求めてから一度にコピーすれば、1 文字ずつ積むより確保回数も少ない。
3. **エラーメッセージに入力をそのまま埋めない。** `{:?}`（`str` の `Debug`）を使えば
   非表示・非印字の文字がエスケープされ、追加依存なしにログインジェクションを防げる。

   **「JSON なら危険な文字は入らない」は誤り。** JSON がエスケープを要求するのは
   C0 制御文字（U+0000..=U+001F）だけで、それ以外は生で書ける。実測すると
   U+202E（RTL override）と U+007F（DEL）は合法な JSON 文字列を素通りして到達する:

   ```
   $ printf '{"a":"\u{202e}RTL\u{7f}"}\n' | tally --field lvl --strict
   error: ... "{\"a\":\"\u{202e}RTL\u{7f}\"}"
   ```

   なお **stdout 側では意図的にエスケープしていない。** stdout は他のツールへ渡す
   データでありバイト透過に保つ。エスケープするのは人間が読む stderr のほうだけ。
   この非対称は仕様であって漏れではない。
4. **`--strict` は「取り出せたか否か」で一貫させた。** キーの不在と値が `null` を
   区別していない。区別する設計も可能だが、フラグの意味を説明なしに理解できるほうを採った。

**証跡**（段階 2 完了時点で `cargo t` が全件通過）:

| 保証する内容 | テスト |
| --- | --- |
| 欠損行で失敗し行番号が正しい | `core::tests::strict_でフィールドが無い行はエラーになる` |
| `null` も欠損として扱う | `core::tests::strict_では_null_値もエラーになる` |
| 既定の挙動が変わらない | `core::tests::strict_なしなら従来どおりスキップされる` |
| 行全体がキーなら無効 | `core::tests::行全体がキーなら_strict_でも失敗しない` |
| 抜粋が 40 文字に切れる | `core::tests::抜粋は先頭_40_文字に切り詰められる` |
| マルチバイトで panic しない | `core::tests::抜粋がマルチバイト境界で切れても_panic_しない` |
| 制御文字がエスケープされる | `core::tests::抜粋の制御文字は生のまま表示されない` |
| CLI として配線されている | `cli::tests::strict_指定が_selector_に反映される` |
| 終了コードと stderr | `cli::strict_はフィールド欠損で失敗し行番号と抜粋を示す` |

## 段階 3: トレイトとジェネリクス

**扱う概念**: トレイト境界、`impl Trait`（引数位置と戻り値位置の違い）、
`dyn Trait` と単相化のトレードオフ、関連型 vs 型パラメータ、
孤児ルール（orphan rule）、`From`/`Into`/`AsRef`/`Deref`。

**課題**: 出力形式を `Format` の `enum` + `match` から、
`trait Formatter { fn write(&self, out: &mut dyn Write, report: &Report) -> Result<()> }`
に切り替える。CSV 形式を追加する。

**問い**: `Box<dyn Formatter>` と `impl Formatter` のどちらを選ぶか。
この場面での動的ディスパッチのコストは実測でどれくらいか。
**enum + match のままのほうが良い可能性も検討すること**（Rust では
「トレイトにすべき」が常に正解ではない）。

## 段階 6: 並行・並列

**扱う概念**: `Send` / `Sync` が何を保証するか、`std::thread::scope`、
チャネル、`Arc<Mutex<T>>`、`rayon` のデータ並列、
そして **「並列化しても速くならない」典型パターン**。

**課題**: 複数ファイルを引数に取れるようにし、ファイル単位で `rayon` 並列化する。
`Counter` のマージ処理を実装する（`Extend` か、専用の `merge` メソッド）。

**確認**: **ベンチで実測する。** ファイル 1 個・10 個・1000 個で比較し、
I/O バウンドの場合に並列化が効かない（あるいは遅くなる）ことを確認する。
`divan` でベンチを書く。

## 段階 8: `unsafe` の境界（読むだけ）

**扱う概念**: `unsafe` が無効化するのは何か（借用検査ではない）、
未定義動作の実例、健全性（soundness）と安全な抽象、`miri`。

このリポジトリでは `unsafe` は `deny` のままにする。
**書くのではなく、標準ライブラリや依存クレートの `unsafe` を読んで、
どう安全性を担保しているかを説明できるようにする。**

```bash
rustup component add miri
cargo +nightly miri test -p tally
```
