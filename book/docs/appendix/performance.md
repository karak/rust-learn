# 付録 A 性能を測って直す（プロファイリングとメモリ）

性能を上げるときに最初にやることは、コードを書くことではない。
どこに時間が掛かっているかを測り、改善を 1 つずつ入れて、同じ条件で比べ直すことである。
この付録では、`tally` を 1000 万行の入力で測り、JSON 入力を 2.29 倍、行全体キーを 1.80 倍にしたときの計測と判断の記録を辿る。

## 測る前に、プロファイルと時間計測の道具を分ける

「どこが重いか」と「どれだけ速くなったか」は、別の道具で測る。
プロファイラの下では計測の負荷が乗って実行時間が伸びるため、端から端までの時間は `release` ビルドを単独で測る必要がある。

[Cargo](../glossary.md#cargo) の既定の `release` プロファイルは最適化が効く代わりにデバッグ情報を持たない。
さらに `[profile.release]` で `strip = "symbols"` を付けていると、シンボル表の関数名まで削られる。
`Cargo.toml` に `release` を継承した専用プロファイルを足しておくと、最適化を保ったままデバッグ情報とシンボルを残せる。

```toml
[profile.profiling]
inherits = "release"
debug = true
strip = "none"
```

`tally` の計測では、この `profiling` プロファイルでビルドしたバイナリを `samply`（サンプリングプロファイラ）で取り、端から端までの時間は `release` ビルドを `hyperfine` で測った。
また、比較のたびに中身が変わらないよう、1000 万行の入力は乱数を使わず行番号から決まるスクリプトで生成した。
キーは 4 種類の繰り返しで、JSON は 2 フィールドのエスケープ無し、行全体も前後の空白無しという条件である。

## 1000 万行で測ると、予想の順位と内訳がずれた

計測は手元の 10 コアの Mac（性能コア 4 + 効率コア 6）で、ページキャッシュが温まった状態で行った。
入力は 1000 万行の 2 種類である。JSON 行から 1 フィールドを抜く場合と、行全体をキーにする場合をそれぞれプロファイルした。

| 上位 | JSON 入力（`--field`） | 行全体キー |
| --- | --- | --- |
| 1 | `serde_json::Value` の構築 31.5% + 破棄 15.8% | 行ごとの [`String`](../glossary.md#string-str) 確保と [UTF-8](../glossary.md#utf-8) 検証 |
| 2 | `read` システムコール 17.4% | `read` 9.2% |
| 3 | ハッシュ（SipHash）約 6% | ハッシュ約 9%、`trim_matches` 5.7% |

測る前の予想では、JSON は「パースが重い」と見込んでいた。
実際の内訳は、1 フィールドしか要らないのに行の全フィールドを [`BTreeMap`](../glossary.md#btreemap) に組み立てて行ごとに捨てており、**破棄だけで 15.8%** を占めていた。
一方、既に数えたキーを毎回確保するコストが 2 番目に来るという予想は外れ、JSON 側では 2 番目が `read` システムコール（17.4%）だった。
推測のまま手を入れていれば、JSON では 2 番目でなかった確保を、2 番目の対策として先に直しにいっていた。

## 効いた改善は 3 つ、戻した改善は 1 つ

改善案はまとめて入れず、1 つずつ単独で測って採否を決めた。

| # | 改善 | JSON（1000 万行） | 行全体（1000 万行） | 採否 |
| --- | --- | --- | --- | --- |
| 1 | `BufRead::lines()` をやめ、1 本のバッファを使い回す | 1.808 → 1.613 s | 610 → 403 ms | 採用 |
| 2 | `serde_json::Value` を作らず、1 フィールドだけ取り出す | 1.613 → 869 ms | 影響なし | 採用 |
| 3 | 行全体キーの空白除去を ASCII ならバイト単位に | — | 1.01 ± 0.04 倍 | 戻した |
| 4 | [`HashMap`](../glossary.md#hashmap) のハッシュを `foldhash` に差し替える | 869 → 829 ms | 422 → 366 ms | 採用 |

基準と最終のバイナリを 15 回ずつ並べて測った通しの結果は、JSON 入力が 1.903 s から 832.5 ms（2.29 ± 0.22 倍）になった。
同じ条件で行全体キーも測ると、682.9 ms から 379.4 ms（1.80 ± 0.36 倍）まで縮んだ。

### 改善 1: 行ごとの確保を消す

`BufRead::lines()` は[イテレータ](../glossary.md#iterator)が 1 行ごとに新しい `String` を[ヒープ](../glossary.md#heap)に確保して返す。
`String` を 1 本だけ用意し、`buf.clear()` と `read_line(&mut buf)` で使い回すと、`lines()` が行ごとに行っていた 1000 万回の確保と解放が消える。
行全体キーではこれだけで 610 ms から 403 ms まで縮んだ（3 章の「`lines()` は行ごとに確保する」で触れた測定と同じものである）。

### 改善 2: DOM を作らずに必要な 1 フィールドだけ読む

`serde_json::from_str::<Value>(line)` は、行の JSON 全体をツリーに組み立てる。
`serde` で JSON を型へ変換するときに使う通常の `Deserialize` trait は、型だけで振る舞いが決まり、実行時に渡されたフィールド名を持ち込めない。
代わりに `self` に状態を持てる `DeserializeSeed` と、構文を順に受け取る `Visitor` を使うと、探すフィールド名に一致した値だけを拾い、ほかのフィールドは `IgnoredAny` で読み捨てられる。

さらに、`Deserializer::from_str` で行の `&str` を直接読んでいる場合、`Visitor::visit_borrowed_str` は入力文字列にエスケープが無いときだけ呼ばれ、行の一部をそのまま[借用](../glossary.md#borrow)した `&str` を渡す。
そこで `Cow::Borrowed` を返せば、抽出の段階での文字列コピーも消える（マップへ入れるときに所有する `String` を確保するかは、呼び出し側の設計による）。
ただし、JSON オブジェクトでない行（数値や配列だけの行）は `deserialize_map` だとエラーになるため、`deserialize_any` で受けて「フィールドが無い行」と同じ扱いに揃え、仕様をテストで固定した。
速くするための書き換えは静かに振る舞いを変えることがある。

### 改善 4: ハッシュ差し替えは速さだけで決めない

標準ライブラリの `HashMap` が既定で使う `SipHash 1-3` は、速さより安全性を優先して乱数シードを持つ。
外から渡された入力でハッシュ衝突を意図的に起こさせ、表の操作全体を O(n²) に落とす攻撃（HashDoS）を防ぐためである。

`tally` のキーは利用者が渡すログ行そのものなので、固定シードの高速ハッシュを選ぶと衝突を事前計算される余地が残る。
コンパイラの内部のように入力が信頼できる場面とは前提が違う。
そこでインスタンスごとに乱数シードを持つ高速な `foldhash` を選び、JSON で 869 → 829 ms、行全体で 422 → 366 ms に縮めた。
乱数シードは衝突の事前計算を防ぐが、`foldhash` 自身は、応答を見ながら入力を変えてくる対話的な攻撃者に対する HashDoS 耐性までは主張していない。

## プロファイルの上位を直しても、速くならないことがある

改善 3 では、プロファイルで上位に入っていた `trim_matches`（`str::trim` が内部で呼ぶ空白除去の関数）を置き換えた。
ところが単独測定では 1.01 ± 0.04 倍しか動かず、ノイズと区別できなかったため元に戻した。

サンプリングプロファイラは「どの命令のところで止まっていたか」を数えるが、命令数が重いのか、メモリの到着を待っているだけなのかは区別しない。
メモリアクセスや別の要因が支配的な処理では、命令数を減らしても端から端までの時間が縮まらないことがある。
改善案をまとめて入れてしまうと、こうした効かない変更が「効いたもの」に紛れて残る。

もう 1 つ、空白除去の置き換えで仕様のずれが見つかった。
`str::trim` は Unicode の `White_Space` を削るが、`str::trim_ascii` は WhatWG の定義に従うため、ASCII の垂直タブ（`0x0B`）を空白と見なさない。
「ASCII なら速いほう」と気軽に置き換えると、先頭や末尾に垂直タブを含む行のキーが変わるのに、型検査は何も言わない。
コードは戻し、垂直タブを空白として扱うことを確かめるテストを書いた。

## 測定のノイズは、同じ時間帯に 2 つのバイナリを並べて消す

計測の途中で、同じコマンドの時間が 389 ms から 684 ms へ跳ね上がった回があった。
別の作業で動いていたブラウザが CPU を占有し、機械の負荷平均が 49 に達していたためである。

「同じ機械で測る」だけでは足りない。
測る前に `uptime` で負荷を確かめ、改善前と改善後のバイナリを 2 つ用意して、同じ `hyperfine` の 1 回の実行で続けて並べて測ると、時間帯によるぶれを抑えられる。

また、ページキャッシュが温まった状態と冷えた状態では、測っている対象そのものが変わる。
12 章の末尾で触れた複数ファイルの並列化のように CPU の時間を縮めた場合、キャッシュが冷えた状態では隠れていたファイル読み込みの I/O が表に出て律速になりうる。
「何倍速くなったか」を書くときは、入力の規模や偏りだけでなく、キャッシュが温かいか冷たいかという前提も添える必要がある。
